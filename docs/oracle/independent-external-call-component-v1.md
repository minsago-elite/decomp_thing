# Independent external-call component v1

This component composes independently captured physical call instructions with the rich ELF's dynamic-symbol, version and relocation records. Its inputs contain no recovered model, recovered function boundaries, or recovered call graph. It is a candidate evidence producer; neither successful parsing nor an `ext-…` token grants production source authority. `complete`, `releaseEligible`, `negativeCompleteness`, and `sourceCallPopulationComplete` remain false. The component enumerates every site in its committed source report, whose positive-only traversal is itself incomplete.

`IndependentExternalCallWorkerV1` accepts a canonical closed request naming committed rich ELF, original machine-call report and original machine-call request bytes, the authenticated bundled Ghidra runtime, output path, and bounded limits. It uses the same isolated JAR loader and pinned x86 language as the machine-call worker. A separate owner must still provide and retain process containment, launch/execution receipts, immutable capture, and production qualification. Original absolute paths embedded in the source request are not reopened. The source report is validated against that request, and every physical call is re-decoded from the currently authenticated rich ELF bytes before composition.

## ELF population and joins

The bounded parser retains the section-declared dynamic-symbol population, including null entries, undefined symbols with nonzero `st_value`, weak and NOTYPE symbols, defined symbols, and IFUNC resolvers. It retains raw relocation records, overlapping runtime table membership, GNU version records, hidden bits, and requested provider names. `PT_DYNAMIC`, section metadata and file-backed `PT_LOAD` mappings must agree. Version-chain counts, links, hashes and dangling indices are checked. The current profile requires ELF64 little-endian x86-64 and section-backed metadata; hash-table population reconciliation and packed relocations remain explicitly unsupported.

A call can reference a static import request only when the byte decoder identifies one exact eight-byte memory slot and a unique supported active relocation identifies the corresponding dynamic symbol. No PLT layout, instruction mnemonic, symbol spelling, or fixed stub width supplies a target. The supported forwarding case is one exact indirect-jump instruction at the direct call's physical destination. ENDBR/NOP-prefixed stubs, multi-instruction forwarding chains, register calculations and other unsupported forms stay unresolved. The forwarding instruction belongs to the original physical call record; it does not create a second semantic call.

The relocation-write index conservatively checks all active relocation writes for overlap with a candidate slot. A write at `slot + 4`, unknown write width, overflowing write, duplicate relocation, partial/zero-filled slot, or unexpanded relocation mechanism prevents a unique static association. Widths are pinned to the referenced LP64 glibc implementation; COPY uses the declared destination size as a bound and TLSDESC covers both words. These checks do not model arbitrary runtime code or claim immutable pointer contents.

## Typed memory-transfer evidence

`ByteStaticMemoryTransferDecoderV1` receives only an address and an owned byte window. It uses bundled Ghidra Java APIs without a `Program`, analysis manager, recovered graph, or an external installation. Raw p-code must show a constant default-RAM slot read, optionally through exact COPY operations, consumed by the typed indirect transfer. Ghidra's implicit memory varnodes and explicit LOAD operations are distinguished. Register/indexed values, arithmetic transforms, conflicting writes, competing transfers, context changes and unsupported p-code remain unresolved or fail closed. The static-memory receipt must match the separate basic decoder's address, complete instruction bytes, length, classification and context.

A constant slot address is evidence of where a pointer is read. It is not the pointer value or the runtime callee. Every record preserves its original caller identity, instruction RVA, physical target, return PC, source disposition and ordinal. Independent target-binding evidence is separate from final composition disposition, so an excluded or unresolved caller never receives a composed positive merely because its target slot is understood.

## Object-local external namespace

The namespace commits the rich input SHA-256 and every eligible section-declared undefined dynamic symbol. An entry's identity includes the dynamic-symbol table/index, exact name, symbol type/binding/visibility, GNU version raw/index/hidden/kind/name, and requested provider name. Its token is `ext-` followed by the SHA-256 of that canonical versioned identity. `externalNamespaceSha256` commits the entire canonical namespace document. It must be shared by independently normalized oracle and recovery claims before comparison.

A token identifies an object-local import request, not an actual resolved provider or implementation. Weak symbols may remain null; IFUNC implementations and interposition remain unresolved. NOTYPE imports cannot establish function identity. Runtime provider and implementation availability remain false even for the supported strong-function request case. Recovery normalization must establish its own physical reference/slot chain and cannot select a token by copying an oracle call row or matching a bare recovered name.

## Bounds and retained authority

Defaults cap source sites at 100,000, composition work at 100,000,000 units, canonical output at 64 MiB, and elapsed work at 1,800,000 ms. Input caps are 512 MiB rich ELF, 64 MiB source report, and 64 KiB source request. The closed metadata policy caps dynamic entries at 65,536, dynamic symbols and version records at 131,072, relocation records at 1,000,000, individual strings at 16 KiB, aggregate strings at 8 MiB, and metadata reads at 256 MiB. Record, byte and work budgets supplement wall/cancellation checks. These are component resource bounds, not benchmark acceptance thresholds.

The closed report validator checks schema, populations, order, duplicates, namespace commitments, typed witness coordinates, dispositions and request/runtime commitments. It verifies internal consistency only. Production handoff must additionally authenticate source artifacts, actual execution and capture before a later ledger may consume positive witnesses. Absence from this report never establishes a negative call fact or proves a recovered claim fabricated.
