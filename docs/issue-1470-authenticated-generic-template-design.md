# Authenticated generic template evidence: design proposal

**Review artifact for the open design issue.** This document proposes a bounded contract and implementation issue set for independent review. It is not a frozen or accepted contract, and authorizes no producer, observation sink, truth projection, schema migration, or production qualification. The reviewed repository baseline is master commit `e5ff2c537c09eb3c048cba80a1ac53dcf00f2d6a` (merged PR #1469).

## Decision

Use a versioned Clang frontend evidence adapter as the first supported generic-template provider. It must run with the exact Clang frontend authenticated for the build action, over the authenticated source and build inputs, and record compiler-owned declaration relationships and typed template arguments. A separate raw-input validator replays that action and regenerates the evidence. The serialized frontend output is a transport artifact, never truth by virtue of its own digest.

DWARF remains the source of physical emitted-instance evidence. Frontend pattern facts and DWARF DIE facts have different physical locators and are not joined by names, mangling, candidate hashes, offsets, visitation order, or approximate coordinates. DWARF5 §2.23 explicitly says the format does not represent generic definitions, but represents each instantiation and its actual parameters; §3.3.7 and §5.7.7 make the same limitation for function and class templates. Therefore a missing frontend proof remains unknown. The GCC and Clang DWARF5 records inspected for #1469 show typed concrete instances but no generic-pattern-to-instance edge. The accepted ordinary `DW_AT_abstract_origin` edge in #1469 is inline evidence only.

The generic facts use a new `full-tree-generic-template-evidence-v1` schema/policy. They do not extend observation-v2 or truth-v3. When they are eventually projected, use additive observation-v3 and truth-v4 paths; keep observation-v1/v2 and truth-v2/v3 schemas, policies, digests, APIs, and migration vectors byte-for-byte unchanged. The generic source census remains separate from emitted-RVA score denominators.

## Evidence and feasibility

| Evidence inspected | What it supports | Limit |
| --- | --- | --- |
| Official DWARF5 §2.23, §3.3.7, §5.7.7 | Concrete template-instance DIEs and typed actual parameters can be retained. | No portable generic-definition DIE or mandatory pattern-to-instance link. |
| Merged #1469 at the reviewed baseline; source-identity producer/model and fixture report | Bounded artifact-bound DIE rows, ordered typed actuals, concrete candidate identities, unknown generic links, digest-bound scope/inventory, and existing no-partial-publication controls. | It intentionally has no source/frontend generic relation. |
| Clang LibTooling and AST API documentation | A `ClangTool` runs a `FrontendAction` with a compilation database; `FunctionDecl::getPrimaryTemplate`, `ClassTemplateSpecializationDecl::getSpecializedTemplateOrPartial`, and `getTemplateArgs` expose semantic links and typed actuals. | This is a Clang-specific interface. Its records still require authenticated inputs and raw replay. |
| Clang JSON compilation database specification | A command entry records the working directory, main source and compile command; the `arguments` vector is preferred over shell text. | A database describes a command; it does not attest that it ran or that its ambient files/environment were controlled. |
| Official GCC template-instantiation documentation | GCC may emit duplicate instances per translation unit and let the linker discard duplicates. | Emission/linker behavior is not a generic source identity relation. GCC is not a v1 frontend provider. |

The feasibility claim is deliberately narrow: Clang's semantic AST APIs offer direct template declaration pointers and ordered `TemplateArgument` values, so a bounded C++ `FrontendAction` can serialize those relationships without parsing names. PR #1469 already established that the selected C++ compiler fixtures contain the concrete-instance side of the evidence and that the DWARF side lacks the generic edge. The first implementation should exercise a pinned Clang 18.1.3 fixture profile (also used by #1469's recorded fixture matrix) and record the exact executable/runtime digests; version text alone is not authentication. No claim is made that GCC's frontend has equivalent stable API coverage, that any production build has been requalified, or that Clang and GCC ASTs are interchangeable.

Pinned Clang 18.1.3 primary API sources: [`DeclTemplate.h`](https://github.com/llvm/llvm-project/blob/llvmorg-18.1.3/clang/include/clang/AST/DeclTemplate.h#L1774-L1812) documents the selected class partial and its deduced `getTemplateInstantiationArgs()`; lines [436–612](https://github.com/llvm/llvm-project/blob/llvmorg-18.1.3/clang/include/clang/AST/DeclTemplate.h#L436-L612) distinguish `FunctionTemplateSpecializationInfo::TemplateArguments` from `TemplateArgumentsAsWritten` and document the separate `MemberSpecializationInfo` relationship/kind. [`Decl.h`](https://github.com/llvm/llvm-project/blob/llvmorg-18.1.3/clang/include/clang/AST/Decl.h#L2583-L2663) defines `FunctionDecl` member/template-specialization APIs and [`FunctionDecl::getNameInfo()`](https://github.com/llvm/llvm-project/blob/llvmorg-18.1.3/clang/include/clang/AST/Decl.h#L1969-L1972). [`DeclarationName.h`](https://github.com/llvm/llvm-project/blob/llvmorg-18.1.3/clang/include/clang/AST/DeclarationName.h#L694-L801) defines `DeclarationNameInfo::getSourceRange()` and multi-token name locations; [`Lexer.h`](https://github.com/llvm/llvm-project/blob/llvmorg-18.1.3/clang/include/clang/Lex/Lexer.h#L366-L394) defines token-end and character-range conversion. The traversal pins [`TemplateDecl::getTemplatedDecl()`](https://github.com/llvm/llvm-project/blob/llvmorg-18.1.3/clang/include/clang/AST/DeclTemplate.h#L402-L404), the class partial ordered-list overload (lines [2163–2165](https://github.com/llvm/llvm-project/blob/llvmorg-18.1.3/clang/include/clang/AST/DeclTemplate.h#L2163-L2165)), class specialization range (lines [2201–2213](https://github.com/llvm/llvm-project/blob/llvmorg-18.1.3/clang/include/clang/AST/DeclTemplate.h#L2201-L2213)), and [function specialization ranges](https://github.com/llvm/llvm-project/blob/llvmorg-18.1.3/clang/include/clang/AST/DeclTemplate.h#L983-L995). The exact type normalization API is pinned to [`QualType::getCanonicalType()` and `getSplitUnqualifiedType()` in `Type.h`](https://github.com/llvm/llvm-project/blob/llvmorg-18.1.3/clang/include/clang/AST/Type.h#L944-L981), and macro descriptor fields to [`MacroInfo.h`](https://github.com/llvm/llvm-project/blob/llvmorg-18.1.3/clang/include/clang/Lex/MacroInfo.h#L163-L196). The exact frontend call path is pinned to [`ToolInvocation` in `Tooling.cpp`](https://github.com/llvm/llvm-project/blob/llvmorg-18.1.3/clang/lib/Tooling/Tooling.cpp#L329-L435): it builds the driver invocation from the supplied vector, then runs the supplied action; the same source shows [`ClangTool` installs three default adjusters and injects a resource directory](https://github.com/llvm/llvm-project/blob/llvmorg-18.1.3/clang/lib/Tooling/Tooling.cpp#L437-L479). Therefore the v1 adapter uses `ToolInvocation` directly and does not use `ClangTool` or call `ClangTool::run`. These APIs are the v1 profile contract, not claims that another Clang release or frontend is wire-compatible. Primary references: [DWARF5](https://dwarfstd.org/doc/DWARF5.pdf), [Clang LibTooling](https://clang.llvm.org/docs/LibTooling.html), [Clang JSON Compilation Database](https://clang.llvm.org/docs/JSONCompilationDatabase.html), [Clang `FunctionDecl`](https://clang.llvm.org/doxygen/classclang_1_1FunctionDecl.html), [Clang `ClassTemplateSpecializationDecl`](https://clang.llvm.org/doxygen/classclang_1_1ClassTemplateSpecializationDecl.html), and [GCC template instantiation](https://gcc.gnu.org/onlinedocs/gcc/Template-Instantiation.html).

## Trust inputs and authentication contract

The producer and validator would accept only the following proposed input chain. Every digest below is SHA-256 over the exact canonical bytes or file bytes named; no caller-provided digest is accepted without rereading and validating its input.

1. **Source identity.** Reuse the authenticated scope, source lock, artifact manifest, source archive, source inventory, generated-file inventory/provenance, and the source-root path normalizer. Bind the Git source revision/tree identity, archive bytes, every translation-unit source blob, every generated source/header, and every opened include. Reject dirty, replaced, symlink-escaping, missing, or digest-mismatched inputs. A file outside the authenticated source/generated/toolchain closure makes that translation unit unsupported; it is not silently read from the host.
2. **Build action.** Reuse the authenticated build-record and compiler-action/compilation-database inputs. Select one unique action by authenticated `unitId` and exact argv digest. Require the authenticated compilation database to express cwd and every path-bearing argument in closure-relative virtual paths before authentication; resolve those virtual paths to contained files. Canonicalize the argv as an ordered string array, cwd, main file, target triple, language mode, ordered `-D`/`-U` definitions, include search order, response-file bytes, sysroot, resource directory, and PCH/module inputs. Require the compilation-database `arguments` string array; reject shell `command` entries in v1. The original top-level `arguments` vector must already contain exactly one standalone `--no-default-config` token; reject the action if it is absent or occurs more than once, and reject another occurrence introduced by response expansion. Never insert, remove, reorder, or otherwise rewrite a semantic argument except for the one explicitly specified response-file expansion transform below. This v1 requirement excludes ambient Clang default config files without adding them to the authenticated input set. Before response expansion, reject the original top-level `argv` if it contains `--driver-mode=cl`/`-driver-mode=cl` or any `--rsp-quoting=*`/`-rsp-quoting=*` token; this fixes the parser mode before it reads a response file. Then authenticate every response-file byte and recursively expand `argv` with the pinned Clang 18.1.3 `clang::driver::expandResponseFiles()` routine against the authenticated VFS, with `ClangCLMode=false` and its default GNU tokenizer. This produces `executionArgv`. After expansion, scan both vectors and reject any top-level or nested `--driver-mode=cl`/`-driver-mode=cl` or response-quoting override. V1 fixes the ordinary Clang/Linux response parser and does not admit CL mode or a quoting override. The original compilation-database vector remains `argv`; `executionArgv` is exactly that vector with only recursive response-file references replaced in place by the tokens Clang 18.1.3's routine returns. Run all closed-policy checks on both vectors and pass `executionArgv`, byte-for-byte, to `ToolInvocation`. No other argument transform is permitted. This is the permitted equivalent of the normal `clang_main` response-expansion step: the ordinary driver expands before `Driver::BuildCompilation`, while `ToolInvocation::run()` forms its `Argv` and calls `BuildCompilation` without that expansion ([`driver.cpp`](https://github.com/llvm/llvm-project/blob/llvmorg-18.1.3/clang/tools/driver/driver.cpp#L351-L374), [`Tooling.cpp`](https://github.com/llvm/llvm-project/blob/llvmorg-18.1.3/clang/lib/Tooling/Tooling.cpp#L347-L398), [`Driver.cpp` expansion routine](https://github.com/llvm/llvm-project/blob/llvmorg-18.1.3/clang/lib/Driver/Driver.cpp#L6114-L6150)). The VFS used for expansion exposes only authenticated response files and build inputs; any missing, changed, outside-closure, cyclic, or over-limit response fails before launch. Reject explicit configuration in either the original vector or expanded tokens: `--config=FILE`, `--config FILE`, `--config-system-dir=DIR`, and `--config-user-dir=DIR` (also reject the two exact bare directory-option spellings defensively). Do not parse or admit a config file: it can inject unauthenticated flags and inputs. The pinned [`Options.td`](https://github.com/llvm/llvm-project/blob/llvmorg-18.1.3/clang/include/clang/Driver/Options.td#L1023-L1037) defines `--config=` plus its separate alias, `--no-default-config`, and the joined system/user directory options; the latter disables default loading only and does not disable explicit configs. Clang's [configuration-file documentation](https://clang.llvm.org/docs/UsersManual.html#configuration-files) states that config files group command-line options, may be loaded explicitly with `--config=`, and may include further `@file` inputs.

   V1 also rejects dynamic extension, command-forwarding, driver-mode, response-quoting override, and output-producing auxiliary options in both `argv` and `executionArgv`. The closed rejection set is `-fplugin=`, `-fplugin-arg-*`, `-fpass-plugin=`, `-load`, `-plugin`, `-plugin-arg-*`, `-add-plugin`, both `-mllvm ARG` and `-mllvm=ARG`, both `-Xclang ARG` and `-Xclang=ARG`, `-cc1`, `-cc1as`, all `-Xarch_*` forms, `-Xassembler`, `-Xlinker`, `-Xoffload-linker`, `-Xopenmp-target`/`-Xopenmp-target=`, `-Xcuda-fatbinary`, and `-Xcuda-ptxas`. The pinned [`Options.td` entries](https://github.com/llvm/llvm-project/blob/llvmorg-18.1.3/clang/include/clang/Driver/Options.td#L889-L918) document driver-to-CC1, assembler, linker, and offload forwarding; `-mllvm` aliases are defined [here](https://github.com/llvm/llvm-project/blob/llvmorg-18.1.3/clang/include/clang/Driver/Options.td#L4301-L4307), direct `-cc1`/`-cc1as` flags [here](https://github.com/llvm/llvm-project/blob/llvmorg-18.1.3/clang/include/clang/Driver/Options.td#L6891-L6897), and the plugin and pass-plugin entries are [here](https://github.com/llvm/llvm-project/blob/llvmorg-18.1.3/clang/include/clang/Driver/Options.td#L3402-L3412) and [here](https://github.com/llvm/llvm-project/blob/llvmorg-18.1.3/clang/include/clang/Driver/Options.td#L6954-L6959), and CC1's plugin loader is [here](https://github.com/llvm/llvm-project/blob/llvmorg-18.1.3/clang/include/clang/Driver/Options.td#L7534-L7540). Reject both the option token and any required operand if the option is separate. These exclusions make the accepted action an in-process fixed `FrontendAction` with no user plugin, LLVM pass loader, direct CC1 override, or offload/child-tool route. The runner clears every ambient host variable outside the allowlist from the child environment, including dynamic-loader injection variables; the authenticated declared action environment is separately rejected if it contains a non-allowlisted name or unreadable value; v1 admits no other argument-controlled mechanism that can load executable extensions. The runner snapshots executable/shared-object mappings immediately before the action and after completion; any changed mapping set, unrecognized/deleted/out-of-profile mapping, or failed enumeration rejects the action. The pre/post mapping snapshots are defense in depth for the stable loaded closure only; they cannot detect a plugin loaded and unloaded during the action and never substitute for closed argument checks.

   V1 also rejects the pinned driver forwarding routes `-Xpreprocessor` and `-Wp,` in both the original argument vector and the authenticated response-expanded tokens. Reject every `-Xpreprocessor` option and its required operand; the pinned option is separate, and `-Xpreprocessor=<arg>` is rejected defensively. Reject every token beginning `-Wp,` as a whole, regardless of its comma-separated contents. This closes forwarding forms that can carry `-load` or another CC1 loader option. Clang 18.1.3 defines `Xpreprocessor` as `Separate` and `Wp_COMMA` as `CommaJoined` in [`Options.td`](https://github.com/llvm/llvm-project/blob/llvmorg-18.1.3/clang/include/clang/Driver/Options.td#L862-L864) and [`Options.td`](https://github.com/llvm/llvm-project/blob/llvmorg-18.1.3/clang/include/clang/Driver/Options.td#L917-L918); the driver forwards both with `Args.AddAllArgValues` in [`Clang.cpp`](https://github.com/llvm/llvm-project/blob/llvmorg-18.1.3/clang/lib/Driver/ToolChains/Clang.cpp#L1155-L1160). These tokens are rejected before `ToolInvocation`; pre/post mappings do not detect a transient load and are not a substitute.

   V1 rejects forced-include and macro-include options before frontend launch: `-include`, `--include`, `-imacros`, and `--imacros` in their separate and joined forms, plus documented `--include=FILE` and any equals form defensively. The separate option operand is rejected with its option. `-include-pch` remains covered by the PCH ban. Apply this closed check to original and response-expanded vectors. The pinned [`Options.td`](https://github.com/llvm/llvm-project/blob/llvmorg-18.1.3/clang/include/clang/Driver/Options.td#L4094-L4105) declares the include and imacros forms and [the `--include=` alias](https://github.com/llvm/llvm-project/blob/llvmorg-18.1.3/clang/include/clang/Driver/Options.td#L5428). Clang 18.1.3's [`InitPreprocessor.cpp`](https://github.com/llvm/llvm-project/blob/llvmorg-18.1.3/clang/lib/Frontend/InitPreprocessor.cpp#L61-L71) appends these implicit include directives to the predefines buffer. No forced-include or macro-include dependency/event is admitted as valid v1 evidence.

   Require argv[0] to be `/__decomp/toolchain/<profile-relative>/bin/clang`, mapped to its authenticated bytes; path operands use relative paths under the authenticated virtual cwd or absolute paths under `/__decomp/{source,generated,build,toolchain}`. Reject host absolute paths in argv/cwd. Preserve `argv` byte-for-byte as UTF-8 strings in original order, and preserve `executionArgv` exactly as returned by the one permitted recursive response expansion. The adapter calls Clang 18.1.3 `clang::tooling::ToolInvocation` directly with `executionArgv`, the authenticated cwd/VFS, and the evidence `FrontendAction`; it does not call `ClangTool`, apply argument adjusters, insert a resource-directory flag, or launch a second compiler. The Clang driver translates that expanded vector to frontend options; the custom action parses the AST and never creates code-generation output. Reject preprocessor/dependency-only actions (`-E`, `-M`, `-MM`), save-temps/output-producing dependency flags (`-save-temps*`, `-MD`, `-MMD`, `-MF`, `-MT`, `-MQ`, `-dependency-file`), and all output-producing auxiliary-file options before launch in original or expanded arguments: `-serialize-diagnostics FILE`/`--serialize-diagnostics FILE` (also reject equals forms defensively), `-diagnostic-log-file FILE`, `-serialize-diagnostic-file FILE`, `-ftime-trace`/`-ftime-trace=PATH`, `-fsave-optimization-record`/`-fsave-optimization-record=FORMAT`, `-foptimization-record-file=PATH`, `-opt-record-file FILE`, and `-fproc-stat-report=PATH`. Also reject reproducer writers (`-gen-reproducer`/`-gen-reproducer=*`, `-fcrash-diagnostics`/`-fcrash-diagnostics=*`, and `-fcrash-diagnostics-dir=*`) and compilation-database writers: `-MJ PATH`, every joined `-MJ<PATH>` token (including defensive `-MJ=<PATH>`), and `-gen-cdb-fragment-path DIR`. Reject each separate option together with its required operand. Clang 18.1.3 pins `-MJ` as `JoinedOrSeparate` and `-gen-cdb-fragment-path` as `Separate` ([`Options.td`](https://github.com/llvm/llvm-project/blob/llvmorg-18.1.3/clang/include/clang/Driver/Options.td#L665-L666) and [the `-MJ` declaration](https://github.com/llvm/llvm-project/blob/llvmorg-18.1.3/clang/include/clang/Driver/Options.td#L844-L845)); its driver writes these outputs in [`Clang.cpp`](https://github.com/llvm/llvm-project/blob/llvmorg-18.1.3/clang/lib/Driver/ToolChains/Clang.cpp#L4748-L4755). The pinned [`Options.td`](https://github.com/llvm/llvm-project/blob/llvmorg-18.1.3/clang/include/clang/Driver/Options.td#L5459-L5461) defines serialized diagnostics, [time-trace and file forms](https://github.com/llvm/llvm-project/blob/llvmorg-18.1.3/clang/include/clang/Driver/Options.td#L3634-L3652), [optimization-record files](https://github.com/llvm/llvm-project/blob/llvmorg-18.1.3/clang/include/clang/Driver/Options.td#L3575-L3589), [CC1 diagnostic writers](https://github.com/llvm/llvm-project/blob/llvmorg-18.1.3/clang/include/clang/Driver/Options.td#L6846-L6852), and [reproducer controls](https://github.com/llvm/llvm-project/blob/llvmorg-18.1.3/clang/include/clang/Driver/Options.td#L596-L602) and [crash-diagnostic outputs](https://github.com/llvm/llvm-project/blob/llvmorg-18.1.3/clang/include/clang/Driver/Options.td#L1807-L1820). The authenticated environment allowlist excludes Clang's output-controlling `CC_PRINT_OPTIONS`, `CC_PRINT_HEADERS`, `CC_LOG_DIAGNOSTICS`, `CC_PRINT_PROC_STAT`, and `CC_PRINT_INTERNAL_STAT` variables and the corresponding `CC_PRINT_OPTIONS_FILE`, `CC_PRINT_HEADERS_FILE`, `CC_LOG_DIAGNOSTICS_FILE`, `CC_PRINT_PROC_STAT_FILE`, and `CC_PRINT_INTERNAL_STAT_FILE` path variables. Exact `-c` and `-o` entries may remain because this action does not open an object output; acceptance fixtures must verify absence of every side effect. Reject unauthenticated response files. Bind the exact environment allowlist below; clear every other variable. Do not treat the repo's current Clang capture-input or Ninja prestart object as execution evidence: those objects are explicitly unexecuted.
3. **Frontend identity.** Bind a registered `clang-libtooling-cxx-v1` profile to compiler executable SHA-256, Clang/LLVM runtime and loaded-library closure digests, resource-header manifest digest, adapter source revision, adapter executable digest, adapter ABI/API version, target triple, and the existing toolchain reproduction/profile digest. Resolve the compiler by its authenticated absolute virtual path; `PATH` cannot select or replace it. `--version` output is diagnostic only. Reject an unregistered profile, a substituted executable/library, an implicit host `PATH` lookup, or a compiler different from the compiler authenticated for the build action. For v1, GCC, MSVC, clang-cl, and a Clang frontend substituted for a GCC-built artifact have capability `unsupported`, not a guessed fallback.
4. **Preprocessor/build context.** `argv` is the exact original normalized compilation-database `arguments` vector; `executionArgv` is its exact authenticated recursive response expansion under the pinned Clang 18.1.3 GNU parser. This response expansion is the sole permitted argument transform and the exact `executionArgv` vector is passed to `ToolInvocation`. No `ClangTool` adjuster or implicit resource-dir argument is allowed. The execution receipt records the exact input vector, cwd, environment, driver-resolved resource directory, actual ordered include/dependency closure with per-file hashes, generated inputs, and a deterministic preprocessor-context digest over active macros, include resolution, language/target options, and authenticated PCH/module inputs. The full argv/environment/action digest binds every option, including optimization and debug flags. V1 rejects PCH/modules; accepting them requires a later policy/schema version that authenticates their full artifacts and import closure. The full action and runner context are provenance, not part of the semantic anchor preimage; the anchor includes source revision/blob and complete typed declaration/argument facts. Therefore `-O0` and `-O2` may yield the same candidate when that tuple matches, while their action and physical IDs differ. A macro/configuration change changes the authenticated semantic-context digest and action/physical IDs; candidate equality still never merges or links rows.
5. **Executed frontend receipt.** The bounded isolated runner records deterministic action success, authenticated compiler/profile/action digests, dependency digests observed by the frontend, preprocessor-context digest, zero compiler-artifact output bytes, exit status, and action ID in the canonical receipt. CPU, wall, memory, stdout, and stderr telemetry stays in a non-evidence runner log. Once canonical evidence output is complete, an enclosing authenticated output inventory binds its SHA-256 and byte count. A planned command, compile database row, stderr/stdout text, compiler version string, or producer-authored JSON is not an execution receipt. On any failed command, changed input, missing include, resource termination, or receipt mismatch, publish no partial facts.

The current Kotlin trust chain is a viable base: `FullTreeScopeControl` snapshots and validates the exact scope/source-lock/manifest/build-record bindings; `FullTreeSourceInventoryControl` checks the locked source archive and per-file inventory; `FullTreeFunctionObservationProducer.authenticateShardInputs` binds inventory and rich-artifact bytes; and the #1469 producer enforces authenticated per-shard and no-partial-output budgets. The gap is explicit: current `FullTreeClangCaptureInputControl` and Ninja prestart represent validated but unexecuted inputs. The first implementation issue must add a frontend execution receipt instead of upgrading either plan object by implication.

## Schema and identities

### Proposed wire and digest contracts

The proposal defines four independently registered contracts that would freeze wire, policy, and compatibility versions. All objects use `additionalProperties: false`; every listed member is required, and nullable members are present as JSON `null`. Empty arrays/objects, null, zero, and omitted members are distinct. Hashes are lowercase 64-character SHA-256 hex. JSON integers are non-negative and at most signed 64-bit; arbitrary-width C++ integral values are canonical base-10 strings. Strings use strict UTF-8 with no Unicode normalization. Arrays preserve declared order unless this section specifies canonical sorting. `schemaVersion` is independent of the `vN` registry name; truth-v4's registry schema name is `full-tree-function-truth-v4` while its wire `schemaVersion` is 3, advancing the #1468 wire version 2.

| Contract | Registry/schema name | Wire version | Policy id/version | Configuration digest input |
| --- | --- | ---: | --- | --- |
| Frontend receipt/provenance | `full-tree-generic-template-frontend-v1` | `schemaVersion: 1` | `full-tree-generic-template-frontend` / 1 | `OracleSchemas.configurationSha256([name], canonicalPolicy)`; canonical policy JSON followed by exact bundled schema bytes. |
| Generic evidence | `full-tree-generic-template-evidence-v1` | `schemaVersion: 1` | `full-tree-generic-template-evidence` / 1 | Same rule, evidence schema and evidence policy only. |
| Function observation | `full-tree-function-observations-v3` | `schemaVersion: 3` | `full-tree-function-observations` / 5 | Same rule, new v3 schema/policy only; v1/v2 schema and policy bytes stay frozen. |
| Function truth shard/index | `full-tree-function-truth-v4`, `full-tree-function-truth-index-v4` | `schemaVersion: 3` in each | `full-tree-function-truth` / 4 | `OracleSchemas.configurationSha256(["full-tree-function-exclusions", "full-tree-function-truth-v4", "full-tree-function-truth-index-v4"], canonicalPolicy)`, in exactly that order. |

For frontend/evidence policies, the canonical policy JSON has exactly `id`, `version`, `argvPolicy`, `environmentAllowlist`, `supportedEntityKinds`, `supportedDeclarationKinds`, `supportedEdgeKinds`, `supportedStatusKinds`, `supportedSpecializationKinds`, `supportedQualifierKinds`, `supportedTypeKinds`, `supportedArgumentKinds`, `unsupportedKinds`, `reasonCodes`, and `limits`. `argvPolicy` is the exact closed string `clang-toolinvocation-authenticated-response-expansion-v1`: preserve the authenticated compilation-database vector as `argv`, derive `executionArgv` only through pinned authenticated response-file expansion, and pass `executionArgv` unchanged to `ToolInvocation`; no other argument adjuster or resource-dir insertion is permitted. Each array is sorted unique and exactly the closed enums/allowlist written below; `reasonCodes` is exactly the closed evidence reason enum below. `maxFormalActualDescriptorNodesPerEntity: 1024` is one aggregate ceiling per emitted physical entity, applied after normalized defaults are merged and exact duplicate edges are collapsed. Count every serialized `Formal` occurrence (including nested formals), every serialized `TemplateArgument` occurrence (including each pack container and each pack element), and every serialized `TypeDescriptor` node occurrence across the entity’s formals/defaults, typed actual vectors and edge payloads, signature result/parameters, and nested descriptor/template-argument trees. Count by serialized occurrence/path: equal values, repeated uses, or shared Clang pointers each count again wherever they occur; do not deduplicate them. A normalized default appears once, while distinct edge payloads each count. Exceeding the aggregate limit produces the defined fail-closed limit outcome. `limits` contains only fixed policy ceilings: `maxFormalActualDescriptorNodesPerEntity: 1024`, `maxEdgesPerEntity: 32`, `maxRelationWalkDepth: 32`, `maxMacroExpansionDepth: 256`, `maxTypeDepth: 64`, `maxEntityRowBytes: 67108864`, `maxGenericEvidenceBytes: 67108864`, `maxResourceHeaderFiles: 65536`, `maxResourceHeaderManifestBytes: 67108864`, `maxResourceHeaderTreeBytes: 1073741824`, `genericResidentShareDivisor: 4`, `genericResidentCanonicalByteMultiplier: 3`, and `genericResidentFixedBytes: 64`. Authenticated whole-run action count, per-shard entity/output/resident limits, worker count, and runner limits come only from validated controls and are not copied into this policy object. A location is exactly `{path, byteOffset, line, column, macroExpansionDepth}`. Construct spelling and expansion locations independently from the same raw declaration-name `SourceLocation`: the spelling object uses `SourceManager::getSpellingLoc(rawLoc)`, and the expansion object uses `SourceManager::getExpansionLoc(rawLoc)`. For each object, derive `path` from that projected location’s own authenticated `FileID`, `byteOffset` from that same projected file location, and physical `line`/`column` from that same `FileID` plus byte offset using `SourceManager` file line/column getters. Never derive expansion coordinates through the spelling file or borrow one object’s path/offset for the other. Presumed `#line` coordinates never replace physical coordinates. For both spelling and expansion location objects, `macroExpansionDepth` is computed from the same original direct declaration-name `SourceLocation` before either location is projected: use the first token location of the exact raw name span (the direct child token for a template wrapper), set `cursor` to that raw location and `depth` to zero, and keep a local set of visited source-location values. While `cursor.isMacroID()`, require the depth to remain below 256, obtain `next = SourceManager::getImmediateMacroCallerLoc(cursor)`, require `next` to be valid and not already visited, add it to the set, increment depth once, and continue with `next`. Stop only at a valid file location; a file-written name therefore has depth zero and each Clang immediate-macro-caller transition counts one, including macro-argument and macro-body frames. A broken chain aborts, and a 257th frame fails with `limit-exceeded`. `getImmediateMacroCallerLoc` is the pinned Clang API that follows one level toward the initial macro invocation; spelling/expansion projection does not change the recorded count ([`SourceManager.h`](https://github.com/llvm/llvm-project/blob/llvmorg-18.1.3/clang/include/clang/Basic/SourceManager.h#L1627-L1639)). `nameRaw` is the exact UTF-8 byte slice of the authenticated original source span: for a simple identifier, start at the direct declaration name token location and end at `Lexer::getLocForEndOfToken`; for overloaded operators, conversion/literal operators, constructors/destructors, and any other multi-token declaration name, use the direct `DeclarationNameInfo::getSourceRange()` (including the operator keyword and full conversion type as applicable), then take the byte interval from its first token through `Lexer::getLocForEndOfToken` at its last token. For a `TemplateDecl` wrapper, obtain the name span only from its direct `getTemplatedDecl()` pointer and verify that declaration's source location; do not perform a name lookup. Convert spelling endpoints to one authenticated file and original-file byte offsets. The half-open span includes all original whitespace/comments between its first and last name tokens, excludes surrounding trivia, and is never reconstructed from a pretty-printer, demangler, `DeclarationName::getAsString()`, or normalized identifier. Decode the slice as strict UTF-8 without normalization. If the range is invalid, non-contiguous, macro scratch/unmapped, crosses files, contains invalid UTF-8, or cannot be read from an authenticated source file, encode `nameRaw:null`, add `missing-source-anchor`, and withhold the candidate. Tests pin identifiers, `operator+`, `operator new`, conversion operators with multi-token types, literal operators, and macro-generated names. The pinned APIs are Clang 18.1.3 `DeclarationNameInfo::getSourceRange()` and `Lexer::getLocForEndOfToken`; the lexer returns an invalid end when it cannot form a file location.

V1 accepts an `explicit-specializes` class edge only when Clang's direct target is the primary `ClassTemplateDecl`; a partial target or otherwise unrepresentable selection remains unknown/unsupported until a separately versioned vector shape is reviewed. `redeclares`, `templated-declaration`, and `member-specialization` never supply candidate argument vectors; a member-specialization edge remains independent metadata. Apply binding-edge cardinality checks only to `partial-specialization`, `concrete-instantiation`, and `explicit-specialization` rows, for which the mapping above defines an authoritative edge kind. If such a row lacks that required edge, has an ineligible edge kind, targets the wrong declaration class, or has more than one non-identical eligible edge, mark it `unknown` with `argument-vector-incomplete` or `ambiguous-template-selection` as appropriate and withhold its candidate; never select the first edge. `primary-template` and `supporting-declaration` rows intentionally require no candidate-binding edge or argument vector, so absence of one does not by itself change their status or candidate eligibility. `declares-specialization-of` remains typed non-binding evidence and cannot satisfy this requirement. Exact duplicate relation observations normalize to one edge. Within a canonical redeclaration group, normalize the direct binding relation payloads against canonical target anchors: repeated identical payloads count once, while missing or conflicting payloads withhold the group's candidate. Retain every distinct typed edge as evidence. For relationship bounds, normalize every observation to the complete edge tuple `{unitId,sourcePhysicalId,targetPhysicalId,kind,proofKind,specializationKind,argumentVectors}`. Exact duplicates collapse to one row before `maxEdgesPerEntity`, `edgeCount`, or byte admission. Two rows with the same endpoints/kind but any different proof, specialization kind, or argument-vector payload are distinct rows and each counts. The ceiling is at most 32 unique outgoing rows per physical source entity; an edge is charged only to its source, never to its target or both endpoints. Relation-walk depth separately counts direct API links on one walk (32 admitted, the 33rd or a cycle fails). Every retained unique edge contributes its complete canonical JSON bytes once to the evidence artifact and its exact marginal bytes to the generic byte ledger; copies repeated in observation/truth shards, indexes, or other artifacts are charged again in each serialized file. Exact duplicate observations add no graph/count/byte contribution after normalization; they do not erase distinct typed relations.

For `ClassTemplateSpecializationDecl`, `getTemplateArgs()` is the exact class argument vector. A `TSK_ExplicitSpecialization` row emits `explicit-specializes` to the exact `getSpecializedTemplate()` pointer. A row with `TSK_ImplicitInstantiation`, `TSK_ExplicitInstantiationDeclaration`, or `TSK_ExplicitInstantiationDefinition` emits `instantiates-primary` or `instantiates-partial` only if `getInstantiatedFrom()` is non-empty and pointer-equal to the exact `getSpecializedTemplateOrPartial()` result; its `proofKind` is `ClassTemplateSpecializationDecl.getInstantiatedFrom`. If that instantiation proof is absent or inconsistent, keep the row as `supporting-declaration`, `unknown`, with `missing-template-relation`, preserve the observed specialization kind, and emit no instantiates edge or candidate. For `TSK_Undeclared`, `getInstantiatedFrom()` is empty by contract even when `getSpecializedTemplateOrPartial()` returns a target. Preserve that direct declaration relation as `declares-specialization-of`, with `specializationKind: undeclared`, the exact selected primary/partial target, and `primaryActuals = getTemplateArgs()`; keep its entity kind `supporting-declaration` and its local status per the precedence rule above; include `specialization-not-instantiated`, any independent unsupported reason, and a null candidate. Example: `template<class T> struct Box; template<class T> struct Box<T*> {}; Box<int*> value;` yields `primaryActuals = [type(pointer(int))]`, selected target `Box<T*>`, and, only for an actual instantiation, `partialDeducedArguments = [type(int)]`. Encoding both as `[type(int*)]`, swapping them, or deriving either from rendered names fails rederivation. For a primary-only instantiation Clang specifies that `getTemplateInstantiationArgs()` equals `getTemplateArgs()`; v1 records it only as `primaryActuals` and keeps the partial vector null.

Missing/inconsistent function relation data yields `supporting-declaration`, `unknown`, `missing-template-relation`, no edge, and no candidate. Clang 18.1.3's `FunctionTemplateSpecializationInfo` setter rejects `TSK_Undeclared`; dependent function-specialization records without a direct selected primary remain bounded supporting evidence and do not use the class-only `declares-specialization-of` edge. `TemplateArgumentsAsWritten` supplies `functionArgumentsAsWritten` when present, otherwise it is null. Function templates are not partially specialized in C++; overload selection is the exact `FunctionTemplateDecl*` returned by Clang. For member-function specializations, serialize the function-template edge and the independent `MemberSpecializationInfo` edge separately. The member edge has null argument vectors and its own `TemplateSpecializationKind`; never copy the function template's specialization kind onto it. Clang's documented `A<int>::f<int>` example is both a function-template specialization and a member specialization, and the two specialization kinds can differ. Class partial selection, its primary ancestor edge, function-template specialization, and member-specialization edge remain distinct. Edges with no binding, including `redeclares` and `templated-declaration`, encode the required all-null `argumentVectors` object; they never infer a binding from parameter spelling.

The evidence `counts` object has exactly `unitCount`, `entityCount`, `edgeCount`, `reasonCodeCount`, `entityKindCounts`, `edgeKindCounts`, `statusCounts`, and `reasonCounts`. Each `*Counts` object has exactly every enum key from its corresponding closed wire enum and a non-negative integer value, including explicit zeroes. Scalar totals equal array lengths; entity-kind and status maps sum to `entityCount`, edge-kind map sums to `edgeCount`, and reason map sums to total reason-code occurrences `reasonCodeCount`.

For v1, support only C++14 class/struct and function templates, primary declarations, class partial specializations, explicit specializations, explicit instantiations, observed implicit instantiations, overload sets, and packs. Formal kinds are type, integral/enum non-type, and template-template; supported actual kinds are type, integral/enum value, template name, and nested pack. A dependent type may appear in a partial-specialization pattern when encoded by supported `templateParameter` descriptors (for example `Box<T*>`); dependent/unresolved instantiated actuals, dependent non-type expressions, unexpanded pack expansions, and unresolved template names are tagged unsupported and cannot yield candidate/resolved identity. Class-valued/floating/pointer NTTPs, modules, unauthenticated PCH, and other Clang argument kinds are retained only as bounded tagged unsupported evidence. Variable templates and all their specialization forms are outside the v1 census; `variable-template` is reserved vocabulary and does not promise any row. The `concepts-requires` unsupported-kind and `unsupported-concept` reason remain reserved vocabulary, with no positive ConceptDecl row path in v1. A C++20 or concepts-enabled action is out of profile and rejects before AST extraction; an unexpected `ConceptDecl` also fails closed before row emission. Expansion requires a new policy/schema version and fixtures.

No other `NamedDecl` is a seed merely because it is named, appears in `DeclContext::decls()`, or shares a spelling. C++20 and any concepts-enabled frontend setting reject before AST extraction; `ConceptDecl` is not seeded or serialized, and its reserved unsupported vocabulary does not create a positive evidence path. Run closure to a fixed point. Relation-walk roots are exactly the seed set above plus each `NamedDecl*` admitted through required typed-reference or parent-chain closure; each root starts at distance zero. A declaration reached only through an eligible relation edge inherits its breadth-first distance and is not reset as a new root. The eligible relation graph contains only direct source-to-target edges from the configured v1 relation APIs, normalized to the nine supported edge kinds; parent-chain steps and typed-reference admissions are not relation links. Use exact `NamedDecl*` identity within one `ASTContext`. Reject any directed cycle in the completed eligible graph by three-color depth-first cycle detection. Then breadth-first search from each root over outgoing edges, visiting a target once at its shortest distance; 32 links are admitted and a target first reachable at distance 33 fails the action. Sort roots by stable AST ordinal and outgoing neighbors by `(edgeKind,targetOrdinal)` so order cannot affect closure. Add only direct relation targets and required typed references; process newly admitted rows by the same rules. Then close every relevant declaration over both complete direct parent chains by repeatedly following `getLexicalDeclContext()` and `getDeclContext()` to the translation-unit root, retaining each intervening named context as a supporting row and applying the same direct-reference closure to it. Do not substitute one parent chain for the other; each row stores its two direct parent IDs separately. The TU root itself is represented as null. A non-named required relation target, parent context, or typed declaration reference, an unavailable direct pointer, or any required parent/target not reached by the ordered walk is a graph-closure failure and aborts the action. Optional unrelated declarations are traversed only as needed to establish this predicate and do not emit rows. Output rows sort by `(unitId, ordinal)` and edges by the wire order described above. Reversing action or worker visitation cannot change per-action ordinals or canonical output.

Location choice is fixed: semantic anchor uses spelling file plus required source line from `getSpellingLoc`; retain exact byte offset, column, and `getExpansionLoc` as separate physical/provenance fields, and record macro expansion depth. Never fall back from invalid spelling location to expansion location. Require all spelling, expansion, and macro-chain files in the authenticated closure. This allows raw rederivation to distinguish two expansions of the same macro definition: they may share a candidate but distinct canonical pointers in one AST context place them in separate groups and collision reconciliation marks them ambiguous. A macro-generated candidate is therefore allowed only when the complete spelling/expansion chain and declaration are authenticated.

Existing DWARF `sourceEntityId` remains an artifact/unit/section/CU/DIE-bound physical key; its candidate remains #1469's source candidate. Frontend physical IDs and DWARF physical IDs are never equated. The frontend record is not joined to a DIE by name, demangling, offset, physical order, candidate, location approximation, or `DW_AT_abstract_origin`. Since portable DWARF5 has no generic-pattern reference, `dwarfSourceEntityId` remains null absent a separately reviewed direct backend proof. Generic pattern evidence never creates or links an emitted-RVA denominator row in v1.

## Bounds, failure behavior, and deterministic interface

The action interface consumes only validated typed registries and an authenticated immutable artifact root; it returns one immutable complete v1 result or a typed failure. It has no arbitrary path/output callback, no partial iterator that sinks can publish, and no ambient compiler selection. Production and raw-rederivation modes call the same strict input verifier but independently invoke the frontend over raw authenticated inputs. Candidate evidence is discarded before rederivation.

Use the smaller of caller limits and authenticated scope limits; do not raise any existing global, per-shard, DIE, function, parameter, serialization, or working-set bound. Propose these additional ceilings for policy v1:

| Item | Hard ceiling | Admission and failure |
| --- | ---: | --- |
| Actions | Authenticated `perShard.compilationUnits` and cumulative `wholeRun.compilationUnits`, plus existing worker ceiling | Count selected actions before launch; reject if any per-shard or cumulative run count exceeds its corresponding scope limit or if the worker ceiling is exceeded. |
| Entity/claim rows | Authenticated `perShard.entities` and cumulative `wholeRun.entities` | Count each physical #1467 source-entity row, each newly retained generic frontend entity, and each distinct ordinary emitted-definition anchor claim once in the run reconciliation model. Deduplicate repeated claims for the same #1467 physical DIE locator; never equate a frontend physical locator with a DIE locator. Do not recount a fact when repeated in evidence/observation/truth projections. Charge before retention; one over aborts the complete shard/run publication. |
| Macro expansion depth | 256 | Count immediate caller transitions from the raw declaration-name location as specified below; a depth of 256 is admitted, 257 or an invalid/cyclic chain aborts with `limit-exceeded`. |
| Formals or actual arguments per entity | 1,024 | Count nested pack leaves and nodes before retention; one over aborts. |
| Relationship edges per entity and relation walk | 32 each | `maxEdgesPerEntity` counts unique outgoing edge rows by `sourcePhysicalId` after exact full-row duplicate normalization; incoming rows do not count against the target. `maxRelationWalkDepth` uses the per-root directed graph and breadth-first shortest-distance algorithm defined in amendment 1: each normalized v1 direct relation edge is one link from its source to its exact target; relation roots start at zero, and parent-chain and typed-reference steps are outside this edge graph. Count repeated evidence/observation-v3/truth-v4 entity rows, fixed envelopes, repeated bindings/unit rows, changed count maps, delimiters, and full-run index fields in every artifact where they appear.

If source locations, argument shapes, or types are syntactically readable but incomplete or conflicting, preserve bounded raw evidence and use `unknown`, `ambiguous`, or `unsupported`, with deterministic reason codes. ## Field-level review amendments (proposal; pending independent acceptance)

This is a review draft, not a frozen contract. The five subsections below are separate review targets for frontend provenance, AST closure/identity, typed argument encoding, downstream projection, and exhaustive Clang entity/relation mapping. They replace any conflicting shorthand earlier in this proposal. Do not create implementation issues or label the design accepted until an independent reviewer checks the exact final text.

### 1. AST closure and redeclaration-group normalization

`DeclContext::decls()` is the lexical child source, but is not the whole declaration graph. For one `ASTContext`, walk from `TranslationUnitDecl` with this ordered, depth-first algorithm:

1. Visit each `DeclContext::decls()` child in the range's stored lexical order. Enter the child, finish its owned children, then advance to the next sibling.
2. On every `TemplateDecl`, visit the direct `getTemplatedDecl()` result first when non-null. Recurse into that declaration's `DeclContext` children before continuing.
3. For a `ClassTemplateDecl` canonical owner, materialize the ordered-list overload `getPartialSpecializations(SmallVectorImpl<ClassTemplatePartialSpecializationDecl*>&)` and visit that returned list, then visit `specializations()` from `spec_begin()` to `spec_end()` in the pinned Clang 18.1.3 API range order. For a `FunctionTemplateDecl` canonical owner, visit its `specializations()` range in API order. Load the owner range before traversal; v1 rejects PCH/modules and any item sourced from an external AST. These are compiler-owned edges, not entries assumed to occur in `DeclContext::decls()`.
4. For a redeclarable template owner, visit its declaration chain from canonical/oldest to most recent by materializing from `getMostRecentDecl()` through `getPreviousDecl()` and reversing that temporary vector. Enumerate each canonical owner's specialization collections once. A child reached by two owner paths is visited only at its first event.
5. On a non-template `DeclContext`, visit its `decls()` range in stored order. On a class specialization or function declaration reached through an owner collection, recurse into its declaration context where applicable.

Maintain `visitedDecls` and `activeDecls` as per-`ASTContext` pointer sets: an active revisit is a cycle and aborts the action; a completed revisit is deduplicated without another ordinal. Assign the next contiguous zero-based `eventOrdinal` to every unique `Decl*` on its first visit, including declarations outside the relevance set; only relevant declarations emit rows, so serialized row ordinals may have gaps. Pointer equality is never serialized. `getCanonicalDecl()` is used only in the separate grouping pass below, never to replace a physical visit. Direct relation targets and referenced named declarations enter the relevance set, but they are not appended from an unordered side table: if any required target is not reached by this ordered walk, abort the action with no evidence. The `ClassTemplateDecl::getPartialSpecializations()` returned order, class/function `specializations()` range order, redeclaration-chain order, and lexical `DeclContext` order are all explicit inputs to ordinals. Worker/action scheduling never participates.

After traversal, partition each unit's rows in the closed redeclaration-supported allowlist in amendment 5 by exact `Decl::getCanonicalDecl()` pointer equality within that `ASTContext`. Keep each distinct `Decl*` as a physical row and emit a `redeclares` edge for each direct `getPreviousDecl()` link supported by that allowlist. For each group, materialize declarations from canonical to most recent and normalize one shared semantic payload before calculating any candidate:

- Validate equal declaration kind, template parameter-list arity, nested template-template parameter shape, and each formal's `(depth,index,kind,isPack)` slot across all group members.
- For each formal slot, collect the effective present defaults from every redeclaration. Normalize a type default through the type algorithm below; normalize a non-type default only when Clang's constant evaluator returns a fully evaluated integral value; normalize a template-template default from its direct `TemplateArgumentLoc`. Packs use the same typed argument recursion. An inherited present default contributes its normalized value; a redeclaration with no effective default contributes no value. Deduplicate present values by canonical typed JSON bytes, then merge by exact set cardinality: zero distinct values produces JSON `null`; one distinct value produces that value; more than one distinct value is a conflict. A conflict makes the entire group `unknown`, adds `conflicting-redeclaration-default`, and withholds its candidate and resolved ID. A dependent or unrepresentable default, missing parameter slot, or incompatible signature also makes the entire group `unknown`, adds `argument-vector-incomplete`, and withholds its candidate and resolved ID. Never pick the first, last, or canonical declaration's unmerged default.
- Use the canonical declaration's authenticated source anchor and raw token spelling; use the merged formals/defaults and normalized signature/specialization/semantic-argument vectors on every physical row in the group. Per-declaration spelling/expansion locations remain physical provenance.

For example, `template<class T, class U> struct Pair; template<class T, class U = int> struct Pair;` is one Clang canonical group. Both declaration rows carry the normalized formal vector `[T(default=null), U(default=type(builtin(int)))]` and therefore the same candidate. If separate TUs expose different default sets under macros, the normalized payloads produce different candidate values for the same source-anchor bucket; the full-run pass below marks that bucket ambiguous. Conflicting values never resolve through candidate equality.

Compute it by following `SourceManager::getIncludeLoc()` from the callback filename's FileID to the main file; a broken chain rejects the action. `resolvedPath` is the normalized authenticated closure-relative resolved `File` path and `resolvedSha256` is its exact file-byte digest; an absent file, outside-closure path, or mismatch rejects the action. Thus callback requested text, original directive bytes, resolved path, nesting base, and event order are distinct and deterministic inputs, not interchangeable spellings.

`semanticContextSha256 = H("decomp-thing/generic-template/semantic-context/v1", {languageOptions,targetTriple,sourceDateEpoch,predefinedMacroDigest,macroEvents,includeEvents,pchModuleDigests})`. `predefinedMacroDigest = H("decomp-thing/generic-template/predefines/v1", sortedRows)` using the macro rows above. A present value must match `0|[1-9][0-9]*` and fit signed 64-bit. No host fallback or adapter-selected default is allowed. V1 accepts the ordinary predefined registration and `MacroDefined`/predefined rows for `__DATE__`, `__TIME__`, and `__TIMESTAMP__`; those stable builtin descriptors remain bound by `predefinedMacroDigest`. Reject an action only when `PPCallbacks::MacroExpands` reports one of those exact identifiers with a `MacroDefinition` whose `MacroInfo::isBuiltinMacro()` is true. Do not reject a builtin because it is registered or defined. Clang invokes `MacroExpands` for builtin macros immediately before `ExpandBuiltinMacro`, so this check observes actual use before time-dependent text is produced ([`PPCallbacks.h`](https://github.com/llvm/llvm-project/blob/llvmorg-18.1.3/clang/include/clang/Lex/PPCallbacks.h#L280-L284), [`PPMacroExpansion.cpp`](https://github.com/llvm/llvm-project/blob/llvmorg-18.1.3/clang/lib/Lex/PPMacroExpansion.cpp#L3006-L3018)). A replacement macro that merely contains one of those identifier tokens is allowed while unused; expanding it directly or indirectly, including when rescanning reaches the builtin after token pasting or in an active preprocessing condition, rejects the action. A `defined`/`#ifdef` check that does not expand the builtin is allowed. Tests accept ordinary Clang registration and an unused forwarding definition, and reject direct/indirect active expansion and token-pasted expansion. In addition, v1 rejects `-march=native`, `-mcpu=native`, `-mtune=native`, `-target-cpu=native`, and their separated spellings in the original argv or authenticated response-file-expanded driver input. The effective target triple, CPU, and feature set must equal the registered profile. No host CPU probe is accepted.

Reserve the mandatory envelopes before retaining AST rows. First construct the complete required generic-evidence envelope and its empty `genericTemplates` observation-v3/truth-v4 shard projections with validated bindings, all ordered unit receipts, empty entity/edge arrays, and zero-filled count maps; also reserve the empty full-run index projection when that output is required. Let `B0` be the exact aggregate incremental serialized-byte delta across those complete artifacts relative to the corresponding ordinary-only artifacts. This includes repeated unit/binding/count-map fields, each artifact's fixed envelope, field names, delimiters, and the index shell. Let `remainingShardBytes = perShard.serializedBytes - alreadySerializedShardBytes` and `remainingRunBytes = wholeRun.serializedBytes - alreadySerializedRunBytes`; compute `genericBudget = min(64 MiB, remainingShardBytes, remainingRunBytes)`. A non-positive budget or `B0 > genericBudget` aborts before AST entity retention. Retain no rows until this entire mandatory delta is reserved. For each admitted entity/edge/claim, compute its exact marginal canonical-byte delta in the standalone evidence, repeated observation-v3/truth-v4 rows and envelopes, and shard/index count/manifest fields; charge every output occurrence and any integer-width, separator, or aggregate-count change. Admit only if the cumulative delta remains within `genericBudget`, the standalone evidence file stays within 64 MiB, and both per-shard and whole-run `entities` limits remain valid. A one-over result aborts the whole shard/run; no truncated envelope or partial publication is allowed.

### 3. Type and template-argument canonicalization

The supported argument kinds remain `type`, `integral`, `template`, and nested `pack`. A `type` argument is context-sensitive: in `partialPatternArguments` it may contain a representable dependent `templateParameter` type; in instantiated `primaryActuals`, `partialDeducedArguments`, `functionActuals`, and written actuals, a dependent/unresolved type or value is `unsupported` with reason `unresolved-dependent-actual`. Thus `Box<T*>` is representable as a partial pattern, while an unresolved actual is not. `Box<int*>` is a concrete actual. A dependent non-type expression such as `N + 1`, an unexpanded pack expansion, or an unresolved template name remains unsupported; do not collapse all dependent pattern types into unsupported actuals.

Before selecting any `TypeDescriptor` variant, normalize a `QualType` in this exact order: (1) call `getCanonicalType()`; (2) call `getSplitUnqualifiedType()` on that canonical type; (3) emit qualifiers from the returned `Qualifiers` before dispatch, in the sorted subset of `const`, `volatile`, `restrict`; if any other qualifier bit is present, mark the descriptor unsupported; (4) select the variant using only the returned canonical unqualified `Type*`; and (5) recursively apply this same sequence to child `QualType`s. Typedef/`typeof` sugar is deliberately erased before variant selection. `RecordType` backed by a `ClassTemplateSpecializationDecl` maps to `templateSpecialization` using direct Clang declaration pointers and typed template arguments; an ordinary record/enum maps to its record/enum variant. No `getAsString()` or `getSingleStepDesugaredType()` output selects identity. An unsupported qualifier/type does not fall back to the source spelling.

Examples: `using Count = const int;` and `const int` both normalize to `{kind:"builtin",name:<Clang BuiltinType::Kind for int>,qualifiers:["const"]}`; `volatile int*` becomes a pointer with empty outer qualifiers and a volatile builtin pointee; `template<class T> struct Box<T*>` records a pointer whose pointee is `{kind:"templateParameter",qualifiers:[],depth:0,index:0}`; and `Box<int*>` records a specialization descriptor whose actual type argument is a pointer to `int`. Qualifier arrays on every descriptor variant are exactly the CVR subset above; `atomic`, address-space, Objective-C, GC, and unaligned qualifiers are unsupported in v1.

Candidate/reference remapping is also exact. In candidate preimages, replace every `declPhysicalId` by `referenceAnchor(target)`, where the target is obtained from the already-held direct AST pointer, reduced to its canonical redeclaration group's `canonicalAnchor`. Replace `templatePhysicalId` in a template argument by the referenced template's `canonicalAnchor`. Replace both `specializationPhysicalId` and `templatePhysicalId` in a `templateSpecialization` descriptor by the exact referenced specialization/template canonical anchors. No physical ID or pointer value occurs in candidate JSON, and no name lookup is permitted. If any target is outside the same authenticated action or has no canonical source anchor, withhold the candidate.

`languageMode` is one exact JSON object in candidate and semantic-context preimages: `{standard:"c++14",standardVersion:201402,extensions:[],modules:false,exceptions:<boolean>,rtti:<boolean>,charSignedness:"signed"|"unsigned",wcharWidth:<positive integer>}`. V1 rejects another standard, a non-empty extension set, or modules. `exceptions` and `rtti` are captured from the effective `LangOptions`, not defaulted by the adapter. `charSignedness` is derived from effective `LangOptions::CharIsSigned` after the driver applies target defaults and admitted signed/unsigned-char overrides; `wcharWidth` is the bit width of `ASTContext::getWCharType()` via `ASTContext::getTypeSize()`, after `CompilerInstance` applies `TargetInfo::adjust()` with the effective `LangOptions` (including `WCharSize`). This captures `-fno-signed-char`, `-fsigned-char`, `-funsigned-char`, `-fno-unsigned-char`, `-fshort-wchar`, and `-fno-short-wchar`; neither value is inferred from the target triple or argv alone. The pinned [`Options.td`](https://github.com/llvm/llvm-project/blob/llvmorg-18.1.3/clang/include/clang/Driver/Options.td#L3606-L3609) defines wchar overrides, [signed-char controls](https://github.com/llvm/llvm-project/blob/llvmorg-18.1.3/clang/include/clang/Driver/Options.td#L3635-L3639) and [unsigned-char controls](https://github.com/llvm/llvm-project/blob/llvmorg-18.1.3/clang/include/clang/Driver/Options.td#L3857-L3858); the driver resolves defaults and overrides in [`Clang.cpp`](https://github.com/llvm/llvm-project/blob/llvmorg-18.1.3/clang/lib/Driver/ToolChains/Clang.cpp#L1325-L1335) and [renders character/wchar options](https://github.com/llvm/llvm-project/blob/llvmorg-18.1.3/clang/lib/Driver/ToolChains/Clang.cpp#L3956-L3981). [`LangOptions.def`](https://github.com/llvm/llvm-project/blob/llvmorg-18.1.3/clang/include/clang/Basic/LangOptions.def#L229-L231) defines the effective state; [`CompilerInstance.cpp`](https://github.com/llvm/llvm-project/blob/llvmorg-18.1.3/clang/lib/Frontend/CompilerInstance.cpp#L150-L152) applies `TargetInfo::adjust()`, whose [pinned implementation](https://github.com/llvm/llvm-project/blob/llvmorg-18.1.3/clang/lib/Basic/TargetInfo.cpp#L391-L401) applies `WCharSize`. `ASTContext` constructs signedness-sensitive `char`/`wchar_t` types from that state ([`ASTContext.cpp`](https://github.com/llvm/llvm-project/blob/llvmorg-18.1.3/clang/lib/AST/ASTContext.cpp#L1205-L1208) and [wchar initialization](https://github.com/llvm/llvm-project/blob/llvmorg-18.1.3/clang/lib/AST/ASTContext.cpp#L1267-L1276)); [`ASTContext.h`](https://github.com/llvm/llvm-project/blob/llvmorg-18.1.3/clang/include/clang/AST/ASTContext.h#L1763-L1765) exposes the effective `wchar_t` type, and [the type-size API](https://github.com/llvm/llvm-project/blob/llvmorg-18.1.3/clang/include/clang/AST/ASTContext.h#L2298-L2308) returns its width in bits. This object replaces the prior undefined `languageMode` shorthand.

For any unsupported argument/type tagged `{kind:"unsupported",clangKind,rawSha256}`, `rawSha256` is nullable. When Clang supplies a contiguous authenticated spelling token range, find its token end with the pinned Clang lexer and set `rawSha256 = SHA-256(exact original source bytes [beginOffset,endOffset))`, including intervening whitespace/comments but without macro expansion or text normalization. The range must map to one file in the authenticated closure. If no such range exists, set null and add `missing-source-anchor`; never hash a pretty-printed type, mangled name, pointer, or formatted diagnostic as raw content. The exact `clangKind` is the pinned Clang 18.1.3 enum spelling.

`entity.specializationKind` is null for `primary-template`, `partial-specialization`, and ordinary `supporting-declaration` rows. An undeclared class specialization retained as `supporting-declaration` carries `undeclared`; function-specialization metadata cannot carry `TSK_Undeclared` in this profile; a full explicit specialization carries `explicit-specialization`; a concrete class/function specialization copies its direct Clang `TemplateSpecializationKind`. A missing direct target never erases the reported specialization kind, but it withholds the edge and candidate. Member-specialization kind is carried only on the separate `member-specialization` edge from `MemberSpecializationInfo::getTemplateSpecializationKind()`. Edge-kind mapping is: `templated-declaration`, `redeclares`, and `specializes-primary` have null specialization kind; `declares-specialization-of` is exactly `undeclared`; `instantiates-primary`, `instantiates-partial`, and `instantiates-function-template` use the matching class/function specialization API value and are permitted only with actual-instantiation evidence; `member-specialization` uses its own member API value; `explicit-specializes` is exactly `explicit-specialization`. The class partial pattern remains `partialPatternArguments`; its dependent typed pattern is not an instantiated actual.

### 4. Observation-v3 and truth-v4 field-level projection

Observation-v3 is the v2 observation shard schema plus one required `genericTemplates` object. The existing root `schemaVersion`, `oracle`, `shard`, `counts`, `emitted`, and `nonEmitted` fields keep their v2 meanings and exact old members; root function/RVA counts remain unchanged. The new object has exactly `schemaVersion`, `provider`, `bindings`, `units`, `entities`, `edges`, and `counts`; `schemaVersion` is 1 and `provider` is `clang-libtooling-cxx-v1`. Its `bindings` has exactly 14 SHA-256 fields: the 11 provenance fields (`scopeSha256`, `sourceLockSha256`, `artifactManifestSha256`, `buildRecordSha256`, `sourceArchiveSha256`, `sourceInventorySha256`, `generatedInventorySha256`, `richArtifactSha256`, `richInventorySha256`, `compilationDatabaseSha256`, `frontendProfileSha256`), plus `frontendReceiptSha256`, `dwarfArtifactSha256`, and `genericEvidenceArtifactSha256`. The evidence artifact digest is the SHA-256 and byte count from the enclosing authenticated output inventory; it is not embedded into the evidence artifact's own hash preimage. `units` uses the exact evidence unit shape, `entities` and `edges` use the exact v1 evidence row shapes, and the final observation projection retains each physical row.

In generic-evidence-v1, `resolvedSemanticIdentityId` and `identityProofKind` are always required JSON nulls; that per-shard file only reports candidates. Observation-v3 assigns those fields only after all authenticated shards are present. Compute `anchorBucketId = H("decomp-thing/generic-template/source-anchor-bucket/v1", {sourceRevision,canonicalAnchor,lexicalParentAnchors,semanticParentAnchors,entityKind,declarationKind,canonicalName,languageMode})`. This bucket is solely for conflict detection and never authorizes a join. Within a bucket, form canonical groups only from same-unit `redeclares` edge connected components; a singleton row is one component. If the bucket has more than one component, more than one normalized group payload, or any unknown/unsupported group member, mark its rows `ambiguous` or preserve their existing unsupported/unknown status, add `semantic-anchor-conflict` for a conflict, and leave both identity fields null. Only a bucket with exactly one supported component and one candidate may receive `resolvedSemanticIdentityId = H("decomp-thing/generic-template/resolved/v1", {candidateId,identityProofKind:"clang-canonical-declaration-group-in-one-ASTContext-v1"})` on every component row. Candidate equality never joins components. Repeated headers in two TUs therefore remain ambiguous; a pattern-to-instance edge remains a relation and never collapses their identity.

The collision population is broader than `genericTemplates.entities`. Before resolving any generic candidate, #1467/#1468's full-run pass must include every bounded ordinary emitted-definition anchor claim exposed by an additive raw-input/rederivation interface, as well as every anchor-bearing #1467 `sourceEntities` row and all generic frontend rows. An ordinary claim is an internal non-scoreable collision record, not an extra `sourceEntities` row or emitted-RVA row. Build it from the authenticated raw DIE locator plus the rederived `FullTreeSourceAnchorFields`/`FullTreeSourceAnchorKind.SOURCE_DEFINITION` fields; never accept a caller-supplied claim or trust a candidate hash as a claim. For comparison only, use `claimBucketId = H("decomp-thing/generic-template/source-claim-bucket/v1", {sourceRevision,sourcePath,sourceFileSha256,line})` from exact validated source path, source-file digest, and declaration line. This deliberately coarse location bucket does not use names, demangling, signatures, or candidate IDs and can only create a collision; it can never join rows. An ordinary emitted claim and a #1467 source-census row with the same authenticated raw DIE locator are one physical claimant; otherwise each distinct physical DIE locator and each frontend physical locator is a separate claimant. Within the generic frontend set, define a claim-only grouping graph inside each unit from direct `redeclares` edges and direct `templated-declaration` ownership edges. The latter joins a `ClassTemplateDecl`/`FunctionTemplateDecl` wrapper only to the exact same-ASTContext pointer returned by that wrapper's `getTemplatedDecl()`; validate the edge by pointer equality and require both physical rows in the same unit. Connected components in this narrow graph count as one claimant in the coarse `claimBucketId` check only. A wrapper plus its templated-declaration child therefore does not self-collide, but both rows remain separate physical facts with unchanged IDs, kinds, locations, candidate fields, and serialized edge. This grouping never joins identities, supplies candidate proof, changes the detailed `anchorBucketId` rule, or crosses units; no name, source tuple, or candidate hash creates a grouping edge. A valid wrapper/child pair plus any third physical locator/component is still multiple claimants and forces generic rows in that coarse bucket to remain ambiguous. A generic identity is eligible for resolution only when its detailed `anchorBucketId` contains exactly one supported direct `redeclares` component, its coarse `claimBucketId` contains exactly one supported claim-only component under these rules, and neither bucket has an incomplete claimant. If a bucket has multiple claimants, all generic rows in it remain represented but ambiguous; if an ordinary claim lacks any field needed to prove its bucket, the full-run pass fails closed and publishes no resolved generic identities. A concrete emitted instance is not linked to an ordinary emitted RVA by this procedure.

After reconciliation, every `supported` entity has a non-null resolved ID; every `ambiguous` entity has null IDs; and `unknown`/`unsupported` entities have null IDs. `resolvedEntityCount` counts `supported` rows with non-null IDs, `ambiguousEntityCount` counts `ambiguous` rows, and `unresolvedEntityCount` counts `unknown` plus `unsupported` rows. These three disjoint categories sum to `entityCount`. Observation-v3 `genericTemplates.counts` is exactly `{unitCount,entityCount,edgeCount,reasonCodeCount,resolvedEntityCount,ambiguousEntityCount,unresolvedEntityCount,entityKindCounts,edgeKindCounts,statusCounts,reasonCounts}`. `entityKindCounts` contains all five entity-kind keys; `edgeKindCounts` all nine edge-kind keys; `statusCounts` all four statuses; `reasonCounts` all closed evidence reason-code keys. Every map contains every key with a non-negative integer, including zeroes. Unit/entity/edge totals equal array lengths; entity-kind/status maps sum to entityCount; edge-kind map sums to edgeCount; reasonCounts sum to reasonCodeCount; resolved + ambiguous + unresolved entity counts sum to entityCount. Root v2 `counts` is not reused for these facts. Any observation-v3 index repeats this exact full-run `genericTemplates.counts` and binds the ordered shard evidence artifact digests; it is published only after the full-run reconciliation above has completed. The index's top-level `genericTemplates` object has exactly `schemaVersion`, `provider`, `bindings`, `shards`, and `counts`, with `schemaVersion:1` and the same provider. Its `bindings` has exactly the eleven common provenance fields plus aggregate `frontendReceiptSha256`. Its `shards` is a one-to-one list for all index shard rows, sorted by unsigned UTF-8 `shardId` bytes with no duplicates; each row has exactly `shardId`, `dwarfArtifactSha256`, `genericEvidenceArtifactSha256`, `genericEvidenceArtifactBytes`, `frontendReceiptSha256`, and `genericCounts`, where `genericCounts` has the exact shard-local count shape defined above. Aggregate `frontendReceiptSha256` is `H("decomp-thing/generic-template/full-run-receipt-set/v1", {schemaVersion:1,shards:[{shardId,frontendReceiptSha256}]})`, where the inner list follows the same unsigned UTF-8 `shardId` order; it is not included in its own preimage. `counts` is the full-run count object above.

Truth-v4 shard and index schemas are additive versions of truth-v3. Each truth shard adds the same required top-level `genericTemplates` object as observation-v3, with shard-local units/entities/edges and the exact nested generic count object; its existing `oracle`, `shard`, `functions`, `nonEmitted`, and numeric root `counts` retain their truth-v3-compatible members and meanings. The truth index retains its existing numeric emitted/non-emitted root count members and adds a top-level `genericTemplates` index object with the exact same index shape specified above; each existing shard manifest row adds its matching generic count object and evidence artifact digest. Truth generation and validation independently rerun the complete raw-input frontend, redo the full-run candidate/anchor-bucket pass, then project the result; neither observation-v3 generic rows nor candidate-supplied resolved IDs are truth inputs. Generic entities/edges are never copied into `functions` or `nonEmitted`, and no generic count changes emitted-RVA, recall, or score denominators.

The only policy additions are now matched by these concrete wire fields: observation-v3 adds `genericTemplates: "separate-nonscoreable-evidence-v1"` at policy version 5; truth-v4 adds `genericTemplates: "raw-rederived-nonscoreable-census-v1"` at policy version 4. ### 5. Exhaustive Clang entity kinds and actual-instantiation proof

The `entityKind` mapping above is normative and distinct from `declarationKind`; the implementation and raw rederiver must share its exact ordered direct-dynamic-type table. Clang 18.1.3 pins class specialization kind, arguments, selected primary/partial, and the `getInstantiatedFrom()` guard in [`DeclTemplate.h`](https://github.com/llvm/llvm-project/blob/llvmorg-18.1.3/clang/include/clang/AST/DeclTemplate.h#L1716-L1795). `getInstantiatedFrom()` returns an empty `PointerUnion` unless the specialization kind is an actual template-instantiation kind, while `getSpecializedTemplateOrPartial()` can still expose a selected template; the latter alone is not instantiation evidence. The function specialization and member-specialization APIs are pinned in [`DeclTemplate.h`](https://github.com/llvm/llvm-project/blob/llvmorg-18.1.3/clang/include/clang/AST/DeclTemplate.h#L489-L514) and [`Decl.h`](https://github.com/llvm/llvm-project/blob/llvmorg-18.1.3/clang/include/clang/AST/Decl.h#L2583-L2663). Clang's function-specialization metadata refuses `TSK_Undeclared`, so the new `declares-specialization-of` edge is class-only.

`declares-specialization-of` preserves a class specialization declaration whose Clang kind is `TSK_Undeclared`: source is the physical `ClassTemplateSpecializationDecl`, target is its exact `getSpecializedTemplateOrPartial()` pointer, `specializationKind` is `undeclared`, and `primaryActuals` is the exact typed `getTemplateArgs()` vector. It is a typed declaration relationship, not an instance edge, not candidate-binding evidence, and not a resolved identity. The source row remains `supporting-declaration` with local status computed by the precedence rule above, includes `specialization-not-instantiated` and any independent unsupported reason, and has null candidate/resolved IDs. Every `instantiates-primary`/`instantiates-partial` class edge requires both an allowed instantiation `TemplateSpecializationKind` and a non-empty `getInstantiatedFrom()` pointer identical to the direct selected-template pointer; every function instantiation edge requires its direct `FunctionTemplateSpecializationInfo`, primary pointer, allowed kind, and typed actuals. Missing proof withholds that edge. This explicit distinction preserves the incomplete `A<int>*` observation without labeling it an instantiation.


### Exhaustive formals and signature API mapping

The `formals` field is an ordered typed parameter list, never inferred from source spelling. The exact row-class mapping is:

| `entityKind` and direct declaration | `formals` source | `signature` source |
| --- | --- | --- |
| `primary-template` class wrapper (`ClassTemplateDecl`) | Its own `TemplateDecl::getTemplateParameters()` list. | Null for a class template. |
| `primary-template` function wrapper (`FunctionTemplateDecl`) | Its own `TemplateDecl::getTemplateParameters()` list. | The exact direct `getTemplatedDecl()` `FunctionDecl` type. |
| `partial-specialization` (`ClassTemplatePartialSpecializationDecl`) | Its own `getTemplateParameters()` list; `partialDeducedArguments` use these slots. | Null. |
| `explicit-specialization` class (`ClassTemplateSpecializationDecl`) | Parameters of the exact direct primary `ClassTemplateDecl` returned by `getSpecializedTemplate()`. | Null. |
| `explicit-specialization` function (`FunctionDecl`) | Parameters of its exact direct `getPrimaryTemplate()` target. | The specialization `FunctionDecl`'s own type. |
| `concrete-instantiation` class (`ClassTemplateSpecializationDecl`) | Parameters of the associated primary `ClassTemplateDecl`; if the selected target is a partial specialization, take its direct `getSpecializedTemplate()` primary. The partial's own parameters are read from the exact partial entity for `partialDeducedArguments`. | Null. |
| `concrete-instantiation` function (`FunctionDecl`) | Parameters of its exact direct `FunctionTemplateSpecializationInfo` primary template. | The instantiated `FunctionDecl`'s own type. |
| `supporting-declaration` | An undeclared class specialization uses the primary parameters reached from its exact selected primary/partial pointer (following a partial's direct `getSpecializedTemplate()`); a function specialization with a direct `getPrimaryTemplate()` uses that exact primary list. A wrapper's templated child may copy its owner's formals only when the serialized `templated-declaration` edge is validated by pointer equality. `ConceptDecl` has no v1 row or formal-list path. All other support rows use an empty array. | For a direct `FunctionDecl`, its own type; for every non-function row, null. |

For every `TemplateParameterList`, enumerate `asArray()` in Clang order and classify each direct parameter as `TemplateTypeParmDecl`, `NonTypeTemplateParmDecl`, or `TemplateTemplateParmDecl`. Read depth/index from the direct parameter's `TemplateParmPosition` API and pack state from its direct kind-specific API; use the non-type parameter's direct declared `QualType`; recurse into a template-template parameter's own `getTemplateParameters()` for `nestedFormals`. Read defaults through that exact parameter's type-, non-type-, or template-template default API and merge redeclaration-chain values under amendment 1's rule. Clang 18.1.3 pins the common position accessors in [`TemplateParmPosition`](https://github.com/llvm/llvm-project/blob/llvmorg-18.1.3/clang/include/clang/AST/DeclTemplate.h#L1040-L1071), the kind-specific pack methods for [type parameters](https://github.com/llvm/llvm-project/blob/llvmorg-18.1.3/clang/include/clang/AST/DeclTemplate.h#L1179-L1186), [non-type parameters](https://github.com/llvm/llvm-project/blob/llvmorg-18.1.3/clang/include/clang/AST/DeclTemplate.h#L1321-L1364), and [template-template parameters](https://github.com/llvm/llvm-project/blob/llvmorg-18.1.3/clang/include/clang/AST/DeclTemplate.h#L1450-L1520); their corresponding defaults are pinned [here](https://github.com/llvm/llvm-project/blob/llvmorg-18.1.3/clang/include/clang/AST/DeclTemplate.h#L1137-L1157), [here](https://github.com/llvm/llvm-project/blob/llvmorg-18.1.3/clang/include/clang/AST/DeclTemplate.h#L1329-L1343), and [here](https://github.com/llvm/llvm-project/blob/llvmorg-18.1.3/clang/include/clang/AST/DeclTemplate.h#L1561-L1577). For each non-null signature, start from the indicated direct `FunctionDecl::getType()`, require a C++14 `FunctionProtoType`, and build `result` from `getReturnType()`, the ordered `parameters` from `getParamTypes()`, and `variadic` from `isVariadic()`. ### Closed redeclaration-supported relevance

Only these redeclarable direct declaration classes may contribute `redeclares` edges or canonical candidate groups in v1: `ClassTemplateDecl`, `FunctionTemplateDecl`, `ClassTemplatePartialSpecializationDecl`, `ClassTemplateSpecializationDecl`, `FunctionDecl`, `RecordDecl`/`CXXRecordDecl`, `EnumDecl`, and `NamespaceDecl`. For each, emit an edge only when its direct `getPreviousDecl()` returns the exact target pointer reached in the same `ASTContext`; do not use generic `Decl::getCanonicalDecl()` to create a missing edge. This covers class/record and enum type declarations, namespace parent rows, template wrappers/specializations, and function declarations required by supported type and argument descriptors. Clang 18.1.3 declares the enum chain in [`Decl.h`](https://github.com/llvm/llvm-project/blob/llvmorg-18.1.3/clang/include/clang/AST/Decl.h#L3554-L3569), namespace redeclarability and inherited `getPreviousDecl()` in [`Decl.h`](https://github.com/llvm/llvm-project/blob/llvmorg-18.1.3/clang/include/clang/AST/Decl.h#L495-L540), record chains in [`Decl.h`](https://github.com/llvm/llvm-project/blob/llvmorg-18.1.3/clang/include/clang/AST/Decl.h#L3769-L3775), function chains in [`Decl.h`](https://github.com/llvm/llvm-project/blob/llvmorg-18.1.3/clang/include/clang/AST/Decl.h#L1937-L1947), and template redeclaration APIs in [`DeclTemplate.h`](https://github.com/llvm/llvm-project/blob/llvmorg-18.1.3/clang/include/clang/AST/DeclTemplate.h#L960-L968) and [class templates](https://github.com/llvm/llvm-project/blob/llvmorg-18.1.3/clang/include/clang/AST/DeclTemplate.h#L2130-L2140).

`VarTemplateDecl`, `VarTemplatePartialSpecializationDecl`, and their full specializations are outside the v1 census; no rows or unsupported-row completeness are promised, and `variable-template` remains reserved vocabulary only. A required typed relation from an in-scope row to this excluded family fails the action closed. `ConceptDecl` has no v1 entity row; `unsupported-concept` remains reserved fail-closed vocabulary, and C++20/concepts-enabled actions reject before extraction. Any other `NamedDecl` reached only as an optional unrelated AST node is not an entity row. For a required direct type/template reference to another unsupported named kind within the v1 census, retain a bounded `supporting-declaration`/`unsupported` row with the matching closed `unsupported-type-kind` or `unsupported-template-kind` reason, emit no unproven relation, and withhold candidates for every fact that depends on it; this fallback explicitly excludes variable-template declarations and specializations. Non-named required relation targets and non-named parent contexts continue to fail the action closed. This keeps `other-named` as a declaration-kind fallback without implying generic relation support.
