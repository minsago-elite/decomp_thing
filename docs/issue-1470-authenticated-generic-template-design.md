# Authenticated generic template evidence: design proposal

**Review artifact for the open design issue.** This document proposes a bounded contract and implementation issue set for independent review. It is not a frozen or accepted contract, and authorizes no producer, observation sink, truth projection, schema migration, or production qualification. The historical DWARF/source baseline is master commit `e5ff2c537c09eb3c048cba80a1ac53dcf00f2d6a` (merged PR #1469); the current integration baseline for this revision is master commit `0dd25c2d31cfcc50d136d7429f9d75f6b263e042` (merged PR #1472).

## Decision

Use a versioned Clang frontend evidence adapter as the first supported generic-template provider. It must run with the exact Clang frontend authenticated for the build action, over the authenticated source and build inputs, and record compiler-owned declaration relationships and typed template arguments. A separate raw-input validator replays that action and regenerates the evidence. The serialized frontend output is a transport artifact, never truth by virtue of its own digest.

DWARF remains the source of physical emitted-instance evidence. Frontend pattern facts and DWARF DIE facts have different physical locators and are not joined by names, mangling, candidate hashes, offsets, visitation order, or approximate coordinates. DWARF5 §2.23 explicitly says the format does not represent generic definitions, but represents each instantiation and its actual parameters; §3.3.7 and §5.7.7 make the same limitation for function and class templates. Therefore a missing frontend proof remains unknown. The GCC and Clang DWARF5 records inspected for #1469 show typed concrete instances but no generic-pattern-to-instance edge. The accepted ordinary `DW_AT_abstract_origin` edge in #1469 is inline evidence only.

The generic facts use a new `full-tree-generic-template-evidence-v1` schema/policy. They do not extend observation-v2 or truth-v3. When they are eventually projected, use additive observation-v3 and truth-v4 paths; keep observation-v1/v2 and truth-v2/v3 schemas, policies, digests, APIs, and migration vectors byte-for-byte unchanged. The generic source census remains separate from emitted-RVA score denominators.

## Evidence and feasibility

| Evidence inspected | What it supports | Limit |
| --- | --- | --- |
| Official DWARF5 §2.23, §3.3.7, §5.7.7 | Concrete template-instance DIEs and typed actual parameters can be retained. | No portable generic-definition DIE or mandatory pattern-to-instance link. |
| Merged #1469 at the reviewed baseline; source-identity producer/model and fixture report | Bounded artifact-bound DIE rows, ordered typed actuals, concrete candidate identities, unknown generic links, digest-bound scope/inventory, and existing no-partial-publication controls. | It intentionally has no source/frontend generic relation. |
| Merged #1472 at current master `0dd25c2d31cfcc50d136d7429f9d75f6b263e042`; source-entity producer/model | Observation-v2 adds a bounded `anchorClaim(kind,candidateId,physicalClaimId)` callback, including ordinary emitted-definition claims. | Ordinary emitted definitions are not `sourceEntities`; the callback omits the provider-resolved source path, source-file digest, and declaration line needed by C's coarser location bucket. |
| Current master build-record schema | [oracle/build-record.schema.json](https://github.com/minsago-elite/decomp_thing/blob/0dd25c2d31cfcc50d136d7429f9d75f6b263e042/oracle/build-record.schema.json#L48-L55) requires environment.variables to include LC_ALL="C", a canonical positive SOURCE_DATE_EPOCH, and TZ="UTC". | The frontend action must carry the required UTC value into its effective environment and authenticated provenance; it cannot silently drop it. |
| Clang LibTooling and AST API documentation | A `ClangTool` runs a `FrontendAction` with a compilation database; `FunctionDecl::getPrimaryTemplate`, `ClassTemplateSpecializationDecl::getSpecializedTemplateOrPartial`, and `getTemplateArgs` expose semantic links and typed actuals. | This is a Clang-specific interface. Its records still require authenticated inputs and raw replay. |
| Clang JSON compilation database specification | A command entry records the working directory, main source and compile command; the `arguments` vector is preferred over shell text. | A database describes a command; it does not attest that it ran or that its ambient files/environment were controlled. |
| Official GCC template-instantiation documentation | GCC may emit duplicate instances per translation unit and let the linker discard duplicates. | Emission/linker behavior is not a generic source identity relation. GCC is not a v1 frontend provider. |

The feasibility claim is deliberately narrow: Clang's semantic AST APIs offer direct template declaration pointers and ordered `TemplateArgument` values, so a bounded C++ `FrontendAction` can serialize those relationships without parsing names. PR #1469 already established that the selected C++ compiler fixtures contain the concrete-instance side of the evidence and that the DWARF side lacks the generic edge. The first implementation should exercise a pinned Clang 18.1.3 fixture profile (also used by #1469's recorded fixture matrix) and record the exact executable/runtime digests; version text alone is not authentication. No claim is made that GCC's frontend has equivalent stable API coverage, that any production build has been requalified, or that Clang and GCC ASTs are interchangeable.

Pinned Clang 18.1.3 primary API sources: [`DeclTemplate.h`](https://github.com/llvm/llvm-project/blob/llvmorg-18.1.3/clang/include/clang/AST/DeclTemplate.h#L1774-L1812) documents the selected class partial and its deduced `getTemplateInstantiationArgs()`; lines [436–612](https://github.com/llvm/llvm-project/blob/llvmorg-18.1.3/clang/include/clang/AST/DeclTemplate.h#L436-L612) distinguish `FunctionTemplateSpecializationInfo::TemplateArguments` from `TemplateArgumentsAsWritten` and document the separate `MemberSpecializationInfo` relationship/kind. [`Decl.h`](https://github.com/llvm/llvm-project/blob/llvmorg-18.1.3/clang/include/clang/AST/Decl.h#L2583-L2663) defines `FunctionDecl` member/template-specialization APIs and [`FunctionDecl::getNameInfo()`](https://github.com/llvm/llvm-project/blob/llvmorg-18.1.3/clang/include/clang/AST/Decl.h#L1969-L1972). [`DeclarationName.h`](https://github.com/llvm/llvm-project/blob/llvmorg-18.1.3/clang/include/clang/AST/DeclarationName.h#L694-L801) defines `DeclarationNameInfo::getSourceRange()` and multi-token name locations; [`Lexer.h`](https://github.com/llvm/llvm-project/blob/llvmorg-18.1.3/clang/include/clang/Lex/Lexer.h#L366-L394) defines token-end and character-range conversion. The traversal pins [`TemplateDecl::getTemplatedDecl()`](https://github.com/llvm/llvm-project/blob/llvmorg-18.1.3/clang/include/clang/AST/DeclTemplate.h#L402-L404), the class partial ordered-list overload (lines [2163–2165](https://github.com/llvm/llvm-project/blob/llvmorg-18.1.3/clang/include/clang/AST/DeclTemplate.h#L2163-L2165)), class specialization range (lines [2201–2213](https://github.com/llvm/llvm-project/blob/llvmorg-18.1.3/clang/include/clang/AST/DeclTemplate.h#L2201-L2213)), and [function specialization ranges](https://github.com/llvm/llvm-project/blob/llvmorg-18.1.3/clang/include/clang/AST/DeclTemplate.h#L983-L995). The exact type normalization API is pinned to [`QualType::getCanonicalType()` and `getSplitUnqualifiedType()` in `Type.h`](https://github.com/llvm/llvm-project/blob/llvmorg-18.1.3/clang/include/clang/AST/Type.h#L944-L981), and macro descriptor fields to [`MacroInfo.h`](https://github.com/llvm/llvm-project/blob/llvmorg-18.1.3/clang/include/clang/Lex/MacroInfo.h#L163-L196). The exact frontend call path is pinned to [`ToolInvocation` in `Tooling.cpp`](https://github.com/llvm/llvm-project/blob/llvmorg-18.1.3/clang/lib/Tooling/Tooling.cpp#L329-L435): it builds the driver invocation from the supplied vector, then runs the supplied action; the same source shows [`ClangTool` installs three default adjusters and injects a resource directory](https://github.com/llvm/llvm-project/blob/llvmorg-18.1.3/clang/lib/Tooling/Tooling.cpp#L437-L479). Therefore the v1 adapter uses `ToolInvocation` directly and does not use `ClangTool` or call `ClangTool::run`. These APIs are the v1 profile contract, not claims that another Clang release or frontend is wire-compatible. Primary references: [DWARF5](https://dwarfstd.org/doc/DWARF5.pdf), [Clang LibTooling](https://clang.llvm.org/docs/LibTooling.html), [Clang JSON Compilation Database](https://clang.llvm.org/docs/JSONCompilationDatabase.html), [Clang `FunctionDecl`](https://clang.llvm.org/doxygen/classclang_1_1FunctionDecl.html), [Clang `ClassTemplateSpecializationDecl`](https://clang.llvm.org/doxygen/classclang_1_1ClassTemplateSpecializationDecl.html), and [GCC template instantiation](https://gcc.gnu.org/onlinedocs/gcc/Template-Instantiation.html).

## Trust inputs and authentication contract

The producer and validator would accept only the following proposed input chain. Every digest below is SHA-256 over the exact canonical bytes or file bytes named; no caller-provided digest is accepted without rereading and validating its input.

1. **Source identity.** Reuse the authenticated scope, source lock, artifact manifest, source archive, source inventory, generated-file inventory/provenance, and the source-root path normalizer. Bind the Git source revision/tree identity, archive bytes, every translation-unit source blob, every generated source/header, and every opened include. Reject dirty, replaced, symlink-escaping, missing, or digest-mismatched inputs. A file outside the authenticated source/generated/toolchain closure makes that translation unit unsupported; it is not silently read from the host.
2. **Build action.** Reuse the authenticated build record, FullTreeClangCaptureInputControl registry, FullTreeClangCompdbReconciliationControl registry, and their raw predecessors. Select one action by authenticated unitId, actionSha256, and its unique reconciliation match; do not infer an action from a source filename or rendered compiler name. The reconciler binds one external compilation-database record to that capture action by exact directory, file, output, compiler token, fixed command suffix, and derived capture argv ([baseline capture frame and validation](https://github.com/minsago-elite/decomp_thing/blob/0dd25c2d31cfcc50d136d7429f9d75f6b263e042/src/main/kotlin/decompengine/oracle/fulltree/FullTreeClangCaptureInputControl.kt#L806-L860), [compdb-to-capture reconciliation](https://github.com/minsago-elite/decomp_thing/blob/0dd25c2d31cfcc50d136d7429f9d75f6b263e042/src/main/kotlin/decompengine/oracle/fulltree/FullTreeClangCompdbReconciliationControl.kt#L317-L395)). Original argv is exactly the selected capture action's validated arguments. Its closed prefix is [clang, --no-default-config, -MD, -MT, <object>, -MF, <object>.d, -o, <object>, -c, <main-source>], followed only by the captured authenticated compiler-option tail. The control already rejects indirect @response/config inputs, joined or duplicate frame options, malformed operands, and a frame that does not identify the authenticated action's object, depfile, and main source. V1 does not admit response files. Let captureActionSha256 be the selected action's validated actionSha256 and argvSha256 = SHA-256(OracleJson.canonicalBytes(original action.arguments)). Derive executionArgv by removing exactly original argv[2..6] (-MD, -MT, its object operand, -MF, and its depfile operand) and preserving every other token and its order; executionArgv is exactly [argv[0], argv[1], argv[7], argv[8], argv[9], argv[10], *argv.drop(11)]. This keeps the existing --no-default-config, -o <object>, -c <main-source>, compiler identity, and every semantic option byte-for-byte. executionArgvSha256 hashes that derived vector. No source, build, or compiler path is rewritten. Construct a read-only VFS that exposes each authenticated source/generated/build/toolchain input only at its exact captured absolute path spelling, backed by digest-verified bytes; source/build/toolchain paths have no second `/__decomp` alias or backing/external-name spelling, and the VFS has no host fallback. Set the runtime VFS cwd to the selected capture action's exact absolute `directory` string byte-for-byte. Serialize only its normalized closure-relative `cwd`; raw replay reconstructs and uses the same captured absolute cwd and path namespace. Persist only captureActionSha256 and the argv/executionArgv digests in provenance; do not serialize either vector, whose exact raw paths are recoverable from the validated controls and would expose machine paths. Raw replay reconstructs both arrays from the same controls, recomputes the digests and strip, and passes the derived vector unchanged to ToolInvocation. The raw compdb bytes and reconciler commitments authenticate the upstream command; the capture action hash and both argv digests bind the original evidence and derived frontend invocation into actionId. Reject any mismatch before driver construction. The original --no-default-config excludes ambient Clang default config files. Explicit config options are rejected in either vector: --config=FILE, --config FILE, --config-system-dir=DIR, and --config-user-dir=DIR (also reject exact bare directory-option spellings defensively). The pinned [Options.td](https://github.com/llvm/llvm-project/blob/llvmorg-18.1.3/clang/include/clang/Driver/Options.td#L1023-L1037) defines --config= plus its separate alias, --no-default-config, and the joined system/user directory options; the latter disables default loading only and does not disable explicit configs. Clang's [configuration-file documentation](https://clang.llvm.org/docs/UsersManual.html#configuration-files) explains that configs group command-line options and may be loaded explicitly.

   V1 also rejects dynamic extension, command-forwarding, driver-mode, response-quoting override, and output-producing auxiliary options in both `argv` and `executionArgv`. As defense in depth, also reject the exact alternate/vendor spellings `-index-store-path` and `-index-unit-output-path` in both arrays, in separate form together with the required operand and in `=<value>` form. These are only denylisted spellings: neither is declared in the pinned upstream Linux Clang 18.1.3 [`Options.td`](https://github.com/llvm/llvm-project/blob/llvmorg-18.1.3/clang/include/clang/Driver/Options.td), and this check does not admit Apple/vendor Clang or define an indexing capability. The closed rejection set is `-fplugin=`, `-fplugin-arg-*`, `-fpass-plugin=`, `-load`, `-plugin`, `-plugin-arg-*`, `-add-plugin`, both `-mllvm ARG` and `-mllvm=ARG`, both `-Xclang ARG` and `-Xclang=ARG`, `-cc1`, `-cc1as`, all `-Xarch_*` forms, `-Xassembler`, `-Xlinker`, `-Xoffload-linker`, `-Xopenmp-target`/`-Xopenmp-target=`, `-Xcuda-fatbinary`, and `-Xcuda-ptxas`. The pinned [`Options.td` entries](https://github.com/llvm/llvm-project/blob/llvmorg-18.1.3/clang/include/clang/Driver/Options.td#L889-L918) document driver-to-CC1, assembler, linker, and offload forwarding; `-mllvm` aliases are defined [here](https://github.com/llvm/llvm-project/blob/llvmorg-18.1.3/clang/include/clang/Driver/Options.td#L4301-L4307), direct `-cc1`/`-cc1as` flags [here](https://github.com/llvm/llvm-project/blob/llvmorg-18.1.3/clang/include/clang/Driver/Options.td#L6891-L6897), and the plugin and pass-plugin entries are [here](https://github.com/llvm/llvm-project/blob/llvmorg-18.1.3/clang/include/clang/Driver/Options.td#L3402-L3412) and [here](https://github.com/llvm/llvm-project/blob/llvmorg-18.1.3/clang/include/clang/Driver/Options.td#L6954-L6959), and CC1's plugin loader is [here](https://github.com/llvm/llvm-project/blob/llvmorg-18.1.3/clang/include/clang/Driver/Options.td#L7534-L7540). Reject both the option token and any required operand if the option is separate. These exclusions make the accepted action an in-process fixed `FrontendAction` with no user plugin, LLVM pass loader, direct CC1 override, or offload/child-tool route. The runner clears every ambient host variable outside the allowlist from the child environment, including dynamic-loader injection variables; the authenticated declared action environment is separately rejected if it contains a non-allowlisted name or unreadable value; v1 admits no other argument-controlled mechanism that can load executable extensions. The runner snapshots executable/shared-object mappings immediately before the action and after completion; any changed mapping set, unrecognized/deleted/out-of-profile mapping, or failed enumeration rejects the action. The pre/post mapping snapshots are defense in depth for the stable loaded closure only; they cannot detect a plugin loaded and unloaded during the action and never substitute for closed argument checks.

   V1 also rejects the pinned driver forwarding routes `-Xpreprocessor` and `-Wp,` in both the original argument vector and the derived executionArgv tokens. Reject every `-Xpreprocessor` option and its required operand; the pinned option is separate, and `-Xpreprocessor=<arg>` is rejected defensively. Reject every token beginning `-Wp,` as a whole, regardless of its comma-separated contents. This closes forwarding forms that can carry `-load` or another CC1 loader option. Clang 18.1.3 defines `Xpreprocessor` as `Separate` and `Wp_COMMA` as `CommaJoined` in [`Options.td`](https://github.com/llvm/llvm-project/blob/llvmorg-18.1.3/clang/include/clang/Driver/Options.td#L862-L864) and [`Options.td`](https://github.com/llvm/llvm-project/blob/llvmorg-18.1.3/clang/include/clang/Driver/Options.td#L917-L918); the driver forwards both with `Args.AddAllArgValues` in [`Clang.cpp`](https://github.com/llvm/llvm-project/blob/llvmorg-18.1.3/clang/lib/Driver/ToolChains/Clang.cpp#L1155-L1160). These tokens are rejected before `ToolInvocation`; pre/post mappings do not detect a transient load and are not a substitute.

   V1 rejects forced-include and macro-include options before frontend launch: `-include`, `--include`, `-imacros`, and `--imacros` in their separate and joined forms, plus documented `--include=FILE` and any equals form defensively. The separate option operand is rejected with its option. PCH use has its own closed gate below; it is not implied by the module or forced-include checks. Apply this closed check to original and derived vectors. The pinned [`Options.td`](https://github.com/llvm/llvm-project/blob/llvmorg-18.1.3/clang/include/clang/Driver/Options.td#L4094-L4105) declares the include and imacros forms and [the `--include=` alias](https://github.com/llvm/llvm-project/blob/llvmorg-18.1.3/clang/include/clang/Driver/Options.td#L5428). Clang 18.1.3's [`InitPreprocessor.cpp`](https://github.com/llvm/llvm-project/blob/llvmorg-18.1.3/clang/lib/Frontend/InitPreprocessor.cpp#L61-L71) appends these implicit include directives to the predefines buffer. No forced-include or macro-include dependency/event is admitted as valid v1 evidence. Separately, reject explicit PCH use before driver preflight and before `ToolInvocation`: in both original `argv` and expanded `executionArgv`, reject the exact pinned separate option `-include-pch` together with its required file operand, plus defensive `-include-pch=FILE` and any concatenated token beginning with `-include-pch`. Clang 18.1.3 defines only `-include-pch FILE` as a `Separate` option (no joined alias) in [`Options.td`](https://github.com/llvm/llvm-project/blob/llvmorg-18.1.3/clang/include/clang/Driver/Options.td#L4102-L4105). After parsing the selected single CC1 command into `CompilerInvocation`, reject unless `PreprocessorOptions` has empty `ImplicitPCHInclude`, empty `ChainedIncludes`, empty `PCHThroughHeader`, false `PCHWithHdrStop` and `PCHWithHdrStopCreate`, `PrecompiledPreambleBytes == {0,false}`, and false `GeneratePreamble`; these effective fields are defined in [`PreprocessorOptions.h`](https://github.com/llvm/llvm-project/blob/llvmorg-18.1.3/clang/include/clang/Lex/PreprocessorOptions.h#L80-L130). After the action, before any row/evidence publication, reject and discard all rows if `CompilerInstance::getASTReader()` is non-null; this catches a PCH/serialized-AST source loaded through a header or preamble path even when the explicit option and `modules:false` checks pass ([`CompilerInstance.h`](https://github.com/llvm/llvm-project/blob/llvmorg-18.1.3/clang/include/clang/Frontend/CompilerInstance.h#L512-L515)). No PCH-backed or precompiled-preamble translation unit is supported in v1.

   V1 rejects explicit PCM load routes before frontend invocation. In both original `argv` and derived `executionArgv`, reject every token beginning with the joined `-fmodule-file=` spelling (covering both unnamed `<file>` and named `<name>=<file>` values) and every token beginning with joined `-fprebuilt-module-path=`; defensively reject either bare option spelling and empty-value forms as well. The pinned Clang 18.1.3 [`Options.td`](https://github.com/llvm/llvm-project/blob/llvmorg-18.1.3/clang/include/clang/Driver/Options.td#L2832-L2839) and [`Options.td`](https://github.com/llvm/llvm-project/blob/llvmorg-18.1.3/clang/include/clang/Driver/Options.td#L2974-L2978) define these joined module-loading paths; `-fmodule-file` explicitly loads a precompiled module. After parsing the selected single-job `CompilerInvocation`, but before `ToolInvocation` or AST extraction, require `FrontendOptions::ModuleFiles.empty()`, `HeaderSearchOptions::PrebuiltModuleFiles.empty()`, `HeaderSearchOptions::PrebuiltModulePaths.empty()`, and `HeaderSearchOptions::EnablePrebuiltImplicitModules == false`. These fields are pinned in [`FrontendOptions.h`](https://github.com/llvm/llvm-project/blob/llvmorg-18.1.3/clang/include/clang/Frontend/FrontendOptions.h#L478-L483) and [`HeaderSearchOptions.h`](https://github.com/llvm/llvm-project/blob/llvmorg-18.1.3/clang/include/clang/Lex/HeaderSearchOptions.h#L111-L149); [`CompilerInvocation.cpp`](https://github.com/llvm/llvm-project/blob/llvmorg-18.1.3/clang/lib/Frontend/CompilerInvocation.cpp#L2633-L2638) fills unnamed `ModuleFiles`, and [its prebuilt-file/path parsing](https://github.com/llvm/llvm-project/blob/llvmorg-18.1.3/clang/lib/Frontend/CompilerInvocation.cpp#L2900-L2910) fills the HeaderSearchOptions fields. Enforce both argv and parsed-state checks even when `LangOptions::Modules` is false. The later non-null `ASTReader` check remains defense in depth and does not replace these pre-invocation gates.

   V1 rejects Clang working-directory overrides in both original argv and derived executionArgv before any driver preflight or ToolInvocation: the pinned option is -working-directory DIR and its joined alias is -working-directory=DIR; reject the option and required operand together. Also reject defensive --working-directory / --working-directory=DIR spellings. The selected capture action's exact absolute `directory` string is the sole runtime cwd, byte-for-byte as captured, and must normalize to the unit's serialized closure-relative `cwd`; the VFS uses that captured path spelling. Clang 18.1.3 defines both forms in [Options.td](https://github.com/llvm/llvm-project/blob/llvmorg-18.1.3/clang/include/clang/Driver/Options.td#L5565-L5571); accepting this option would override the authenticated captured cwd inside the frontend.
   Do not assume Clang's driver preflight is side-effect-free. Driver::BuildCompilation() creates the action graph and jobs before the adapter can count them ([pinned call sequence](https://github.com/llvm/llvm-project/blob/llvmorg-18.1.3/clang/lib/Driver/Driver.cpp#L1385-L1412)). Its job/output planning can create real temporary files: -no-integrated-cpp disables preprocessor-action collapsing, and intermediate output paths use GetTemporaryPath()/createTemporaryFile() ([phase collapse](https://github.com/llvm/llvm-project/blob/llvmorg-18.1.3/clang/lib/Driver/Driver.cpp#L4698-L4702), [temporary-file creation](https://github.com/llvm/llvm-project/blob/llvmorg-18.1.3/clang/lib/Driver/Driver.cpp#L5284-L5320) and [GetTemporaryPath](https://github.com/llvm/llvm-project/blob/llvmorg-18.1.3/clang/lib/Driver/Driver.cpp#L5694-L5702)). Before constructing any Driver or Compilation, scan both original and derived argv and reject exact -###, -fdriver-only, -no-integrated-cpp/--no-integrated-cpp, -traditional-cpp, -rewrite-objc, -save-temps and variants, plus assembler-splitting -fno-integrated-as/-no-integrated-as and any other option that forces a separate frontend/preprocessor/backend/assembler phase or writes driver-planned output. -### and -fdriver-only must be rejected before preflight because ordinary ExecuteCompilation() handles them only after graph construction and can skip job execution; direct ToolInvocation calls the supplied action rather than that execution path ([ExecuteCompilation](https://github.com/llvm/llvm-project/blob/llvmorg-18.1.3/clang/lib/Driver/Driver.cpp#L1751-L1773), [ToolInvocation](https://github.com/llvm/llvm-project/blob/llvmorg-18.1.3/clang/lib/Tooling/Tooling.cpp#L347-L398)). The pinned option definitions include both - and -- spellings for no-integrated-cpp and the -fno-integrated-as/-no-integrated-as aliases ([Options.td](https://github.com/llvm/llvm-project/blob/llvmorg-18.1.3/clang/include/clang/Driver/Options.td#L5020-L5021), [Options.td](https://github.com/llvm/llvm-project/blob/llvmorg-18.1.3/clang/include/clang/Driver/Options.td#L5339-L5362)). Keep the authenticated per-action TMPDIR isolated and remove it on every exit as a backstop; it does not make a denied command acceptable. For remaining inputs, the pinned driver preflight must yield exactly one driver job, exactly one eligible clang CC1 command, exactly one input of the authenticated main-source identity, and no driver::OffloadAction or clang-offload-bundler job. Reject any other action/job/input even if one host CC1 command is present; Tooling.cpp::getCC1Arguments() permits extra CC1 commands in an offload graph and returns the first one. Then call ToolInvocation directly with the same unchanged derived executionArgv, authenticated VFS, and cwd. No job selection occurs after this gate. The graph check is pinned to [Driver::BuildCompilation](https://github.com/llvm/llvm-project/blob/llvmorg-18.1.3/clang/include/clang/Driver/Driver.h#L446-L453), [JobList](https://github.com/llvm/llvm-project/blob/llvmorg-18.1.3/clang/include/clang/Driver/Job.h#L261-L289), and [Tooling.cpp](https://github.com/llvm/llvm-project/blob/llvmorg-18.1.3/clang/lib/Tooling/Tooling.cpp#L87-L155). Additionally reject effective CUDA, HIP, SYCL-device, or OpenCL language modes and the exact pinned offload routes in both argv arrays: -x cuda, -x hip, -x cl, -x hlsl; --cuda-host-only, --cuda-device-only, --cuda-compile-host-device, --cuda-gpu-arch=*, --no-cuda-gpu-arch=*; --offload-arch=*, --no-offload-arch=*; -fopenmp-targets=TRIPLE[,TRIPLE...], -fopenmp-is-target-device, -fopenmp-is-device; and --hip-link. The corresponding Clang 18.1.3 options are defined in [common offload flags](https://github.com/llvm/llvm-project/blob/llvmorg-18.1.3/clang/include/clang/Driver/Options.td#L1130-L1150), [CUDA flags](https://github.com/llvm/llvm-project/blob/llvmorg-18.1.3/clang/include/clang/Driver/Options.td#L1243-L1253), [HIP flags](https://github.com/llvm/llvm-project/blob/llvmorg-18.1.3/clang/include/clang/Driver/Options.td#L1298-L1308), and [OpenMP target flags](https://github.com/llvm/llvm-project/blob/llvmorg-18.1.3/clang/include/clang/Driver/Options.td#L3373-L3375) / [target-device flags](https://github.com/llvm/llvm-project/blob/llvmorg-18.1.3/clang/include/clang/Driver/Options.td#L7801-L7804). Any -fopenmp action has a nonempty openmp extension ID and is unsupported in the C++14 extension-free v1 profile, including host-only OpenMP; the driver preflight independently rejects target/offload job graphs before AST extraction. No multi-job mode is allowed to reach AST extraction.

Stop only at a valid file location; a file-written name therefore has depth zero and each Clang immediate-macro-caller transition counts one, including macro-argument and macro-body frames. A broken chain aborts, and a 257th frame fails with `limit-exceeded`. `getImmediateMacroCallerLoc` is the pinned Clang API that follows one level toward the initial macro invocation; spelling/expansion projection does not change the recorded count ([`SourceManager.h`](https://github.com/llvm/llvm-project/blob/llvmorg-18.1.3/clang/include/clang/Basic/SourceManager.h#L1627-L1639)). `nameRaw` is row-specific physical evidence: it is the exact UTF-8 byte slice of this physical declaration's authenticated original-source name span and is never copied from another redeclaration. It may differ across rows in one canonical redeclaration group. `nameRaw` is never added as a per-row candidate member, nor are row locations; the authenticated file remains bound through `canonicalAnchor.sourceFileSha256`. Only the oldest declaration's own name span supplies the group's `canonicalAnchor.rawName` and `canonicalName` as specified in amendment 1. For a simple identifier, start at the direct declaration name token location and end at `Lexer::getLocForEndOfToken`; for overloaded operators, conversion/literal operators, constructors/destructors, and any other multi-token declaration name, use the direct `DeclarationNameInfo::getSourceRange()` (including the operator keyword and full conversion type as applicable), then take the byte interval from its first token through `Lexer::getLocForEndOfToken` at its last token. For a `TemplateDecl` wrapper, obtain the name span only from its direct `getTemplatedDecl()` pointer and verify that declaration's source location; do not perform a name lookup. Convert spelling endpoints to one authenticated file and original-file byte offsets. The half-open span includes all original whitespace/comments between its first and last name tokens, excludes surrounding trivia, and is never reconstructed from a pretty-printer, demangler, `DeclarationName::getAsString()`, or normalized identifier. Decode the slice as strict UTF-8 without normalization. If the range is invalid, non-contiguous, macro scratch/unmapped, crosses files, contains invalid UTF-8, or cannot be read from an authenticated source file, encode `nameRaw:null`, add `missing-source-anchor`, and withhold the candidate. Tests pin identifiers, `operator+`, `operator new`, conversion operators with multi-token types, literal operators, and macro-generated names. The pinned APIs are Clang 18.1.3 `DeclarationNameInfo::getSourceRange()` and `Lexer::getLocForEndOfToken`; the lexer returns an invalid end when it cannot form a file location.

Map Clang declarations to the closed `declarationKind` enum with this ordered rule set: `ClassTemplateDecl` → `class-template`; `FunctionTemplateDecl` → `function-template`; `CXXRecordDecl` (class, struct, union, including specializations/partials) → `class`; `FunctionDecl` → `function`; `RecordDecl` not already matched as `CXXRecordDecl` → `record`; `EnumDecl` → `enum`; any other `NamedDecl` → `other-named`. The order is significant because template wrappers and `CXXRecordDecl` inherit from broader named/record classes. Non-`NamedDecl` nodes are not entity rows. `TranslationUnitDecl` is the only non-named parent represented by null; if another non-named `DeclContext` occurs in a required parent chain or a required relation target is not a `NamedDecl`, v1 rejects the action rather than dropping a direct parent or fabricating `other-named`. This mapping uses the direct Clang dynamic type only; no spelling heuristic participates.

`entityKind` has a separate exhaustive ordered mapping over every relevant `NamedDecl*` reached by the fixed traversal; it is never inferred from `declarationKind` or a name. First, `ClassTemplatePartialSpecializationDecl` is `partial-specialization`. Next, `ClassTemplateSpecializationDecl` with `TSK_ExplicitSpecialization` is `explicit-specialization`; with `TSK_ImplicitInstantiation`, `TSK_ExplicitInstantiationDeclaration`, or `TSK_ExplicitInstantiationDefinition`, it is `concrete-instantiation` only when `getInstantiatedFrom()` is non-empty and equals the exact `getSpecializedTemplateOrPartial()` target. If that required target is absent or disagrees, retain the row as `supporting-declaration`, `unknown`, with `missing-template-relation`, and emit no instantiates edge. A class specialization with `TSK_Undeclared` is `supporting-declaration`, with base local status `unknown` and `specialization-not-instantiated`; an independent unsupported typed fact raises its status to `unsupported` under the precedence rule below. Next, `ClassTemplateDecl` and `FunctionTemplateDecl` wrappers are `primary-template`; their direct `getTemplatedDecl()` children are `supporting-declaration`, not a second primary. The ordered cases above apply by direct Clang dynamic type, so partial specializations take precedence over their `ClassTemplateSpecializationDecl` base. Non-relevant declarations are walked for closure/ordinals but do not emit rows; non-`NamedDecl` declarations follow the parent/target rules above. This table is exhaustive for emitted entity rows. Local status is computed after collecting every independent row fact and reason code: `unsupported` outranks `unknown`, which outranks `supported`. #### Edge union and Clang specialization mappings

`edges` sort by `(unitId, sourcePhysicalId, kind, targetPhysicalId, canonicalRelationPayloadBytes)`, where the payload is `OracleJson.canonicalBytes({proofKind,specializationKind,argumentVectors})` compared unsigned bytewise. Each edge has exactly `unitId`, `sourcePhysicalId`, `targetPhysicalId`, `kind`, `proofKind`, `specializationKind`, and `argumentVectors`; `specializationKind` is nullable. Endpoints resolve to same-unit entities. Closed `kind` values are `declares-specialization-of`, `templated-declaration`, `redeclares`, `specializes-primary`, `instantiates-primary`, `instantiates-partial`, `instantiates-function-template`, `member-specialization`, and `explicit-specializes`. `proofKind` is one exact API trace: `ClassTemplateSpecializationDecl.getSpecializedTemplateOrPartial`, `ClassTemplateSpecializationDecl.getInstantiatedFrom`, `ClassTemplateSpecializationDecl.getSpecializedTemplate`, `FunctionDecl.getPrimaryTemplate`, `FunctionDecl.getPreviousDecl`, `EnumDecl.getPreviousDecl`, `NamespaceDecl.getPreviousDecl`, `RecordDecl.getPreviousDecl`, `ClassTemplateSpecializationDecl.getPreviousDecl`, `ClassTemplatePartialSpecializationDecl.getPreviousDecl`, `ClassTemplateDecl.getPreviousDecl`, `FunctionTemplateDecl.getPreviousDecl`, `FunctionDecl.getMemberSpecializationInfo->MemberSpecializationInfo.getInstantiatedFrom`, `ClassTemplateDecl.getTemplatedDecl`, or `FunctionTemplateDecl.getTemplatedDecl`. The direct edge receiver and returned declaration pointer are checked under the Clang 18.1.3 profile. Class/function argument-vector fields are independently read from the exact getters specified below: `getTemplateArgs()` / `getTemplateInstantiationArgs()` for class templates, and `getTemplateSpecializationArgs()` / `getTemplateSpecializationArgsAsWritten()` for functions (equivalent to `FunctionTemplateSpecializationInfo::TemplateArguments` / `TemplateArgumentsAsWritten`). `Decl.getCanonicalDecl()` is reserved for same-ASTContext identity grouping, never used to invent an edge. `argumentVectors` always has exactly five required nullable keys: `primaryActuals`, `partialDeducedArguments`, `partialPatternArguments`, `functionActuals`, and `functionArgumentsAsWritten`. For no-binding edges (`templated-declaration`, `redeclares`, `member-specialization`) all five are null. `declares-specialization-of` is a non-binding declaration edge emitted only for `ClassTemplateSpecializationDecl` with `TSK_Undeclared`; it carries class `primaryActuals` and never supplies a candidate-binding vector. Other vectors are populated only as follows.

Vector ordinals are normative: `primaryActuals` and `partialPatternArguments` align with the primary template formals in depth/index order; `partialDeducedArguments` aligns with the selected partial specialization’s own formal depth/index order; `functionActuals` aligns with the selected primary function template’s formals. A pack remains one formal slot whose `pack.elements` preserve inner ordinals. `functionArgumentsAsWritten` preserves only explicit source-written arguments in their written order, may be shorter than the instantiated vector, and is not padded or reindexed. Defaulted/deduced values remain in the corresponding compiler-instantiated vector.

The vector matrix is exhaustive: `templated-declaration` and `redeclares` require all vectors null and null specialization kind; `declares-specialization-of` requires a `ClassTemplateSpecializationDecl` source, `specializationKind: undeclared`, and only class `primaryActuals`; `specializes-primary` requires only `partialPatternArguments`; `instantiates-primary` requires only `primaryActuals`; `instantiates-partial` requires `primaryActuals` plus `partialDeducedArguments`; `instantiates-function-template` requires `functionActuals` and nullable `functionArgumentsAsWritten`; `member-specialization` requires all vectors null and a non-null member specialization kind; `explicit-specializes` requires `primaryActuals` for class specializations or `functionActuals` plus nullable written arguments for function specializations. Every other vector is null. The specialization kind is exactly one of `undeclared`, `implicit-instantiation`, `explicit-specialization`, `explicit-instantiation-declaration`, or `explicit-instantiation-definition`, copied from the matching Clang `TemplateSpecializationKind`; it is null for `templated-declaration`, `redeclares`, and `specializes-primary`.

For each entity, the authoritative edge source for its five `argumentVectors` is determined only by entity class: `primary-template` and `supporting-declaration` have no authoritative candidate-binding edge and use no candidate binding vectors; `declares-specialization-of` is retained as typed relation evidence only and cannot supply candidate identity; `partial-specialization` uses exactly its direct `specializes-primary` edge's `partialPatternArguments`; a concrete class primary uses exactly its direct `instantiates-primary` edge's `primaryActuals`; a concrete class selected through a partial uses exactly its direct `instantiates-partial` edge's `primaryActuals` and `partialDeducedArguments`; a concrete function template specialization uses exactly its direct `instantiates-function-template` edge's `functionActuals` and optional `functionArgumentsAsWritten`; class explicit specializations use exactly their direct `explicit-specializes` edge's `primaryActuals`; function explicit specializations use exactly their direct `explicit-specializes` edge's `functionActuals` and optional written vector. V1 accepts an `explicit-specializes` class edge only when Clang's direct target is the primary `ClassTemplateDecl`; a partial target or otherwise unrepresentable selection remains unknown/unsupported until a separately versioned vector shape is reviewed. `redeclares`, `templated-declaration`, and `member-specialization` never supply candidate argument vectors; a member-specialization edge remains independent metadata. Apply binding-edge cardinality checks only to `partial-specialization`, `concrete-instantiation`, and `explicit-specialization` rows, for which the mapping above defines an authoritative edge kind. If such a row lacks that required edge, has an ineligible edge kind, targets the wrong declaration class, or has more than one non-identical eligible edge, mark it `unknown` with `argument-vector-incomplete` or `ambiguous-template-selection` as appropriate and withhold its candidate; never select the first edge. `primary-template` and `supporting-declaration` rows intentionally require no candidate-binding edge or argument vector, so absence of one does not by itself change their status or candidate eligibility. `declares-specialization-of` remains typed non-binding evidence and cannot satisfy this requirement. Exact duplicate relation observations normalize to one edge. Within a canonical redeclaration group, normalize the direct binding relation payloads against canonical target anchors: repeated identical payloads count once, while missing or conflicting payloads withhold the group's candidate. Retain every distinct typed edge as evidence. For relationship bounds, normalize every observation to the complete edge tuple `{unitId,sourcePhysicalId,targetPhysicalId,kind,proofKind,specializationKind,argumentVectors}`. Exact duplicates collapse to one row before `maxEdgesPerEntity`, `edgeCount`, or byte admission. Two rows with the same endpoints/kind but any different proof, specialization kind, or argument-vector payload are distinct rows and each counts. The ceiling is at most 32 unique outgoing rows per physical source entity; an edge is charged only to its source, never to its target or both endpoints. Relation-walk depth separately counts direct API links on one walk (32 admitted, the 33rd or a cycle fails). Every retained unique edge contributes its complete canonical JSON bytes once to the evidence artifact and its exact marginal bytes to the generic byte ledger; copies repeated in observation/truth shards, indexes, or other artifacts are charged again in each serialized file. There is no independent edge-row ceiling in v1: `maxGenericEvidenceBytes`, authenticated shard/run `serializedBytes`, and the resident-working-set limit bound edge payloads. Exact duplicate observations add no graph/count/byte contribution after normalization; they do not erase distinct typed relations.

For `ClassTemplateSpecializationDecl`, `getTemplateArgs()` is the exact class argument vector. A `TSK_ExplicitSpecialization` row emits `explicit-specializes` to the exact `getSpecializedTemplate()` pointer. A row with `TSK_ImplicitInstantiation`, `TSK_ExplicitInstantiationDeclaration`, or `TSK_ExplicitInstantiationDefinition` emits `instantiates-primary` or `instantiates-partial` only if `getInstantiatedFrom()` is non-empty and pointer-equal to the exact `getSpecializedTemplateOrPartial()` result; its `proofKind` is `ClassTemplateSpecializationDecl.getInstantiatedFrom`. If that instantiation proof is absent or inconsistent, keep the row as `supporting-declaration`, `unknown`, with `missing-template-relation`, preserve the observed specialization kind, and emit no instantiates edge or candidate. For `TSK_Undeclared`, `getInstantiatedFrom()` is empty by contract even when `getSpecializedTemplateOrPartial()` returns a target. Preserve that direct declaration relation as `declares-specialization-of`, with `specializationKind: undeclared`, the exact selected primary/partial target, and `primaryActuals = getTemplateArgs()`; keep its entity kind `supporting-declaration` and its local status per the precedence rule above; include `specialization-not-instantiated`, any independent unsupported reason, and a null candidate. This evidence edge is never a binding edge and never asserts an instantiation. If no direct target exists, preserve the undeclared row but emit no relation edge and add `missing-template-relation`. The partial declaration's own `specializes-primary` edge carries `partialPatternArguments` from `ClassTemplatePartialSpecializationDecl::getTemplateArgs()` in normalized typed pattern order; `getTemplateArgsAsWritten()` source span/raw bytes remain independently authenticated evidence. Example: `template<class T> struct Box; template<class T> struct Box<T*> {}; Box<int*> value;` yields `primaryActuals = [type(pointer(int))]`, selected target `Box<T*>`, and, only for an actual instantiation, `partialDeducedArguments = [type(int)]`. Encoding both as `[type(int*)]`, swapping them, or deriving either from rendered names fails rederivation. For a primary-only instantiation Clang specifies that `getTemplateInstantiationArgs()` equals `getTemplateArgs()`; v1 records it only as `primaryActuals` and keeps the partial vector null.

For function templates, an explicit specialization emits `explicit-specializes` through its direct `FunctionDecl::getPrimaryTemplate()` relationship. An actual function-template instantiation emits `instantiates-function-template` only when `FunctionTemplateSpecializationInfo` is present, its `TemplateSpecializationKind` is one of the three instantiation kinds, the direct primary pointer is non-null, and the exact argument vector is present; the vector `FunctionTemplateSpecializationInfo::TemplateArguments` supplies `functionActuals`. Missing/inconsistent function relation data yields `supporting-declaration`, `unknown`, `missing-template-relation`, no edge, and no candidate. Clang 18.1.3's `FunctionTemplateSpecializationInfo` setter rejects `TSK_Undeclared`; dependent function-specialization records without a direct selected primary remain bounded supporting evidence and do not use the class-only `declares-specialization-of` edge. `TemplateArgumentsAsWritten` supplies `functionArgumentsAsWritten` when present, otherwise it is null. Function templates are not partially specialized in C++; overload selection is the exact `FunctionTemplateDecl*` returned by Clang. For member-function specializations, serialize the function-template edge and the independent `MemberSpecializationInfo` edge separately. The member edge has null argument vectors and its own `TemplateSpecializationKind`; never copy the function template's specialization kind onto it. Clang's documented `A<int>::f<int>` example is both a function-template specialization and a member specialization, and the two specialization kinds can differ. Class partial selection, its primary ancestor edge, function-template specialization, and member-specialization edge remain distinct. Edges with no binding, including `redeclares` and `templated-declaration`, encode the required all-null `argumentVectors` object; they never infer a binding from parameter spelling.

The evidence `counts` object has exactly `unitCount`, `entityCount`, `edgeCount`, `reasonCodeCount`, `entityKindCounts`, `edgeKindCounts`, `statusCounts`, and `reasonCounts`. Each `*Counts` object has exactly every enum key from its corresponding closed wire enum and a non-negative integer value, including explicit zeroes. Scalar totals equal array lengths; entity-kind and status maps sum to `entityCount`, edge-kind map sums to `edgeCount`, and reason map sums to total reason-code occurrences `reasonCodeCount`.

For v1, support only C++14 class/struct and function templates, primary declarations, class partial specializations, explicit specializations, explicit instantiations, observed implicit instantiations, overload sets, and packs. Formal kinds are type, integral/enum non-type, and template-template; supported actual kinds are type, integral/enum value, template name, a direct `templateParameter` only in a dependent template-template pattern, and nested pack. Before inspecting any specialization or actual, gate every primary declaration and each selected primary's direct `NonTypeTemplateParmDecl::getType()` with pinned `QualType::isIntegralOrEnumerationType()`. If any formal is pointer, reference, member-pointer, floating, class, dependent, or otherwise not integral/enum, mark the primary and every row in that same AST canonical redeclaration group `unsupported` with `unsupported-non-type-formal-type`, preserve direct physical facts/relations, and emit no candidate or resolved identity even when no actual exists. For example, `template<int *P> struct PointerNTTP;` is unsupported at its formal declaration; an observed pointer actual cannot restore support. A dependent type may appear in a partial-specialization pattern when encoded by supported `templateParameter` descriptors (for example `Box<T*>`); dependent/unresolved instantiated actuals, dependent non-type expressions, unexpanded pack expansions, and unresolved template names are tagged unsupported and cannot yield candidate/resolved identity. Class-valued/floating/pointer NTTPs and other Clang argument kinds are retained only as bounded tagged unsupported evidence. PCH, precompiled-preamble, and module inputs reject before evidence rows are published; `pch` and `module` remain reserved unsupported-kind vocabulary only. Variable templates and all their specialization forms are outside the v1 census; `variable-template` is reserved vocabulary and does not promise any row. The `concepts-requires` unsupported-kind and `unsupported-concept` reason remain reserved vocabulary, with no positive ConceptDecl row path in v1. A C++20 or concepts-enabled action is out of profile and rejects before AST extraction; an unexpected `ConceptDecl` also fails closed before row emission. Expansion requires a new policy/schema version and fixtures.

### Physical locators, hashes, and admissible semantic identity proof

All identifiers use this normative hash function: `H(domain, value) = SHA-256(ASCII(domain) || 0x00 || OracleJson.canonicalBytes(value))`. Domain strings are exact UTF-8 ASCII below. `OracleJson.canonicalBytes` sorts object keys, emits strict UTF-8, preserves array order, and uses the repository's canonical number/string encoding. No concatenation of unframed strings, pointer values, process IDs, memory addresses, host paths, or iteration order is permitted in an ID preimage.

No action ID, physical ID, pointer value, offset, column, absolute path, demangled name, or name lookup occurs in the preimage. Semantic argument vectors follow amendment 3. This is a present physical parent row with missing semantic anchor, not a missing-parent graph-closure case. Full-run reconciliation never promotes these unknown/unsupported rows to ambiguous or supported. Candidate arrays preserve Clang formal/actual order.

No other identity proof kind is accepted in v1.

No output or receipt digest is included.

The ordered AST traversal, compiler-owned owner collections, reachability checks, and per-ASTContext pointer deduplication are exactly the algorithm in amendment 1. Before any relation, typed-reference, or parent-chain closure, the initial seed set contains exactly the visited `ClassTemplateDecl`, `FunctionTemplateDecl`, `ClassTemplatePartialSpecializationDecl`, and `ClassTemplateSpecializationDecl` nodes; and each visited `FunctionDecl` for which at least one of `getPrimaryTemplate()`, `getTemplateSpecializationInfo()`, or `getMemberSpecializationInfo()` is non-null. No other `NamedDecl` is a seed merely because it is named, appears in `DeclContext::decls()`, or shares a spelling. C++20 and any concepts-enabled frontend setting reject before AST extraction; `ConceptDecl` is not seeded or serialized, and its reserved unsupported vocabulary does not create a positive evidence path. Run closure to a fixed point. Relation-walk roots are exactly the seed set above plus each `NamedDecl*` admitted through required typed-reference or parent-chain closure; each root starts at distance zero. A declaration reached only through an eligible relation edge inherits its breadth-first distance and is not reset as a new root. The eligible relation graph contains only direct source-to-target edges from the configured v1 relation APIs, normalized to the nine supported edge kinds; parent-chain steps and typed-reference admissions are not relation links. Use exact `NamedDecl*` identity within one `ASTContext`. Reject any directed cycle in the completed eligible graph by three-color depth-first cycle detection. Then breadth-first search from each root over outgoing edges, visiting a target once at its shortest distance; 32 links are admitted and a target first reachable at distance 33 fails the action. Sort roots by stable AST ordinal and outgoing neighbors by `(edgeKind,targetOrdinal)` so order cannot affect closure. Add only direct relation targets and required typed references; process newly admitted rows by the same rules. Then close every relevant declaration over both complete direct parent chains by repeatedly following `getLexicalDeclContext()` and `getDeclContext()` to the translation-unit root, retaining each intervening named context as a supporting row and applying the same direct-reference closure to it. Do not substitute one parent chain for the other; each row stores its two direct parent IDs separately. The TU root itself is represented as null. A non-named required relation target, parent context, or typed declaration reference, an unavailable direct pointer, or any required parent/target not reached by the ordered walk is a graph-closure failure and aborts the action. Optional unrelated declarations are traversed only as needed to establish this predicate and do not emit rows. Output rows sort by `(unitId, ordinal)` and edges by the wire order described above. Reversing action or worker visitation cannot change per-action ordinals or canonical output.

Location choice is fixed: semantic anchor uses spelling file plus required source line from `getSpellingLoc`; retain exact byte offset, column, and `getExpansionLoc` as separate physical/provenance fields, and record macro expansion depth. Never fall back from invalid spelling location to expansion location. Require all spelling, expansion, and macro-chain files in the authenticated closure. This allows raw rederivation to distinguish two expansions of the same macro definition: they may share a candidate but distinct canonical pointers in one AST context place them in separate groups and collision reconciliation marks them ambiguous. A macro-generated candidate is therefore allowed only when the complete spelling/expansion chain and declaration are authenticated.

Existing DWARF `sourceEntityId` remains an artifact/unit/section/CU/DIE-bound physical key; its candidate remains #1469's source candidate. Frontend physical IDs and DWARF physical IDs are never equated. The frontend record is not joined to a DIE by name, demangling, offset, physical order, candidate, location approximation, or `DW_AT_abstract_origin`. Since portable DWARF5 has no generic-pattern reference, `dwarfSourceEntityId` remains null absent a separately reviewed direct backend proof. Generic pattern evidence never creates or links an emitted-RVA denominator row in v1.

It has no arbitrary path/output callback, no partial iterator that sinks can publish, and no ambient compiler selection. Production and raw-rederivation modes call the same strict input verifier but independently invoke the frontend over raw authenticated inputs. Candidate evidence is discarded before rederivation.

## Field-level review amendments (proposal; pending independent acceptance)

This is a review draft, not a frozen contract. The five subsections below are separate review targets for frontend provenance, AST closure/identity, typed argument encoding, downstream projection, and exhaustive Clang entity/relation mapping. They replace any conflicting shorthand earlier in this proposal. Do not create implementation issues or label the design accepted until an independent reviewer checks the exact final text.

### 1. AST closure and redeclaration-group normalization

`DeclContext::decls()` is the lexical child source, but is not the whole declaration graph. For one `ASTContext`, walk from `TranslationUnitDecl` with this ordered, depth-first algorithm:

1. Visit each `DeclContext::decls()` child in the range's stored lexical order. Enter the child, finish its owned children, then advance to the next sibling.
2. On every `TemplateDecl`, visit the direct `getTemplatedDecl()` result first when non-null. Recurse into that declaration's `DeclContext` children before continuing.
3. For a `ClassTemplateDecl` canonical owner, materialize the ordered-list overload `getPartialSpecializations(SmallVectorImpl<ClassTemplatePartialSpecializationDecl*>&)` and visit that returned list, then visit `specializations()` from `spec_begin()` to `spec_end()` in the pinned Clang 18.1.3 API range order. For a `FunctionTemplateDecl` canonical owner, visit its `specializations()` range in API order. Load the owner range before traversal; v1 rejects PCH/modules and any item sourced from an external AST. These are compiler-owned edges, not entries assumed to occur in `DeclContext::decls()`.
4. For a redeclarable template owner, materialize its chain backward from `getMostRecentDecl()` through `getPreviousDecl()`, using a chain-local pointer set; the walk must terminate at null, and any repeated link aborts as a malformed cycle. Reverse the vector to obtain oldest-to-recent order. If the exact current owner pointer appears once in its own chain while it is active, skip only that one expected self-entry because it is already being visited. Do not skip any other active pointer or duplicate chain entry: those remain cycle errors. A separate per-canonical-owner set ensures each redeclaration chain is expanded once. Enumerate each canonical owner's specialization collections once as well. A child reached by two owner paths is visited only at its first event. These direct redeclaration APIs are pinned in [`DeclTemplate.h`](https://github.com/llvm/llvm-project/blob/llvmorg-18.1.3/clang/include/clang/AST/DeclTemplate.h#L949-L955) and [`FunctionTemplateDecl`](https://github.com/llvm/llvm-project/blob/llvmorg-18.1.3/clang/include/clang/AST/DeclTemplate.h#L1040-L1065).
5. On a non-template `DeclContext`, visit its `decls()` range in stored order. On a class specialization or function declaration reached through an owner collection, recurse into its declaration context where applicable.

Maintain `visitedDecls` and `activeDecls` as per-`ASTContext` pointer sets: an active revisit is a cycle and aborts the action; a completed revisit is deduplicated without another ordinal. Assign the next contiguous zero-based `eventOrdinal` to every unique `Decl*` on its first visit, including declarations outside the relevance set; only relevant declarations emit rows, so serialized row ordinals may have gaps. Pointer equality is never serialized. `getCanonicalDecl()` is used only in the separate grouping pass below, never to replace a physical visit. Direct relation targets and referenced named declarations enter the relevance set, but they are not appended from an unordered side table: if any required target is not reached by this ordered walk, abort the action with no evidence. The `ClassTemplateDecl::getPartialSpecializations()` returned order, class/function `specializations()` range order, redeclaration-chain order, and lexical `DeclContext` order are all explicit inputs to ordinals. Worker/action scheduling never participates.

After traversal, partition each unit's rows in the closed redeclaration-supported allowlist in amendment 5 by exact `Decl::getCanonicalDecl()` pointer equality within that `ASTContext`. Keep each distinct `Decl*` as a physical row and emit a `redeclares` edge for each direct `getPreviousDecl()` link supported by that allowlist. For each group, materialize declarations from canonical to most recent and normalize one shared semantic payload before calculating any candidate:

- Validate equal declaration kind, template parameter-list arity, nested template-template parameter shape, and each formal's `(depth,index,kind,isPack)` slot across all group members.
- For each formal slot, collect the effective present defaults from every redeclaration. Normalize a type default through the type algorithm below. For a non-type default, use only the direct `NonTypeTemplateParmDecl::getDefaultArgument()` expression; accept it only when it is non-dependent, `Expr::EvaluateAsInt()` succeeds without side effects, and `ASTContext::hasSameType(parameter->getType(), defaultExpr->getType())` confirms Clang's effective expression type exactly matches the declared formal type. The comparison is canonical type equality in the same `ASTContext`. Encode each successful integral default or actual as exactly `{kind:"integral",declaredType,bitWidth,isSigned,value}`. For an actual, take `declaredType` from `TemplateArgument::getIntegralType()` and its APSInt value from `getAsIntegral()`; require `hasSameType(formalType, argument.getIntegralType())`. For a default, take `declaredType` from the formal and the APValue integer from `EvaluateAsInt()`'s result via `APValue::getInt()`. Set `bitWidth = APSInt::getBitWidth()`, `isSigned = APSInt::isSigned()`, and `value` to the canonical base-10 decimal string produced by that same APSInt's `toString(...,10)`. Do not cast, resize, truncate, reinterpret, use `getSExtValue()`/`getZExtValue()`, or infer bool from width. Preserve the exact normalized integral or enum declared type, so bool and enum remain distinguishable. Pinned APIs: [`TemplateArgument`](https://github.com/llvm/llvm-project/blob/llvmorg-18.1.3/clang/include/clang/AST/TemplateBase.h#L2334-L2342), [`APValue`](https://github.com/llvm/llvm-project/blob/llvmorg-18.1.3/clang/include/clang/AST/APValue.h#L401-L428), and [`APSInt`](https://github.com/llvm/llvm-project/blob/llvmorg-18.1.3/llvm/include/llvm/ADT/APSInt.h#L31-L86). The pinned Clang 18.1.3 APIs are [`NonTypeTemplateParmDecl::getDefaultArgument()`](https://github.com/llvm/llvm-project/blob/llvmorg-18.1.3/clang/include/clang/AST/DeclTemplate.h#L1453-L1461), [`Expr::EvaluateAsInt()`](https://github.com/llvm/llvm-project/blob/llvmorg-18.1.3/clang/include/clang/AST/Expr.h#L656-L669), [`ASTContext::hasSameType()`](https://github.com/llvm/llvm-project/blob/llvmorg-18.1.3/clang/include/clang/AST/ASTContext.h#L2551-L2556), and [`TemplateArgument::getIntegralType()`](https://github.com/llvm/llvm-project/blob/llvmorg-18.1.3/clang/include/clang/AST/TemplateBase.h#L2334-L2342). Clang 18.1.3 parses this value as an expression and passes it unchanged to `ActOnNonTypeTemplateParameter` ([`ParseTemplate.cpp`](https://github.com/llvm/llvm-project/blob/llvmorg-18.1.3/clang/lib/Parse/ParseTemplate.cpp#L1065-L1072)); Sema stores that parsed expression on the declaration ([`SemaTemplate.cpp`](https://github.com/llvm/llvm-project/blob/llvmorg-18.1.3/clang/lib/Sema/SemaTemplate.cpp#L1496-L1620)). Thus `template<bool B=1>` remains int-typed in `getDefaultArgument()` and v1 rejects it; the extractor does not perform C++ template-argument conversion and fails closed when the exposed effective type is not already the formal type. Record the integral value as canonical base-10 and take its type only from the formal's `declaredType`; never infer a bool/int distinction from APInt width, signedness, or source token spelling, and never apply a producer-side conversion. For integral `TemplateArgument` actuals, require `argument.getIntegralType()` to match the aligned formal's declared type under the same `ASTContext::hasSameType` check. Any mismatch, unresolved/non-integral evaluation, or side effect makes the affected row/group `unknown` with `argument-vector-incomplete` and withholds its candidate. Normalize a template-template default from its direct `TemplateArgumentLoc`; packs use the same typed argument recursion. An inherited present default contributes its normalized value; a redeclaration with no effective default contributes no value. Deduplicate present values by canonical typed JSON bytes, then merge by exact set cardinality: zero distinct values produces JSON `null`; one distinct value produces that value; more than one distinct value is a conflict. A conflict makes the entire group `unknown`, adds `conflicting-redeclaration-default`, and withholds its candidate and resolved ID. A dependent or otherwise unrepresentable default, missing parameter slot, or incompatible signature also makes the entire group `unknown`, adds `argument-vector-incomplete`, and withholds its candidate and resolved ID. Never pick the first, last, or canonical declaration's unmerged default.
- Use the canonical declaration's authenticated source anchor, and derive the group's `canonicalName` only from that declaration's own name span. Preserve each physical row's own `nameRaw`, spelling location, and expansion location. Calculate the candidate once from the canonical anchor and merged formals/defaults plus normalized signature/specialization/semantic-argument vectors, then copy that candidate unchanged to every physical row. Never copy the canonical row's `nameRaw` or locations onto another row, or substitute a noncanonical row's `nameRaw` as the group's `canonicalName`; the complete source file remains bound through its authenticated digest.

For example, `template<class T, class U> struct Pair; template<class T, class U = int> struct Pair;` is one Clang canonical group. Both declaration rows carry the normalized formal vector `[T(default=null), U(default=type(builtin(int)))]` and therefore the same candidate. If separate TUs expose different default sets under macros, the normalized payloads produce different candidate values for the same source-anchor bucket; the full-run pass below marks that bucket ambiguous. Conflicting values never resolve through candidate equality.

#### Dependent formal defaults versus pattern and actual expressions

A non-type formal default and a `TemplateArgument::Expression` carried by a specialization are separate extraction cases. Keep the formal-default rule from amendment 1: if a direct `NonTypeTemplateParmDecl::getDefaultArgument()` is dependent or otherwise cannot be represented by the accepted integral-default path, mark the complete canonical redeclaration group `unknown`, add `argument-vector-incomplete`, set that unavailable formal's `defaultArgument` to JSON null, and withhold both candidate and resolved identity. Do not reclassify that row as `unsupported` and do not feed the expression to the actual-argument handler. For each admitted entity/edge, charge its exact marginal bytes in the generic-evidence artifact and the corresponding output-inventory delta (including field, delimiter, and byte-count-width changes; the inventory digest remains fixed-width); also enforce B's row, retained-model resident, entity, and evidence-document ceilings. C computes its own exact `B0_C` and projected-row deltas, including C-owned output-inventory entries, from the frozen observation-v3 shapes before retaining in its sink; D independently computes `B0_D` and truth-v4 deltas, including D-owned output-inventory entries, from the frozen truth shapes before retaining in its projection. For each later stage, `stageBudget = min(remainingShardBytes, remainingRunBytes)`; the separate 64-MiB standalone-evidence cap applies only to B. C/D charges use the same shared counters and do not double-charge B files. A one-over at any stage aborts that stage's complete publication; no truncated envelope or partial output is allowed.

### 3. Type and template-argument canonicalization

The supported `TemplateArgument` wire kinds are exactly `type`, `integral`, `template`, `templateParameter`, and nested `pack`, matching `supportedArgumentKinds`; `templateParameter` is used only for a direct `TemplateTemplateParmDecl` in a dependent template-template pattern, not for a concrete instantiated actual. An `integral` value has the exact shape `{kind:"integral",declaredType,bitWidth,isSigned,value}`; it uses the same direct Clang APSInt source, exact declared type, width, signedness, and canonical signed base-10 string specified above for defaults and actuals. Bool stays bool-typed, and enum values retain their exact enum descriptor and APSInt width/signedness. No conversion or width-based type inference is allowed. A `type` argument is context-sensitive: in `partialPatternArguments` it may contain a representable dependent `templateParameter` type; in instantiated `primaryActuals`, `partialDeducedArguments`, `functionActuals`, and written actuals, a dependent/unresolved type or value is `unsupported` with reason `unresolved-dependent-actual`. Thus `Box<T*>` is representable as a partial pattern, while an unresolved actual is not. `Box<int*>` is a concrete actual. A dependent non-type expression such as `N + 1`, an unexpanded pack expansion, or an unresolved template name supplied as a pattern or actual argument remains unsupported by the argument-vector path; a dependent actual uses `unresolved-dependent-actual`, while a dependent pattern expression uses `dependent-non-type-expression` and `unsupported-argument-kind`. Formal defaults are governed separately by amendment 1 and become `unknown` with `argument-vector-incomplete` when dependent or otherwise unrepresentable. Do not collapse pattern expressions, actual expressions, and defaults into one rule.

Before selecting any `TypeDescriptor` variant, normalize a `QualType` in this exact order: (1) call `getCanonicalType()`; (2) call `getSplitUnqualifiedType()` on that canonical type; (3) emit qualifiers from the returned `Qualifiers` before dispatch, in the sorted subset of `const`, `volatile`, `restrict`; if any other qualifier bit is present, mark the descriptor unsupported; (4) select the variant using only the returned canonical unqualified `Type*`; and (5) recursively apply this same sequence to child `QualType`s. Typedef/`typeof` sugar is deliberately erased before variant selection. `RecordType` backed by a `ClassTemplateSpecializationDecl` maps to `templateSpecialization` using direct Clang declaration pointers and typed template arguments; an ordinary record/enum maps to its record/enum variant. No `getAsString()` or `getSingleStepDesugaredType()` output selects identity. An unsupported qualifier/type does not fall back to the source spelling.

The array subtype mapping is an exhaustive switch over Clang 18.1.3 `ArrayType` classes: `ConstantArrayType` (`ConstantArray`) emits `{kind:"array",qualifiers,element,bound}` with `element` recursively normalized and `bound` the unsigned base-10 value of `getSize()` with no sign or leading zeroes; `IncompleteArrayType` (`IncompleteArray`) emits the same descriptor with `bound:null`. `DependentSizedArrayType` (`DependentSizedArray`) and `VariableArrayType` (`VariableArray`) emit the existing `{kind:"unsupported",clangKind,rawSha256}` type fallback with that exact Clang kind and make the containing entity `unsupported` with `unsupported-type-kind`; its `semanticAnchorCandidateId`, `resolvedSemanticIdentityId`, and `identityProofKind` are null. A null `bound` means only `IncompleteArrayType`; never map an unevaluated/dependent/variable extent to null or evaluate its expression into a bound. Any future/unmapped array type class fails closed as unsupported. The class split and constant-bound accessor are pinned in [`Type.h`](https://github.com/llvm/llvm-project/blob/llvmorg-18.1.3/clang/include/clang/AST/Type.h#L2899-L2960), with the incomplete, variable, and dependent class definitions [here](https://github.com/llvm/llvm-project/blob/llvmorg-18.1.3/clang/include/clang/AST/Type.h#L2987-L3081).

### 5. Exhaustive Clang entity kinds and actual-instantiation proof

The `entityKind` mapping above is normative and distinct from `declarationKind`; the implementation and raw rederiver must share its exact ordered direct-dynamic-type table.
