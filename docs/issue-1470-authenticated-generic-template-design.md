# Authenticated generic template evidence: design proposal

**Review artifact for the open design issue.** This document proposes a frozen, bounded contract and implementation issue set. It authorizes no producer, observation sink, truth projection, schema migration, or production qualification. The reviewed repository baseline is master commit `e5ff2c537c09eb3c048cba80a1ac53dcf00f2d6a` (merged PR #1469).

## Decision

Use a versioned Clang frontend evidence adapter as the first supported generic-template provider. It must run with the exact Clang frontend authenticated for the build action, over the authenticated source and build inputs, and record compiler-owned declaration relationships and typed template arguments. A separate raw-input validator replays that action and regenerates the evidence. The serialized frontend output is a transport artifact, never truth by virtue of its own digest.

DWARF remains the source of physical emitted-instance evidence. Frontend pattern facts and DWARF DIE facts have different physical locators and are not joined by names, mangling, candidate hashes, offsets, visitation order, or approximate coordinates. DWARF5 §2.23 explicitly says the format does not represent generic definitions, but represents each instantiation and its actual parameters; §3.3.7 and §5.7.7 make the same limitation for function and class templates. Therefore a missing frontend proof remains unknown. The GCC and Clang DWARF5 records inspected for #1469 show typed concrete instances but no generic-pattern-to-instance edge. The accepted ordinary `DW_AT_abstract_origin` edge in #1469 is inline evidence only.

The generic facts use a new `full-tree-generic-template-evidence-v1` schema/policy. They do not extend observation-v2 or truth-v3. When they are eventually projected, use additive observation-v3 and truth-v4 paths; keep observation-v1/v2 and truth-v2/v3 schemas, policies, digests, APIs, and migration vectors byte-for-byte unchanged. The generic source census remains separate from emitted-RVA score denominators.

## Evidence and feasibility

| Evidence inspected | What it supports | Limit |
| --- | --- | --- |
| Official DWARF5 §2.23, §3.3.7, §5.7.7 | Concrete template-instance DIEs and typed actual parameters can be retained. | No portable generic-definition DIE or mandatory pattern-to-instance link. |
| Merged #1469 at the reviewed baseline; source-identity producer/model and fixture report | Bounded artifact-bound DIE rows, ordered typed actuals, concrete candidate identities, unknown generic links, digest-bound scope/inventory, and existing no-partial-publication controls. | It intentionally has no source/frontend generic relation. |
| Clang LibTooling and AST API documentation | A `ClangTool` runs a `FrontendAction` with a compilation database; `FunctionDecl::getPrimaryTemplate`, `ClassTemplateSpecializationDecl::getSpecializedTemplateOrPartial`, and `getTemplateArgs` expose semantic links and typed actuals. | This is a Clang-specific interface. Its records still require authenticated inputs and raw replay. |
| Clang JSON compilation database specification | A command entry records the working directory, main source and compile command; the `arguments` vector is preferred over shell text. | A database describes a command; it does not attest that it ran or that its ambient files/environment were controlled. |
| Official GCC template-instantiation documentation | GCC may emit duplicate instances per translation unit and let the linker discard duplicates. | Emission/linker behavior is not a generic source identity relation. GCC is not a v1 frontend provider. |

The feasibility claim is deliberately narrow: Clang's semantic AST APIs offer direct template declaration pointers and ordered `TemplateArgument` values, so a bounded C++ `FrontendAction` can serialize those relationships without parsing names. PR #1469 already established that the selected C++ compiler fixtures contain the concrete-instance side of the evidence and that the DWARF side lacks the generic edge. The first implementation should exercise a pinned Clang 18.1.3 fixture profile (also used by #1469's recorded fixture matrix) and record the exact executable/runtime digests; version text alone is not authentication. No claim is made that GCC's frontend has equivalent stable API coverage, that any production build has been requalified, or that Clang and GCC ASTs are interchangeable.

Pinned Clang 18.1.3 primary API sources: [`DeclTemplate.h`](https://github.com/llvm/llvm-project/blob/llvmorg-18.1.3/clang/include/clang/AST/DeclTemplate.h#L1774-L1812) documents the selected class partial and its deduced `getTemplateInstantiationArgs()`; lines [436–612](https://github.com/llvm/llvm-project/blob/llvmorg-18.1.3/clang/include/clang/AST/DeclTemplate.h#L436-L612) distinguish `FunctionTemplateSpecializationInfo::TemplateArguments` from `TemplateArgumentsAsWritten` and document the separate `MemberSpecializationInfo` relationship/kind. [`Decl.h`](https://github.com/llvm/llvm-project/blob/llvmorg-18.1.3/clang/include/clang/AST/Decl.h#L2583-L2663) defines `FunctionDecl` member/template-specialization APIs. These APIs are the v1 profile contract, not claims that another Clang release or frontend is wire-compatible. Primary references: [DWARF5](https://dwarfstd.org/doc/DWARF5.pdf), [Clang LibTooling](https://clang.llvm.org/docs/LibTooling.html), [Clang JSON Compilation Database](https://clang.llvm.org/docs/JSONCompilationDatabase.html), [Clang `FunctionDecl`](https://clang.llvm.org/doxygen/classclang_1_1FunctionDecl.html), [Clang `ClassTemplateSpecializationDecl`](https://clang.llvm.org/doxygen/classclang_1_1ClassTemplateSpecializationDecl.html), and [GCC template instantiation](https://gcc.gnu.org/onlinedocs/gcc/Template-Instantiation.html).

## Trust inputs and authentication contract

The producer and validator accept only the following frozen input chain. Every digest below is SHA-256 over the exact canonical bytes or file bytes named; no caller-provided digest is accepted without rereading and validating its input.

1. **Source identity.** Reuse the authenticated scope, source lock, artifact manifest, source archive, source inventory, generated-file inventory/provenance, and the source-root path normalizer. Bind the Git source revision/tree identity, archive bytes, every translation-unit source blob, every generated source/header, and every opened include. Reject dirty, replaced, symlink-escaping, missing, or digest-mismatched inputs. A file outside the authenticated source/generated/toolchain closure makes that translation unit unsupported; it is not silently read from the host.
2. **Build action.** Reuse the authenticated build-record and compiler-action/compilation-database inputs. Select one unique action by authenticated `unitId` and exact argv digest. Canonicalize the argv as an ordered string array, working directory, main file, target triple, language mode, ordered `-D`/`-U` definitions, include search order, forced includes, response-file bytes, sysroot, resource directory, and PCH/module inputs. Require the compilation-database `arguments` string array; reject shell `command` entries in v1. Preserve that array byte-for-byte as UTF-8 strings and in order. Do not rewrite, append, remove, or reorder argv entries: install a Clang `FrontendAction` over the original compile action and perform no code generation. Reject preprocessor/dependency-only actions (`-E`, `-M`, `-MM`), save-temps/output-producing dependency flags (`-save-temps*`, `-MD`, `-MMD`, `-MF`, `-MT`, `-MQ`, `-MJ`, `-dependency-file`) and unauthenticated response files. Exact `-c` and `-o` entries may remain because this frontend action writes no object. Bind the exact environment allowlist below; clear every other variable. Do not treat the repo's current Clang capture-input or Ninja prestart object as execution evidence: those objects are explicitly unexecuted.
3. **Frontend identity.** Bind a registered `clang-libtooling-cxx-v1` profile to compiler executable SHA-256, Clang/LLVM runtime and loaded-library closure digests, resource-header manifest digest, adapter source revision, adapter executable digest, adapter ABI/API version, target triple, and the existing toolchain reproduction/profile digest. Resolve the compiler by its authenticated absolute path; `PATH` cannot select or replace it. `--version` output is diagnostic only. Reject an unregistered profile, a substituted executable/library, an implicit host `PATH` lookup, or a compiler different from the compiler authenticated for the build action. For v1, GCC, MSVC, clang-cl, and a Clang frontend substituted for a GCC-built artifact have capability `unsupported`, not a guessed fallback.
4. **Preprocessor/build context.** There is no argv adjustment in v1. The execution receipt records the exact unchanged frontend argv, cwd, environment, actual ordered include/dependency closure with per-file hashes, generated inputs, and a deterministic preprocessor-context digest over active macros, include resolution, language/target options, and authenticated PCH/module inputs. The full argv/environment/action digest binds every option, including optimization and debug flags. V1 rejects PCH/modules; accepting them requires a later policy/schema version that authenticates their full artifacts and import closure. The full action and runner context are provenance, not part of the semantic anchor preimage; the anchor includes source revision/blob and complete typed declaration/argument facts. Therefore `-O0` and `-O2` may yield the same candidate when that tuple matches, while their action and physical IDs differ. A macro/configuration change changes the authenticated semantic-context digest and action/physical IDs; candidate equality still never merges or links rows.
5. **Executed frontend receipt.** The bounded isolated runner records action success, the authenticated compiler/profile/action digests, dependency digests observed by the frontend, preprocessor-context digest, output byte count, exit status, resource usage, and a deterministic action ID. Once canonical evidence output is complete, an enclosing authenticated output inventory binds its SHA-256 and byte count. A planned command, compile database row, stderr/stdout text, compiler version string, or producer-authored JSON is not an execution receipt. On any failed command, changed input, missing include, resource termination, or receipt mismatch, publish no partial facts.

The current Kotlin trust chain is a viable base: `FullTreeScopeControl` snapshots and validates the exact scope/source-lock/manifest/build-record bindings; `FullTreeSourceInventoryControl` checks the locked source archive and per-file inventory; `FullTreeFunctionObservationProducer.authenticateShardInputs` binds inventory and rich-artifact bytes; and the #1469 producer enforces authenticated per-shard and no-partial-output budgets. The gap is explicit: current `FullTreeClangCaptureInputControl` and Ninja prestart represent validated but unexecuted inputs. The first implementation issue must add a frontend execution receipt instead of upgrading either plan object by implication.

## Schema and identities

### Frozen wire and digest contracts

Four independently registered contracts freeze wire, policy, and compatibility versions. All objects use `additionalProperties: false`; every listed member is required, and nullable members are present as JSON `null`. Empty arrays/objects, null, zero, and omitted members are distinct. Hashes are lowercase 64-character SHA-256 hex. JSON integers are non-negative and at most signed 64-bit; arbitrary-width C++ integral values are canonical base-10 strings. Strings use strict UTF-8 with no Unicode normalization. Arrays preserve declared order unless this section specifies canonical sorting. `schemaVersion` is independent of the `vN` registry name; truth-v4's schema name is `...v4` while its new wire `schemaVersion` is 3, advancing the #1468 wire version 2.

| Contract | Registry/schema name | Wire version | Policy id/version | Configuration digest input |
| --- | --- | ---: | --- | --- |
| Frontend receipt/provenance | `full-tree-generic-template-frontend-v1` | `schemaVersion: 1` | `full-tree-generic-template-frontend` / 1 | `OracleSchemas.configurationSha256([name], canonicalPolicy)`; canonical policy JSON followed by exact bundled schema bytes. |
| Generic evidence | `full-tree-generic-template-evidence-v1` | `schemaVersion: 1` | `full-tree-generic-template-evidence` / 1 | Same rule, evidence schema and evidence policy only. |
| Function observation | `full-tree-function-observations-v3` | `schemaVersion: 3` | `full-tree-function-observations` / 5 | Same rule, new v3 schema/policy only; v1/v2 schema and policy bytes stay frozen. |
| Function truth shard/index | `full-tree-function-truth-v4`, `full-tree-function-truth-index-v4` | `schemaVersion: 3` in each | `full-tree-function-truth` / 4 | `OracleSchemas.configurationSha256(["full-tree-function-exclusions", "full-tree-function-truth-v4", "full-tree-function-truth-index-v4"], canonicalPolicy)`, in exactly that order. |

For frontend/evidence policies, the canonical policy JSON has exactly `id`, `version`, `argvPolicy`, `environmentAllowlist`, `supportedEntityKinds`, `supportedTypeKinds`, `supportedArgumentKinds`, `unsupportedKinds`, and `limits`. `argvPolicy` is `compilation-database-arguments-unchanged-v1`; each array is sorted unique and exactly the closed enums/allowlist written below; `limits` is exactly the ceilings in the bounds table. The observation-v3 policy JSON is the accepted #1467 v2 policy JSON with no existing member changed or removed, plus exactly `genericTemplates: "separate-nonscoreable-evidence-v1"`; its `id` is `full-tree-function-observations` and `version` is 5 (up from 4). The truth-v4 policy JSON is the accepted #1468 truth-v3 policy JSON with no existing member changed or removed, plus exactly `genericTemplates: "raw-rederived-nonscoreable-census-v1"`; its `id` is `full-tree-function-truth` and `version` is 4 (up from 3). No policy object contains source/build/artifact hashes, machine paths, run IDs, or compiler versions; those are envelope bindings. The configuration digest is computed once exact schema bytes exist; no placeholder/fabricated digest is accepted.

#### Frontend provenance envelope

The document has exactly `schemaVersion`, `policyId`, `policyVersion`, `configurationSha256`, `bindings`, `units`, and `counts`. `bindings` requires exactly `scopeSha256`, `sourceLockSha256`, `artifactManifestSha256`, `buildRecordSha256`, `sourceArchiveSha256`, `sourceInventorySha256`, `generatedInventorySha256`, `richArtifactSha256`, `richInventorySha256`, `compilationDatabaseSha256`, and `frontendProfileSha256`. `units` is ordered by `(unitId, actionId)`. Every unit has exactly `unitId`, `actionId`, `sourcePath`, `sourceFileSha256`, `argv`, `argvSha256`, `cwd`, `environment`, `environmentSha256`, `dependencySetSha256`, `dependencies`, `semanticContextSha256`, `frontendProfileSha256`, `adapterSha256`, `receiptSha256`, `exitCode`, `cpuMillis`, `wallMillis`, `peakBytes`, and `outputBytes`. `sourcePath` is a closure-relative `source/<repo-relative>` or `generated/<inventory-relative>` path. `argv` is the exact compile-database `arguments` array, unchanged. `dependencies` is an ordered array of exactly `{path, sha256, role}`, where `role` is `main-source`, `source`, `generated`, `header`, `response-file`, `resource-header`, `pch`, or `module`; response-file bytes are read and authenticated before Clang expands them, and v1 rejects `pch` and `module`. `environment` is a sorted object of allowlisted string values only. Receipt hash covers all unit fields except `receiptSha256` itself. Successful receipt requires `exitCode: 0` and completed bound/resource accounting. `counts` has exactly `unitCount`, `dependencyCount`, and `outputBytes`.

The v1 environment allowlist is exactly `PATH`, `HOME`, `TMPDIR`, `LANG`, `LC_ALL`, `SOURCE_DATE_EPOCH`, `CPATH`, `C_INCLUDE_PATH`, `CPLUS_INCLUDE_PATH`, `OBJC_INCLUDE_PATH`, `OBJCPLUS_INCLUDE_PATH`, and `SDKROOT`. Absent variables are omitted, not null. `PATH` entries are absolute paths under the authenticated toolchain root. `HOME` and `TMPDIR` are fixed virtual paths `/__decomp/home` and `/__decomp/tmp`, mounted as empty contained per-action directories; both their virtual names and empty contents are bound. `PATH` uses authenticated virtual toolchain paths, and `SDKROOT` uses a profile-relative virtual path. No host path appears in the environment object. Include-path and SDK variables are accepted only when their resolved files are in the authenticated dependency closure. Any non-allowlisted variable or unreadable environment input rejects the action.

#### Generic-evidence envelope and rows

The evidence document has exactly `schemaVersion`, `provider`, `policyId`, `policyVersion`, `configurationSha256`, `bindings`, `units`, `entities`, `edges`, and `counts`. `provider` is exactly `clang-libtooling-cxx-v1`. `bindings` has exactly the eleven provenance digest members above plus `frontendReceiptSha256` and `dwarfArtifactSha256`. Each evidence `unit` has exactly `unitId`, `actionId`, `sourcePath`, `sourceFileSha256`, `argvSha256`, `cwd`, `environmentSha256`, `semanticContextSha256`, `frontendProfileSha256`, `dependencySetSha256`, and `receiptSha256`; the set and action IDs must equal the authenticated receipt. Entity rows sort by `(unitId, ordinal)` and require exactly `physicalId`, `unitId`, `ordinal`, `entityKind`, `declarationKind`, `nameRaw`, `spellingLocation`, `expansionLocation`, `lexicalParentPhysicalId`, `semanticParentPhysicalId`, `status`, `reasonCodes`, `formals`, `signature`, `specializationKind`, `semanticAnchorCandidateId`, `resolvedSemanticIdentityId`, and `identityProofKind`. Nullable-but-required fields are `nameRaw`, both locations, `lexicalParentPhysicalId`, `semanticParentPhysicalId`, `signature`, `specializationKind`, both IDs, and `identityProofKind`. `entityKind` is `primary-template`, `partial-specialization`, `explicit-specialization`, `concrete-instantiation`, or `supporting-declaration`; `declarationKind` is `class`, `function`, `class-template`, `function-template`, `record`, `enum`, or `other-named`. `status` is `supported`, `unsupported`, `unknown`, or `ambiguous`; `reasonCodes` is a sorted, unique array from this closed enum: `argument-vector-incomplete`, `ambiguous-template-selection`, `cross-unit-target`, `dependent-argument`, `invalid-source-location`, `limit-exceeded`, `missing-source-anchor`, `missing-template-relation`, `unauthenticated-input`, `unsupported-argument-kind`, `unsupported-compiler-profile`, `unsupported-concept`, `unsupported-language-mode`, `unsupported-module`, `unsupported-pch`, `unsupported-template-kind`, and `unsupported-type-kind`.

A location is exactly `{path, byteOffset, line, column, macroExpansionDepth}`. `line`/`column` use physical source coordinates from the spelling file and byte offset (`SourceManager` file line/column getters); presumed `#line` coordinates never replace them. The raw `nameRaw` field is the exact UTF-8 token spelling from the authenticated source byte span; do not use demangled/qualified/pretty-printed names. If a declaration has no recoverable source token spelling, encode null and withhold a candidate. `path` is a canonical closure-relative name with one root prefix: `source/<repo-relative>`, `generated/<inventory-relative>`, `toolchain/<profile-relative>`, or `build/<authenticated-relative>`; it never contains an absolute path or `..`. Offset is zero-based in original authenticated file bytes; line/column are one-based diagnostics; macro depth is zero for a non-macro location. Both spelling and expansion locations are always present as an object or null. Semantic anchors use `SourceManager::getSpellingLoc` mapped to authenticated closure-relative path and required source line; byte offset is retained but excluded from the semantic candidate. `getExpansionLoc` is retained as provenance and may locate use/point-of-instantiation facts; it never substitutes for the spelling anchor. The spelling file and every macro expansion source must be in the authenticated dependency closure. Invalid, scratch-buffer, or unauthenticated locations yield null semantic IDs and a reason; no file-name/name fallback is permitted.

Each entity parent ID is a direct pointer reference from `getLexicalDeclContext()` or `getDeclContext()` respectively; both parent chains are retained separately, point to same-unit supporting/template rows, and are null only at the translation-unit root. Each formal has exactly `depth`, `index`, `kind`, `isPack`, `declaredType`, `defaultArgument`, and `nestedFormals`. `kind` is `type`, `nonType`, or `templateTemplate`. `declaredType` is null for type/template-template formals and a `TypeDescriptor` for non-type formals. `defaultArgument` is null or a tagged `TemplateArgument`. `nestedFormals` is empty for type/non-type formals and holds the ordered nested formal list for template-template formals. Signature is null when not applicable, otherwise exactly `{result, parameters, variadic, memberCvQualifiers, memberRefQualifier, callingConvention, exceptionSpecification}`; `exceptionSpecification` uses the same required `{kind,types}` object defined for function types. Qualifier arrays use only `const`, `volatile`, `restrict`, `atomic`, sorted and unique; member ref qualifier is null, `lvalue`, or `rvalue`. `variadic` is a JSON boolean. Calling convention is one of `cdecl`, `stdcall`, `fastcall`, `thiscall`, `vectorcall`, `aapcs`, `win64`, `sysv64`, `preserve-most`, or `preserve-all`; any other target calling convention makes that signature unsupported. Parameter arrays preserve ordinal order.

`TypeDescriptor` is a closed tagged object. Supported variants and exact fields are: `builtin` (`kind,name,qualifiers`, where `name` is the Clang 18.1.3 `BuiltinType::Kind` enumerator, never `QualType::getAsString()`); `record` or `enum` (`kind,qualifiers,declPhysicalId`); `pointer` (`kind,qualifiers,pointee`); `lvalueReference` or `rvalueReference` (`kind,qualifiers,referent`); `array` (`kind,qualifiers,element,bound`, where bound is null or canonical decimal); `function` (`kind,qualifiers,result,parameters,variadic,memberCvQualifiers,memberRefQualifier,callingConvention,exceptionSpecification`); `templateParameter` (`kind,qualifiers,depth,index`); and `templateSpecialization` (`kind,qualifiers,specializationPhysicalId,templatePhysicalId,arguments`). Every descriptor variant has a required `qualifiers` array (empty where C++ does not permit qualifiers); its closed values are `const`, `volatile`, `restrict`, and `atomic`, sorted and unique. `memberCvQualifiers` uses only `const` and `volatile`. `exceptionSpecification` is exactly `{kind,types}`, where kind is `none`, `noexcept-true`, `noexcept-false`, or `dynamic`; `types` is empty except for supported C++14 dynamic exception specifications and then contains the ordered typed exception list. Dependent/unresolved exception specifications are unsupported. Every variant has exactly the listed fields. For `templateSpecialization`, `specializationPhysicalId` points to the exact same-unit `ClassTemplateSpecializationDecl` fact and `templatePhysicalId` to its primary `ClassTemplateDecl`; ordered actuals are the specialization's direct `getTemplateArgs()` vector. The selected primary/partial disposition is read from that specialization entity's typed edge, not inferred from the type spelling. All declaration references resolve to same-unit `supporting-declaration` or template entities via direct Clang AST pointers. Supported `TemplateArgument` variants are exactly: `type` (`kind,type`); `integral` (`kind,type,isSigned,bitWidth,value`); `template` (`kind,templatePhysicalId`); and `pack` (`kind,elements`), recursively preserving ordinals. Each has exactly the listed fields. Other Clang argument/type forms use `{kind:"unsupported", clangKind, rawSha256}` and force row status `unsupported` with null candidate and resolved ID. No pretty-printed type is a semantic substitute.

#### Edge union and Clang specialization mappings

`edges` sort by `(unitId, sourcePhysicalId, kind, targetPhysicalId, canonicalRelationPayloadBytes)`, where the payload is `OracleJson.canonicalBytes({proofKind,specializationKind,argumentVectors})` compared unsigned bytewise. Each edge has exactly `unitId`, `sourcePhysicalId`, `targetPhysicalId`, `kind`, `proofKind`, `specializationKind`, and `argumentVectors`; `specializationKind` is nullable. Endpoints resolve to same-unit entities. Closed `kind` values are `templated-declaration`, `redeclares`, `specializes-primary`, `instantiates-primary`, `instantiates-partial`, `instantiates-function-template`, `member-specialization`, and `explicit-specializes`. `proofKind` is one exact API trace: `ClassTemplateSpecializationDecl.getSpecializedTemplateOrPartial`, `ClassTemplateSpecializationDecl.getSpecializedTemplate`, `FunctionDecl.getPrimaryTemplate`, `FunctionDecl.getPreviousDecl`, `RecordDecl.getPreviousDecl`, `ClassTemplateSpecializationDecl.getPreviousDecl`, `ClassTemplatePartialSpecializationDecl.getPreviousDecl`, `ClassTemplateDecl.getPreviousDecl`, `FunctionTemplateDecl.getPreviousDecl`, `FunctionDecl.getMemberSpecializationInfo->MemberSpecializationInfo.getInstantiatedFrom`, `ClassTemplateDecl.getTemplatedDecl`, or `FunctionTemplateDecl.getTemplatedDecl`. The direct edge receiver and returned declaration pointer are checked under the Clang 18.1.3 profile. Class/function argument-vector fields are independently read from the exact getters specified below: `getTemplateArgs()` / `getTemplateInstantiationArgs()` for class templates, and `getTemplateSpecializationArgs()` / `getTemplateSpecializationArgsAsWritten()` for functions (equivalent to `FunctionTemplateSpecializationInfo::TemplateArguments` / `TemplateArgumentsAsWritten`). `Decl.getCanonicalDecl()` is reserved for same-ASTContext identity grouping, never used to invent an edge. `argumentVectors` always has exactly five required nullable keys: `primaryActuals`, `partialDeducedArguments`, `partialPatternArguments`, `functionActuals`, and `functionArgumentsAsWritten`. For no-binding edges (`templated-declaration`, `redeclares`, `member-specialization`) all five are null. Other vectors are populated only as follows.

The vector matrix is exhaustive: `templated-declaration` and `redeclares` require all vectors null and null specialization kind; `specializes-primary` requires only `partialPatternArguments`; `instantiates-primary` requires only `primaryActuals`; `instantiates-partial` requires `primaryActuals` plus `partialDeducedArguments`; `instantiates-function-template` requires `functionActuals` and nullable `functionArgumentsAsWritten`; `member-specialization` requires all vectors null and a non-null member specialization kind; `explicit-specializes` requires `primaryActuals` for class specializations or `functionActuals` plus nullable written arguments for function specializations. Every other vector is null. The specialization kind is exactly one of `undeclared`, `implicit-instantiation`, `explicit-specialization`, `explicit-instantiation-declaration`, or `explicit-instantiation-definition`, copied from the matching Clang `TemplateSpecializationKind`; it is null only for `templated-declaration` and `redeclares`.

For `ClassTemplateSpecializationDecl`, `getTemplateArgs()` is `primaryActuals`; the edge target is the exact pointer returned by `getSpecializedTemplateOrPartial()`. If the target is a primary template, `partialDeducedArguments` is null. If the target is a selected partial, `getTemplateInstantiationArgs()` is the separate `partialDeducedArguments` vector, deduced for the partial's own formals. The partial declaration's own `specializes-primary` edge carries `partialPatternArguments` from `ClassTemplatePartialSpecializationDecl::getTemplateArgs()` in the normalized typed pattern order; `getTemplateArgsAsWritten()` source span/raw bytes remain independently authenticated evidence. Example: `template<class T> struct Box; template<class T> struct Box<T*> {}; Box<int*> value;` yields `primaryActuals = [type(pointer(int))]`, selected target `Box<T*>`, and `partialDeducedArguments = [type(int)]`. Encoding both as `[type(int*)]`, swapping them, or deriving either from rendered names fails rederivation. For a primary-only class instantiation Clang specifies that `getTemplateInstantiationArgs()` equals `getTemplateArgs()`; v1 records it only as `primaryActuals` and keeps the partial vector null.

For function templates, `FunctionTemplateSpecializationInfo::TemplateArguments` supplies `functionActuals`; `TemplateArgumentsAsWritten` supplies `functionArgumentsAsWritten` when present, otherwise it is null. Function templates are not partially specialized in C++; overload selection is the exact `FunctionTemplateDecl*` returned by Clang. For member-function specializations, serialize the function-template edge and the independent `MemberSpecializationInfo` edge separately. The member edge has null argument vectors and its own `TemplateSpecializationKind`; never copy the function template's specialization kind onto it. Clang's documented `A<int>::f<int>` example is both a function-template specialization and a member specialization, and the two specialization kinds can differ. Class partial selection, its primary ancestor edge, function-template specialization, and member-specialization edge remain distinct. Edges with no binding, including `redeclares` and `templated-declaration`, encode the required all-null argumentVectors object; they never infer a binding from parameter spelling.

The evidence `counts` object has exactly `unitCount`, `entityCount`, `edgeCount`, `reasonCodeCount`, `entityKindCounts`, `edgeKindCounts`, `statusCounts`, and `reasonCounts`. Each `*Counts` object has exactly every enum key from its corresponding closed wire enum and a non-negative integer value, including explicit zeroes. Scalar totals equal array lengths; entity-kind and status maps sum to `entityCount`, edge-kind map sums to `edgeCount`, and reason map sums to total reason-code occurrences `reasonCodeCount`.

For v1, support only C++14 class/struct and function templates, primary declarations, class partial specializations, explicit specializations, explicit instantiations, observed implicit instantiations, overload sets, and packs. Formal kinds are type, integral/enum non-type, and template-template; supported actual kinds are type, integral/enum value, template name, and nested pack. Unsupported variable templates, class-valued/floating/pointer NTTPs, dependent/unresolved arguments, concepts/requires, modules, unauthenticated PCH, and other Clang argument kinds are retained only as bounded tagged unsupported evidence and cannot yield candidate/resolved identity. Expansion requires a new policy/schema version and fixtures.

### Physical locators, hashes, and admissible semantic identity proof

All identifiers use this normative hash function: `H(domain, value) = SHA-256(ASCII(domain) || 0x00 || OracleJson.canonicalBytes(value))`. Domain strings are exact UTF-8 ASCII below. `OracleJson.canonicalBytes` sorts object keys, emits strict UTF-8, preserves array order, and uses the repository's canonical number/string encoding. No concatenation of unframed strings, pointer values, process IDs, memory addresses, host paths, or iteration order is permitted in an ID preimage.

- `actionId = H("decomp-thing/generic-template/action/v1", {"scopeSha256", "sourceLockSha256", "artifactManifestSha256", "buildRecordSha256", "sourceArchiveSha256", "sourceInventorySha256", "generatedInventorySha256", "richArtifactSha256", "richInventorySha256", "compilationDatabaseSha256", "unitId", "sourceFileSha256", "argvSha256", "cwd", "environmentSha256", "dependencySetSha256", "semanticContextSha256", "frontendProfileSha256", "adapterSha256"})`. The JSON object has exactly those 19 keys and their exact values from validated controls/unit receipt; dependencies are represented by `dependencySetSha256`, computed from the canonical ordered `{path,sha256,role}` array. This excludes output and receipt digests, so there is no cycle.
- `physicalId = H("decomp-thing/generic-template/physical/v1", {"actionId": actionId, "eventOrdinal": ordinal, "entityKind": entityKind})`. Ordinal is an unsigned logical AST-event index encoded as a canonical JSON integer; entity kind is one of the closed wire enums. This is a per-action physical frontend locator, not a source identity.
- `semanticAnchorCandidateId = H("decomp-thing/generic-template/candidate/v1", {"sourceRevision", "sourcePath", "sourceFileSha256", "canonicalDeclarationLine", "languageMode", "lexicalParentAnchors", "semanticParentAnchors", "entityKind", "declarationKind", "rawName", "formals", "signature", "specializationKind", "argumentVectors"})`. `sourceRevision` is the authenticated source-tree/revision identity. `canonicalDeclarationLine` is the required one-based source line of Clang's canonical declaration. Parent anchors are ordered root-to-leaf direct AST parent descriptors `{sourcePath,sourceFileSha256,line,declarationKind,rawName}`. In formal/signature/argument descriptors, each referenced `declPhysicalId` is replaced in the candidate preimage by the referenced declaration's equivalent source anchor object obtained from the already held AST pointer. This remapping is performed by pointer lookup, never name lookup. If a direct referenced declaration has no authenticated spelling anchor, the candidate is null. The hash object values are exact: `sourceRevision` from the authenticated tree control; `sourcePath`, file digest, and required line from the canonical declaration spelling location; `languageMode` from the captured standard/extension options; `lexicalParentAnchors` and `semanticParentAnchors` from the separate direct Clang parent-pointer chains root-to-leaf; and kind, raw name, formals, signature, specialization kind, and the five-key `argumentVectors` from that AST node and its direct API edges. Patterns use all-null argument vectors except a partial pattern's `partialPatternArguments`; concrete class-partial instances include both `primaryActuals` and `partialDeducedArguments`; function instances include `functionActuals` and optional written args. Arrays remain in Clang formal/actual order. Action/preprocessor context and machine-specific invocation are bound by the envelope/action receipt and deliberately excluded from this source-semantic candidate. Raw columns, byte offsets, and absolute paths are diagnostic/physical provenance, not candidate fields. This follows #1467's optional-column rule: line is required, columns/offsets are retained but excluded; same-line collisions remain separate and are resolved only by direct proof plus complete-run collision reconciliation.
- `resolvedSemanticIdentityId = H("decomp-thing/generic-template/resolved/v1", {"candidateId": candidate, "identityProofKind": "clang-canonical-declaration-group-in-one-ASTContext-v1"})`. It is non-null only after raw rederivation and whole-run collision reconciliation. The proof is direct equality of Clang `Decl::getCanonicalDecl()` pointers in the same `ASTContext`; this admits only members of that exact redeclaration/canonical-specialization group. Rows are equivalent only when those API pointers are equal. A pattern-to-instance API edge proves that relation, never that pattern and instance are the same identity. Pointer values are temporary process-local comparison aids and are never serialized or hashed. The complete candidate bucket must contain exactly one such canonical group across the authenticated run; another TU/group with the same candidate makes every row in the bucket `ambiguous` and resolved ID null. Cross-TU same-header declarations are not deduplicated even when bytes, path, candidate, or debug coordinates match. Unsupported/incomplete evidence has null candidate and resolved IDs; `identityProofKind` is null with a null resolved ID. No other identity proof kind is accepted in v1.

`argvSha256` is SHA-256 of `OracleJson.canonicalBytes(argv)`; `environmentSha256` is SHA-256 of canonical environment JSON; `dependencySetSha256` is SHA-256 of the canonical ordered `{path,sha256,role}` array. `frontendProfileSha256` is `H("decomp-thing/generic-template/frontend-profile/v1", {compilerSha256, runtimeLibraryDigests, resourceHeaderManifestSha256, adapterSourceRevision, adapterSha256, adapterApiVersion, targetTriple, toolchainProfileSha256})`, with exactly those keys and `runtimeLibraryDigests` sorted by normalized path. `semanticContextSha256` is `H("decomp-thing/generic-template/semantic-context/v1", {languageOptions, targetTriple, predefinedMacroDigest, macroEvents, includeEvents, pchModuleDigests})`. `languageOptions` is exactly `{standard, standardVersion, extensions, modules, exceptions, rtti, charSignedness, wcharWidth}`; `predefinedMacroDigest` is `H("decomp-thing/generic-template/predefines/v1", rows)` where rows are sorted by macro name and each row is exactly `{name,tokenSha256}` for the initial active macro map. Each `tokenSha256` is `H("decomp-thing/generic-template/macro-tokens/v1", tokens)`, where `tokens` is the ordered array of exact `{kind,spelling}` preprocessing tokens from the macro replacement list (empty for `undef`). Each ordered macro event is exactly `{kind,name,tokenSha256,origin,path,line,byteOffset,includeDepth}`, with kind `define` or `undef`; origin is `source`, `command-line`, or `builtin`. `path`, `line`, and `byteOffset` are all null for command-line/builtin definitions and otherwise use authenticated closure-relative source coordinates. Each include event is exactly `{kind,requested,resolvedPath,resolvedSha256,line,byteOffset,includeDepth}`, with kind `include`, `include-next`, or `import`. Paths use the closure-relative form above; macro/include events preserve frontend callback order and exact names/tokens or requested/resolved paths plus file hashes. V1 requires an empty PCH/module digest array. The adapter records this transcript from authenticated `Preprocessor` callbacks and target/language options; it does not launch a second altered compiler invocation. `receiptSha256` is `H("decomp-thing/generic-template/receipt/v1", unitObjectWithoutReceiptSha256)`.

A frontend action receipt hashes only input identity, successful execution status, observed dependency closure, and bounded resource/output-byte counts. It intentionally does not contain the hash of its own evidence output. After canonical evidence bytes are complete, the enclosing authenticated output inventory/publication receipt stores `genericEvidenceArtifactSha256` and byte count. That external post-output binding avoids a self-referential digest; raw rederivation regenerates canonical bytes and compares the external digest.

The `actionId` preimage member values are exact: scope, source-lock, artifact-manifest, build-record, source-archive, source-inventory, generated-inventory, rich-artifact, rich-inventory, and compilation-database digests come from validated controls; `unitId`, `sourceFileSha256`, argv digest, exact cwd, environment digest, ordered dependency digest, semantic-context digest, frontend-profile digest, and adapter digest come from the selected unit and receipt. The preimage has exactly the 19 keys named in the `actionId` definition above and no output/receipt digest.

Each action builds a relevance set from the selected generic declarations, their direct API relation targets, direct referenced `NamedDecl` types/templates, and lexical-parent declaration chain. It then produces the event stream by starting at `TranslationUnitDecl` and recursively visiting each `DeclContext::decls()` child in Clang stored lexical order, depth-first; assign the next zero-based ordinal when a relevant entity is emitted. Visit a declaration's child declaration contexts before the next sibling. Use this ordered traversal only; never assign ordinals by iterating pointer-keyed maps, folding sets, hash maps, or worker completion order. A `Decl*` is emitted once at its first event; pointer equality is only a per-`ASTContext` dedup aid. Same spelling/expansion locations remain distinct by AST visit ordinal. If any relevant pointer is not reachable in that same-unit walk, the related row/edge/type is unsupported rather than appended in map order. Output rows then sort by `(unitId, ordinal)` and edges by the wire order described above. Reversing action or worker visitation cannot change per-action ordinals or canonical output.

Location choice is fixed: semantic anchor uses spelling file plus required source line from `getSpellingLoc`; retain exact byte offset, column, and `getExpansionLoc` as separate physical/provenance fields, and record macro expansion depth. Never fall back from invalid spelling location to expansion location. Require all spelling, expansion, and macro-chain files in the authenticated closure. This allows raw rederivation to distinguish two expansions of the same macro definition: they may share a candidate but distinct canonical pointers in one AST context place them in separate groups and collision reconciliation marks them ambiguous. A macro-generated candidate is therefore allowed only when the complete spelling/expansion chain and declaration are authenticated.

Existing DWARF `sourceEntityId` remains an artifact/unit/section/CU/DIE-bound physical key; its candidate remains #1469's source candidate. Frontend physical IDs and DWARF physical IDs are never equated. The frontend record is not joined to a DIE by name, demangling, offset, physical order, candidate, location approximation, or `DW_AT_abstract_origin`. Since portable DWARF5 has no generic-pattern reference, `dwarfSourceEntityId` remains null absent a separately reviewed direct backend proof. Generic pattern evidence never creates or links an emitted-RVA denominator row in v1.

## Bounds, failure behavior, and deterministic interface

The action interface consumes only validated typed registries and an authenticated immutable artifact root; it returns one immutable complete v1 result or a typed failure. It has no arbitrary path/output callback, no partial iterator that sinks can publish, and no ambient compiler selection. Production and raw-rederivation modes call the same strict input verifier but independently invoke the frontend over raw authenticated inputs. Candidate evidence is discarded before rederivation.

Use the smaller of caller limits and authenticated scope limits; do not raise any existing global, per-shard, DIE, function, parameter, serialization, or working-set bound. Freeze these additional ceilings in policy v1:

| Item | Hard ceiling | Admission and failure |
| --- | ---: | --- |
| Actions | Authenticated `wholeRun.compilationUnits` and existing worker ceiling | Reject before starting actions if the set exceeds either. |
| Evidence entities | Authenticated `perShard.entities` | Charge before retention; one over aborts the complete shard. |
| Formals or actual arguments per entity | 1,024 | Count nested pack leaves and nodes before retention; one over aborts. |
| Relationship edges per entity and relation walk | 32 each | Existing ceiling; one-over edge or chain aborts before publication. |
| Type descriptor depth / nodes per descriptor | 64 / 4,096 | Reject unsupported depth or node count; do not truncate. |
| One canonical entity row | `min(authenticated per-shard output bytes, 64 MiB)` | Reserve 2x row bytes for scratch before serialization. |
| Aggregate retained generic model | `min(perShard.maximumResidentBytes / 4, 3 × perShard output bytes, 64 MiB)` | Charge each retained contribution as 3x canonical bytes + 64 bytes, in the same source-identity working-set model; share, do not add to, the authenticated shard budget. |
| Aggregate evidence/observation output | Sum of all generic-evidence and observation outputs must stay within existing authenticated per-shard output bytes; standalone generic evidence is additionally capped at 64 MiB | Preflight the aggregate exact projected bytes; no partial file or receipt on one-over. |
| Frontend process | Existing selected contained-runner CPU, wall-time, memory, PID, FD, and output ceilings | Any process/resource failure aborts; no fallback to an unconstrained host compiler. |

If source locations, argument shapes, or types are syntactically readable but incomplete or conflicting, preserve bounded raw evidence and use `unknown`, `ambiguous`, or `unsupported`, with deterministic reason codes. If a declaration boundary, typed AST relation, or dependency closure cannot be established, abort that action. If a hard bound is exceeded, abort the shard before publishing any fact set. Exact-bound and one-over-bound behavior must be tested with lowered test limits for every row above.
