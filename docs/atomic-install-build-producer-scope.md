# Atomic installation build-producer scope

The ACP build producer uses the `cooperative-build-producer-v1` contract. This is an explicit revision of the later proposed hostile-namespace custody contract for this build producer, following the original cooperative installer design and the scope review of 2026-11-05. It does not establish qualification for issues #1834 or #1842.

The controller, JVM, operating system, pinned compiler/probe, and stable repository/build namespace are trusted. Supported producers share a stable, never-unlinked lock for the canonical output; scratch configuration must not create independent lock domains. Build outputs remain exclusively owned through compilation, validation, publication, cleanup, and downstream consumption. Independent simultaneous builds use disjoint outputs. The installation lock does not protect prerequisite compilation.

Arbitrary same-user namespace exchange, malicious descendants, ptrace, hostile writable aliases, and external cleanup during production are outside this contract. The three retained ancestor-exchange, lock-substitution, and foreign-cleanup reproductions remain **RED and unresolved under their original stronger contract**. They are not passing tests and must not be relabelled as fixes. No privileged custody service is introduced or approved.

Fresh compilation remains mandatory on every preparation and replay. Successful validated candidates may preserve an existing output only on complete byte equality and the exact required mode, without modifying its inode or timestamps. Changed output requires forced, same-filesystem atomic replacement and final validation. Compiler, probe, force, move, cleanup, cancellation, and ordinary cooperating-writer failures remain in scope. Every acquired resource must be released, every close attempted, and the original failure preserved with later cleanup failures suppressed.

Producer receipts must use schema version 2 and explicitly carry `publicationScope="cooperative-build-producer-v1"` and `bindingEvidence="stable-namespace-path-observations-v1"`. The immutable replay plan must carry the same constants. These receipts describe observed build consistency; they do not authenticate an opened executable inode, a hostile compiler, or runtime authorization. Old receipts are not upgraded. Unknown assurance fields and missing or incorrect scope declarations must be rejected.

Strict source, compiler, recipe, prepared-input, and protected-installation equality remains required, including bytes, mode, device, and inode where specified. Replay retains exactly the two existing exclusions, `:buildAnalysisIoHelper` and `:buildLlvmBehaviorHelper`; ACP and frontend work remain fresh. No restored outputs, relaxed identity comparison, added exclusions, or retries until stable are allowed.

ACP runtime manifest/digest validation, retained descriptors, mount and process identity checks, isolation, and authorization remain unchanged. Native helper hot updates and whole-install transactions are not established by the application-JAR publication protocol. Qualification still requires actual installed A→B→A late loading, no-update and failed-update behavior, authority outcomes, distribution verification, exact-source CI, and independent review. Issue #1842 additionally requires integrated authenticated ChatGPT reconstruction and continuation under the user's explicitly selected local acceptance policy.

Implementation and hosted evidence remain pending. The source-bound decision and review are retained in `build/orchestration/atomic-install-scope-reconciliation/PROPOSAL.md` and `build/orchestration/atomic-install-scope-reconciliation-review.md`; historical failure evidence remains unchanged.
