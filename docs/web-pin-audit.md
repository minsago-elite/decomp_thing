# Applied progress-pin audit receipts

Tracking: #177 and #172. This records successful progress-retention policy changes. It does not yet implement request auditing or the complete sensitive-operation audit contract.

Each changed pin is committed with its receipt in the existing atomic `workflow-state.json` publication, under the same job stripe and storage ownership lease. A receipt contains a per-job decimal sequence, server-clock timestamp, actor kind, optional session digest, target run, fixed `progress.pin`/`progress.unpin` action, fixed `applied` outcome, previous run version and applied run version. Job identity comes from the containing state. Lifecycle transitions preserve these receipts. A receipt means the policy was applied, not that any workflow or source revision was accepted.

The internal actor is explicit. A browser actor is derived from an already-authorized session identity using domain-separated SHA-256; the receipt never holds the cookie, CSRF/bootstrap token, headers, body, filename, private path or exception text. Actor attribution grants no authority. A future HTTP handler must obtain its actor from the authorized session, never from request JSON. The service forwards attribution to the store while coordinating the owned task's current version.

At most 256 receipts are retained per job. Additional changes evict the oldest receipt and advance an exact `omitted` prefix count. Sequence exhaustion rejects the change. Sequences establish publication order even when the server clock moves backward. Entries are immutable and decoding validates fixed keys, types, canonical timestamps, sequence continuity, actor shape, selected run membership, alternating pin actions and agreement between each run's latest retained receipt and its current pin. This is bounded operational history, not an indefinite or tamper-evident compliance archive.

Pin state and receipts use one publication, so interruptions cannot commit one without the other. Existing uncertain-publication handling prevents further mutation until reopening storage. A response lost after publication may leave an applied receipt even though the caller received an error; recovery exposes the persisted state. CAS rejection and unchanged-pin requests preserve bytes and do not add an applied receipt. Denied, stale, failed and no-op request audit outcomes still require a separate request-audit boundary.

The optional `pinAudit` field is absent until the first applied change. Existing records without it remain readable without rewriting or inventing attribution for earlier changes. Malformed audit data is rejected and preserved, not defaulted away. Older strict application versions reject records containing the new field; reopening those records requires a compatible version or an appropriate verified backup.

Tests use owned inert upload records and direct lifecycle transitions, plus an inert service callback. They exercise attribution forwarding, no-op/stale-byte preservation, restart, all five injected publication interruptions, bounded omission, immutable entries, malformed metadata and legacy reads. No binary analysis, provider or native workflow execution is required. Public mutation routes, rejected-request auditing, audit presentation/export, general operation coverage and retention-policy UI remain unfinished.

All 285 selected JVM tests pass with the pin audit and termination-lock fix together. The [retained manifest](evidence/web-pin-audit-shutdown-20260908/manifest.json) identifies the tested source, passing reports, original deadlock and failing negative control. Frontend/package/browser checks were not repeated for these internal changes.
