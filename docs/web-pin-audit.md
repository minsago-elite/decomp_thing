# Applied progress-pin audit receipts

Tracking: #177 and #172. This records applied progress-retention policy changes and successful keyed pin requests, including no-ops. It does not yet implement denied/failed-request auditing or the complete sensitive-operation audit contract.

Each changed pin is committed with its receipt in the existing atomic `workflow-state.json` publication, under the same job stripe and storage ownership lease. A receipt contains a per-job decimal sequence, server-clock timestamp, actor kind, optional session digest, target run, fixed `progress.pin`/`progress.unpin` action, `applied` or `unchanged` outcome, previous run version and applied run version. Unchanged requests preserve the run version; changed pins advance it. Job identity comes from the containing state. Lifecycle transitions preserve these receipts. A receipt means the policy was applied, not that any workflow or source revision was accepted.

The internal actor is explicit. A browser actor is derived from an already-authorized session identity using domain-separated SHA-256; the receipt never holds the cookie, CSRF/bootstrap token, headers, body, filename, private path or exception text. Actor attribution grants no authority. A future HTTP handler must obtain its actor from the authorized session, never from request JSON. The service forwards attribution to the store while coordinating the owned task's current version.

At most 256 receipts are retained per job. Additional changes evict the oldest receipt and advance an exact `omitted` prefix count, except that a keyed receipt cannot be evicted during its first 24 hours. If the oldest receipt is still protected, `PIN_RECEIPT_CAPACITY` refuses the new change without rewriting state. This bounds memory/disk use without silently shortening the idempotency window; it can also temporarily refuse internal pin changes. Sequence exhaustion rejects the change. Sequences establish publication order even when the server clock moves backward. Entries are immutable and decoding validates fixed keys, types, canonical timestamps, sequence continuity, actor shape, selected run membership, consistent changed/no-op pin actions, unique scoped request keys and agreement between each run's latest retained receipt and its current pin. This is bounded operational history, not an indefinite or tamper-evident compliance archive.

Pin state and receipts use one publication, so interruptions cannot commit one without the other. Existing uncertain-publication handling prevents further mutation until reopening storage. A response lost after publication may leave an applied receipt even though the caller received an error; recovery exposes the persisted state. CAS rejection and internal unkeyed unchanged-pin requests preserve bytes and do not add a receipt. A successful keyed no-op records `unchanged` atomically, advancing only the job metadata version. Denied, stale and failed request audit outcomes still require a separate request-audit boundary.

The optional `pinAudit` field is absent until the first applied change. Existing records without it remain readable without rewriting or inventing attribution for earlier changes. Malformed audit data is rejected and preserved, not defaulted away. Older strict application versions reject records containing the new field; reopening those records requires a compatible version or an appropriate verified backup.

Tests use owned inert upload records and direct lifecycle transitions, plus an inert service callback. They exercise attribution forwarding, no-op/stale-byte preservation, restart, all five injected publication interruptions, bounded omission, immutable entries, malformed metadata and legacy reads. No binary analysis, provider or native workflow execution is required. Rejected-request auditing, audit presentation/export, general operation coverage and retention-policy UI remain unfinished.

All 285 selected JVM tests pass with the pin audit and termination-lock fix together. The [retained manifest](evidence/web-pin-audit-shutdown-20260908/manifest.json) identifies the tested source, passing reports, original deadlock and failing negative control. Frontend/package/browser checks were not repeated for these internal changes.

## Durable request replay

`requestProgressRetentionPinned` requires a browser-session actor and a bounded idempotency key. Only a domain-separated digest scoped to the actor, job and selected run is stored. The raw key is neither persisted nor included in diagnostics. The normalized intent is the desired boolean plus the original run-version precondition; the operation itself is fixed to the selected progress-pin resource.

Under the job stripe, the store resolves an existing key before evaluating CAS. An exact repeat returns the original receipt with `replayed=true`, preserving its original result pin/version even if later policy or lifecycle changes have occurred. Reusing the key with a different boolean or precondition fails with `IDEMPOTENCY_CONFLICT`. New successful requests atomically publish their receipt with the pin or no-op decision. Concurrent duplicates produce one receipt. Replaying never writes metadata.

The result deliberately carries both the original receipt and the **current** attempt. The service uses only the current attempt to update its owned task cache; a later HTTP response must use the receipt for the original result. This prevents replaying an older successful pin from rolling back a queued task's version or its subsequent unpin.

Keys remain replayable while retained, including after storage reopen. A same-actor request can replay even after restart recovery changes the run version. This storage property does not preserve browser sessions across server restart: session authentication still has its own lifetime, and a new session is a different actor. The endpoint must not accept a caller-supplied actor to recover a previous session's scope.

The 24-hour protection starts at the successful request timestamp, including no-op requests. Backward clock movement conservatively retains the receipt. At the exact deadline eviction may resume, with an explicit omitted prefix; once a key is evicted, the request is new and must pass current CAS. Clients must reconcile state before choosing a fresh action rather than blindly retrying an expired key. Validation rejects null/non-digest keys, duplicate scoped keys, contradictory outcomes and unkeyed no-op records; older applied-only receipts remain readable.

The authenticated HTTP route and typed client now use this request boundary; see [the API contract](web-api.md#implemented-progress-pin-policy-endpoint). Rejected-request audit coverage and default periodic maintenance activation remain unfinished.
