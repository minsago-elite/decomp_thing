## Selected runtime measurement contract

Reuse native GCC shared-library execution, the actual compatible caller, all 24 scenario definitions and their five exported functions plus mutable state. Preserve struct argument/return, variadic and callback/context behavior exercised by those scenarios. Reuse the existing bubblewrap isolation, verified systemd cgroup, bounded capture, PID identity and cleanup mechanisms. The missing seam is truthful report/coordinator/schema semantics, not a new emulator. Remove diagnostic marker emissions from the new trusted caller source; do not strip marker-like bytes on either reference or candidate path. Do not interpret them as load, call, callback, or completion evidence.

The external runner can establish process-level facts: a launch request, successful OS process creation, verified owned scope, captured bytes, process termination status and verified cleanup. With the existing systemd-run/bwrap wrappers, Popen's PID is the launcher, not direct evidence of a /caller exec or an export entry. Report launcher creation and kernel-verified worker scope separately. A completed contained invocation may yield a process observation only after verified scope admission, completed capture/wait and cleanup. Wrapper setup failures are infrastructure unknown, not automatically candidate failures. Keep termination of the wrapped invocation explicit rather than calling it an independently observed library exit. If the wrapper does not establish a usable completed worker observation, mark unknown. The qualification matrix must demonstrate this distinction with synthetic scope/wrapper failures.

Candidate stdout/stderr are untrusted behavior bytes even though their capture is performed externally. Compare them verbatim, together with the exact completed termination result, against a newly generated reference under the identical runner/caller/profile. A candidate can imitate expected output: passing is a finite native process-behavior result, not proof of internal execution or general equivalence. A parent-issued scenario request never means an API entry. No inherited FD, shared memory, caller-resident secret, marker string, or observed caller PC is a trusted semantic event channel.

Load attempt/completion, specific export entry, API completion and callback counts remain `unverified` with value `null` absent independent evidence. Admission refusals establish that the evaluator did not issue a runtime request for that candidate; this is a controller decision, not a measured internal zero-call event. Report load as a separate unverified phase after admitted launches, and not-attempted after admission refusal. Behavior can pass while load/API observations remain unverified. A new external loader/guest executor is future work only if exact internal API claims are requested; it is not required for this correction or #1507 acceptance.

## New generation and schema migration

Create a new corrected namespace `oracle/acp/callable-evaluator-v3/source/`, copied from the exact archived baseline, leaving the historical v2 namespace untouched. The new execution/preparation namespace is `build/acp-decomp-effectiveness/callable-library-v3/`; it is a new generation, not a relocated qualification claim. Preserve target, GCC commands, native loader semantics and export rules. Adapt existing `_v2` module/coordinator filenames to `_v3` in the new generation. Set helper, profile/visible manifest, report, reference-observation, matrix, execution-bindings and final preparation schema versions to 3; add closed JSON schemas for each changed exchange. The helper's version changes because identity/builtin descriptors change. The profile changes because limits and report semantics change. Reject v2 input in v3 readers; never reinterpret or rewrite old receipts. The new helper/profile/reference/matrix hashes bind every report and seal.

The report schema must express these distinct fields:

- `scenarioCount:24`, `admitted`, `runtimeRequestCount`, `launcherCreatedCount`, `scopeVerifiedCount`, `completedScenarioProcessCount`, `matchedScenarioProcessCount`, `mismatchedScenarioProcessCount`, `unknownScenarioProcessCount` and `admissionRefusedCount`. Counts derive from per-scenario facts, with no request counted as creation or completion.
- `processBehaviorRate = matchedScenarioProcessCount / completedScenarioProcessCount`, or null for zero denominator; always disclose completed/24 coverage and unknown/refused counts. This is a process metric, never pooled with CLI cases or called API coverage.
- `apiEntryCount`, `apiCompletionCount`, `callbackCount`, `apiCoverage` and `apiBehaviorRate` are null. Remove the old `candidateCalled`, `recordedCallCount`, `executedScenarios` and `behaviorRate` fields instead of preserving misleading defaults. Per-scenario load/API observations carry `status:unverified,value:null` when runtime is requested, and not-attempted/null otherwise.
- Per-scenario process status is admission-refused, matched, mismatched, or unknown. A completed signal or bounded termination is represented explicitly as a known process termination outcome only with complete runner evidence; incomplete capture, failed containment or missing cleanup remains unknown. Keep timeout/output-limit flags and partial bytes in the receipt without turning truncation into an exact behavior match. A completed ordinary exit requires exact exit code and byte equality. Reference schema describes termination kind and code/signal explicitly; synthetic fixtures cover nonzero reference exits. Do not equate run()'s exit-zero convenience status with outcome comparability.
- Aggregate behavior is passed only if all 24 are completed and matched, failed if any known mismatch exists, otherwise unknown if any required observation is unknown, or not-attempted when admission prevents runtime. Preserve known mismatches alongside unknown rows. ABI accuracy, formal structural score, API score and production authority remain null/unassessed/false as appropriate.
