## Closed deliverables and sequence

### 1. Authenticated input lock and static inspector

The packaging owner implements a bounded input-lock/inspection command and focused inert controls in the dedicated Task6 worktree. Expected identities come from reviewed application/build policy, never an adjacent checksum supplied by the candidate. First accept only the named OCI family and one uniquely identified `linux/amd64` platform; reject ambiguous selection, unsupported media types/foreign layers, inconsistent sizes/digests/diffIDs, unsafe path/whiteout semantics and decompression overflow. The lock must enumerate every descriptor and selected payload source, source ownership and exact tool/recipe identity.

Proposed acquisition/inspection ceilings, separate from the unchanged production runtime ceilings: 1MiB per JSON descriptor, 8MiB aggregate metadata, 128 descriptors, at most one index plus one selected platform manifest/config, 32 layers, 512MiB per compressed layer, 2GiB aggregate compressed input, 1GiB expanded per layer and 4GiB aggregate expanded stream. At most 65,536 archive entries, depth32, 4096 UTF-8 path bytes, 256MiB per regular input member and 1MiB per inspection record; stream file hashing/copy in <=64KiB blocks and charge every read/decoded entry. Reject incompatible candidate inputs without truncation. The complete lane, including container storage and both output builds, must preflight an 8GiB added-disk ceiling, 1800-second absolute end, <=1GiB inspector and <=2GiB builder memory, two CPUs and 128 PIDs before execution; account duplicated stores/output archives rather than ignoring them. If this concrete source cannot fit, optimize the storage/streaming recipe or return unavailable for review, never silently raise a cap.

Validate OCI layer paths and type transitions into a bounded virtual member map, not by applying archive paths to the host filesystem. Define and test regular/directory replacement and both ordinary and opaque whiteouts against prior layers. Unknown operations, path escape/collision ambiguity and special nodes are unsupported. Recorded links in the authenticated trusted builder image are not eligible native payload sources and are never followed by the package selector; final production output has no links at all. Before execution, review the engine/loader-to-image identity binding and confined read-only builder/mount recipe as part of the toolchain. A source digest alone cannot turn an unrestricted host Docker command into the reviewed lane.

Reuse existing bounded archive/ELF helpers only after reviewing their distinct authority and behavior. Reject unresolved/duplicate providers and unapproved search/audit/filter/plugin behavior. A literal required-file list or caller-provided DLOPEN edge is not semantic proof.

## Acyclic application, approval and qualification commitments

Use a documented, domain-separated DAG; this definition overrides the audit's preliminary placement of review hashes inside its proposed approval record. Every hash identifies immutable bytes, with authority supplied by the appropriate trusted issuer/receipt rather than the hash alone.

| Node | Commits | Cannot contain |
| --- | --- | --- |
| Application input identity A | A closed manifest of source/code, dependency locks, build/generator recipe, fixed worker and non-generated inputs, excluding only schema-declared generated runtime/approval resources and receipts | Runtime manifest/approval/review outputs or final application artifact hash; no caller-chosen exclusion list |
| Build/source input lock I | Exact OCI/tool/jmod/source/patch/recipe identities and prior authentication receipts | Generated runtime manifest, app artifact or later approval/qualification receipts |
| Runtime manifest M | A, I, regular runtime file/archive identities, worker, ABI/loader/dependency/mount/bounds fields | Its own digest, approval-envelope/review/qualification hashes or final app hash |
| Resolver approval core P | A, M, exact resolver bytes/digest, transport/network/deployment/source-owner/launch semantics and immutable policy-input identities | Any receipt that cites P; review/approval-envelope/qualification/final app hashes |
| Detached approval envelope E | Exact A/I/M/P and prior source/provisioning/policy-decision/independent-review receipt hashes; each such receipt cites the relevant immutable inputs/core, never E itself | Its own digest or later qualification/final app hashes |
| Final application artifact F | Compiled code, generated expected identities and packaged A/I/M/P/E resources under the authenticated build recipe | Its own final hash or a qualification/release receipt that cites F |
| External qualification/release receipt Q | Final F hash plus A/I/M/P/E, exact native/CI evidence, detached independent qualification review and release/deployment decision | Embedding Q back into F or requiring an attesting receipt to contain its own hash |

For example, an independent approval review hashes M/P and source/provisioning evidence; E then commits that review hash. The review does not hash E, and P does not contain the review hash. Native run evidence hashes final F; detached qualification review hashes that evidence; the outer release receipt commits both. These stages never rewrite earlier immutable nodes to add a downstream receipt.

The new schema must call A an application **input** identity, not ambiguously claim it is the final self-containing JAR/image SHA. If a legacy candidate field remains named `applicationBuildSha256`, its unsupported v1 meaning cannot be silently repurposed: use the reviewed new-version field and explicit schema semantics. Record final F only externally after packaging. Validate schema-declared dependency direction/unknown fields and wrong or missing A/I/M/P/E/F links; add controls for embedded self-reference, substituted review/core, mixed app input/final artifact identities and unrecognized authority roots. The authenticated distribution/installation and private factory still must verify the exact approved tuple; generating internally consistent hashes grants no new caller authority.
