## 1. Authority, installation and genesis

The production boundary is a root-installed supervisor, its independently approved immutable tooling image(s), a dedicated private Docker/containerd instance, and kernel isolation. The caller may be a malicious process with the authorized user's UID. Root administrator, kernel, supervisor and dedicated runtime are trusted; payload programs, caller records, caller source trees and child stdout do not confer authority.

Install the supervisor as `/usr/libexec/decomp-thing/clang1813-supervisor`, a self-contained reviewed bundle launched with a fixed root-owned interpreter and isolated `-I -B` configuration. Do not import Python/build/plugin code from the caller checkout, current working directory, user site, environment or writable caches. Pin the supervisor bundle, interpreter/stdlib/native-library closure, runtime CLI, service unit, namespace-monitor binary and their package/dependency construction evidence in an administrator-approved deployment manifest. Root-owned parent directories, no group/world writes and no symlink components are mandatory for every installed executable, approval, key, config and state path. Hold checked executable snapshots/descriptors for use. Do not execute root code supplied by a request, even if a caller supplies a matching digest.

The root-owned approval anchor at `/etc/decomp-thing/approved-actions/v1/approval-anchor.json` pins the approval authority public key identity, exact approved index digest, supervisor/deployment manifest digest and receipt public key digest. The administrator installs that anchor through a separate authenticated/reviewed deployment procedure. Request handling cannot create or update it. Verify authority signatures on the index/deployment/action/environment manifests using the installed key and current production validity policy, and require the anchor's exact digest pins as well. Missing, revoked, expired, unsigned, malformed or mutable approval inputs reject. Approval of an image never implies approval of arbitrary client sources or plugins.

No approval key, package digest, image digest, deployment manifest or receipt key is currently available for this design. Do not generate placeholder production approvals or promote the existing inert test values. A real administrator-approved genesis is a deployment prerequisite. The checked-in policy remains `qualificationEnabled: false` until all implementation and evidence gates pass; editing that JSON cannot enable the installed supervisor.

Use a dedicated root-only runtime socket `/run/decomp-thing/clang1813-docker.sock`, mode 0600, root:root, under a root-protected parent. Its daemon/config/containerd/storage/service identity is separately pinned in deployment approval. Authorized users must not be members of its control group or have an alternate endpoint into that daemon. Never use the caller's default Docker context, daemon, environment or socket. This daemon has fixed user-namespace remapping, no live restore, no automatic restart of worker containers, and a dedicated data root/service cgroup. No generic host Docker daemon restart or cleanup is authorized.

State and artifact roots are administrator-created root-owned directories on the approved quota/verity-capable filesystem. The supervisor opens and authenticates their device/inode/filesystem identity at service startup, then retains directory FDs. No request may name a stage parent, host output directory, socket, command, mount, environment, key or approval path. Existing `DockerBackend`'s trusted stage-parent FD comes from this startup authority, never from a client's FD vector. Deployment path names are specifications only; preparing this plan writes nothing there.

## 2. Independent gates before any native action

1. **Acquisition permission:** preserve the current explicit acquisition pause. No supervisor action can lift it. The expired 18.1.3 key still fails current-clock production verification. No faked time, alternate trust/key, expiry exception or source-route workaround is introduced.
2. **Approved tooling:** authenticate the installed deployment/index/action manifests and actual immutable host image/interpreter/runtime closure before execution. Exact source/build/plugin/resource/classpath inputs must match the complete approved action manifest. Caller-computed recipe or record equality is insufficient.
3. **Approved artifacts:** root-approved acquisition evidence must bind signed Snapshot metadata, exact package/source artifact bytes and source audit inputs. A self-consistent candidate is still a candidate until independently reviewed/approved under the existing project rules. The supervisor must rerun the cryptographic/content checks; receipt signing cannot bless an expired or unverified source.
4. **Implemented action/profile:** each requested action must have a versioned independently approved execution policy, compiled monitor/filter where required, implemented artifact transport and passing deployment controls. Unsupported package behavior or absent namespace/resource support rejects; no fallback widens capabilities or invokes host legacy functions.
5. **Capacity/deadline:** reserve source/input/work/output quotas before admission. One qualification request at a time, at most one active container; enforce a shared 2,100-second monotonic deadline across its two clean builds and all replays. Action limits below are maxima, not additive entitlements; every action receives the smaller remaining deadline. Crossing a host boot aborts unfinished qualification rather than extending its deadline.

Public CLI functions remain blocked until these gates and the installed transport are implemented. The old `_unqualified` helpers are inert test/reference code, not a dispatch target for the privileged service.

Resource and namespace configuration is measured through the trusted daemon before/after execution and kernel PID/namespace checks at the start barrier.

### Bootstrap setup and package execution

The dedicated daemon's approved user namespace mapping must cover all required in-image UIDs/GIDs, map root to a nonzero reserved host range and exclude the caller's UID. Verify `/proc/<container-init>/uid_map`, `gid_map`, namespace inode identities, start time and pidfd through the root supervisor, correlated with daemon container ID. A missing/single-ID/incompatible mapping rejects. Never substitute host-root execution.

A fixed compiled PID-1 monitor from the approved tooling image performs only a predefined setup: enter the bounded work root; hold its root directory FD; mount private target proc and a minimal device view copied/bound from the container's isolated runtime-provided null/zero/random/urandom devices; no host device tree or dynamic user mount request. Fixed mounts carry `nosuid,nodev`/read-only restrictions as applicable. It does not evaluate client shell text or package metadata as mount instructions. If the kernel/runtime cannot provide this setup under the approved mapped namespace, reject without adding host privileges or `--privileged`.

Before executing package code, the monitor creates a child with the exact bounding/permitted/effective set `CHOWN,DAC_OVERRIDE,FOWNER,FSETID,SETUID,SETGID,SYS_CHROOT` in the mapped namespace; all other capabilities, ambient and inheritable sets are cleared. Apply no-new-privileges and a fixed deny filter for mount/umount/pivot_root, unshare/setns, namespace-creating clone flags and clone3, ptrace, bpf, perf, keyctl, userfaultfd, open_by_handle_at, mknod, module/reboot/swap operations and other unneeded privileged syscalls. Ordinary process creation and target-root chroot remain the reviewed install operations. The monitor is nondumpable, holds its setup/control FDs privately, closes them in the child and never accepts package-origin commands. It retains only the narrowly required setup authority for final fixed unmount/cleanup; untrusted package code never receives that authority. PID-1 supervision reaps/kills remaining descendants before export. At a start barrier the trusted monitor keeps the child stopped before package exec. The root supervisor correlates its host PID through the container init's kernel child list/NSpid/start time, opens a pidfd and verifies mapping, capability and no-new-privileges fields. It reads every installed filter with `PTRACE_SECCOMP_GET_FILTER` and compares the ordered instruction digest with the approved compiled filter before releasing the private monitor control channel. The child never receives that channel. Unsupported kernel filter inspection or an extra/mismatching filter rejects production enablement; it is not replaced by checking only Seccomp mode 2.

The builder uses only the complete authenticated offline `file:` mirror: original signed metadata/keyring bytes and every approved bootstrap/final `.deb` payload. Network is absent, proxy variables empty, and missing bytes fail. No `--no-check-gpg`, trust fallback, expiry bypass or mutable host apt repository is allowed. Record the actual fixed offline command/context and its exact mapping to the approved Snapshot origins; do not claim the old HTTPS command was executed. The reviewed implementation may reuse pinned debootstrap/dpkg internals inside this boundary, but it must prove all required operations fit this explicit profile. Unsupported maintainer-script behavior fails closed and requires a separately reviewed exact policy; it cannot request new caps or mount access.

After all installation descendants stop, independently compare installed payloads with authenticated `.deb` manifests and exact approved transformation rules. The empty exception registry remains conservative until real package-specific derivations are approved. Apply only exact recipe-bound normalization, including hostname/resolver/machine ID and existing cache/log rules. Remove the transient target mounts before canonical export; the qualified `/dev` and `/proc` contents are fixed empty directory policies rather than host-derived device/proc bytes. This is an explicit rootfs recipe change that requires schema/inventory/command updates and fresh qualification, not an undocumented exclusion from payload checks.

### Probe, driver/runtime and loader execution

The trusted monitor chroots the compiler child via the held target-root FD only after installation quiescence, then drops UID/GID/caps before compilation. Source and fixture digest checks bracket compilation from immutable snapshots; fixed compile flags do not consume untrusted injected tool flags. The monitor installs the resulting measured probe into the retained rootfs after compiler descendants stop. No package worker remains alive to mutate compiler inputs or outputs.

For driver/runtime/probe replay, load only an OCI artifact generated from the supervisor-authenticated rootfs, with canonical config/layers/ref validated and complete package-payload checks replayed. This dynamic qualified-rootfs image identity is a permitted derivation authorized by the root-approved action and approved acquisition inputs; the root supervisor computes it from held artifacts and records it. A caller-provided image digest or rewritten record never authorizes import. Execute replay directly as UID 65532 in that image, not a host `sudo chroot`. Actual rootfs bytes and each loaded image/config/diff ID must match the supervisor receipt. This cannot be enabled before authenticated payload replay exists.

Loader compilation is a separate fresh action from loader execution. Compile the complete approved production Kotlin/transitive Java/Kotlin source/resources plus Java harness using immutable approved Gradle distribution/plugins/compiler/runtime dependencies, offline with no shared writable cache. Every init/build/plugin file is an input bound by the action manifest; mutable checkout Gradle is only a client. Stop/reap the compile container, copy the output JAR/class closure into a supervisor-owned immutable artifact, validate canonical member names/duplicates/classpath inventory, and issue an internal compile receipt bound to source/action/tooling identities. A fresh loader-run container consumes that read-only artifact and the exact approved dependency classpath. It cannot reopen checkout classes or run from the compile worker's mutable output directory. Packaging always requests fresh loader execution against its exact record/rootfs/artifact identities; reuse of compiled bytes is allowed only through the signed immutable compile receipt matching the active approval. The authoritative loader report is actual root-supervised output and retains infrastructure-only scope.

## 4. Peer authentication and bounded FD protocol

Use a fixed root-owned `AF_UNIX/SOCK_SEQPACKET` client socket `/run/decomp-thing/clang1813-supervisor.sock`, root:approved-client-group mode 0660, under a root-protected parent. This is distinct from the root-only Docker socket. Client verifies `SO_PEERCRED` UID 0 and the socket path's protected installed authority; server obtains peer PID/UID/GID with `SO_PEERCRED`, requires the exact administrator-approved caller UID/group/action policy, records peer start time and opens a pidfd while the peer is alive. Supplementary client-supplied credential fields confer nothing. Unauthorized peers reject before reading artifact contents. A pidfd/connection lifetime ties cancellation to that peer without signaling a later PID reuse.

Fixed protocol v2 messages: `HELLO`, `BEGIN`, ordered `FD_BATCH`, `COMMIT_INPUTS`, `CANCEL`, `STATUS` for the same peer/job, and server `ACCEPTED`, `RESULT`, `REFUSED`. No arbitrary argv/path/env/mount field is legal. Each request identifies action, independently approved lock/action digests, a fresh 256-bit client nonce, qualification parent job ID if relevant, and an ordered manifest of logical FD roles/counts/byte identities. The server generates its own job/attempt identities. JSON uses duplicate-key rejection and exact schema; frames max 64 KiB/depth 16/4,096 nodes; no out-of-band pickle, executable serialization or URL field.

Use `SCM_RIGHTS` with at most 32 FDs per batch, sequential batch/frame counters, exact final count and a SHA256 transcript over canonical headers/ordered manifest (not integer FD numbers). Reject `MSG_TRUNC`, `MSG_CTRUNC`, duplicate logical labels, unexpected ancillary types, missing/extra/reordered batches, duplicate FD open-file identities where independent inputs are required, unknown socket/file types and FD-count overflow. Set CLOEXEC at receive. Before COMMIT, no container or external tool runs. Close every received FD on protocol error, peer disconnect, timeout or cancellation. No service thread changes process-global environment or uses client current-directory state.

Limits: at most 512 recipe/source FDs with 16 MiB each and 64 MiB total; at most 1,200 package/source payload FDs with 1 GiB each and 3 GiB total; at most eight additional record/OCI/rootfs/report inputs under their exact action caps (rootfs/OCI 2 GiB each; metadata/report 1 MiB each). Service FD limit 8,192, one admitted qualification at a time, one active container, input framing deadline 30 seconds plus explicit bounded stream capture time within the aggregate job deadline. Reserve a 20 GiB per-qualification storage budget, including 3 GiB authenticated payload staging, 8 GiB work quota, bounded immutable output/scratch and recovery headroom. This is a deliberately explicit new deployment capacity requirement; it does not inherit the old 7 GiB free-space assertion. If the approved runner/storage cannot reserve it, qualification remains unavailable until independently reviewed capacity or tighter measured bounds are supplied.

FDs are caller-opened read capabilities, not privileged file path requests. Require regular finite files (reject directories/devices/FIFOs/sockets/sparse or unsupported special representations under the applicable input policy), copy/stream them through bounded reads and compare the exact expected digest. Approval for recipe/source rows comes from the root action manifest; approval for large payload rows comes from independently approved acquisition metadata reauthenticated by the supervisor. A request manifest cannot supply its own authorization hash. Small source snapshots use sealed memfds. Large artifacts stream into exclusive broker-owned files via held directory FDs, hash during capture, enforce cumulative limits during reads, fsync and freeze before mounting. Caller mutation after capture cannot affect consumed bytes; mutation during capture either yields the exact approved bytes or rejects.

## 5. Artifact authenticity, publication and receipts

Workers write only fixed logical output locations in the quota work volume; no client output path is mounted. When the action ends, the supervisor verifies all action descendants/cgroups are empty, stops the container, then opens expected output files without following links through the held managed-volume directory authority. Reject extra/unsafe output members, wrong file types, sparse/PAX/path ambiguity and count/size overflow under each exact artifact schema. Copy to a distinct broker-owned artifact inode; never publish a worker-writable inode or trust worker-reported hashes, ownership or exit flags.

Freeze each final artifact with required filesystem verity, verify the verity measurement and independent length/content SHA256, close all write handles and retain a read-only descriptor. Mode 0444/root ownership and protected parents are additional controls, not a substitute for immutable content. Unsupported verity or quota capability rejects production enablement; no mutable-copy fallback. The client receives only read-only FDs, never a writable FD/path or writable volume. File metadata and verity/SHA identity are bound in the result. Client may copy artifacts into its own paths, but subsequent consumers must compare their bytes with the signed receipt rather than trust those paths.

The supervisor computes a canonical signed result manifest containing protocol/action/job/client nonce, active approval index/lock/action/source/acquisition digests, actual tooling and qualified-rootfs image/config/diff IDs, supervisor/monitor/runtime deployment identities, boot/daemon/container/process identity, actual exit/limit/cleanup status, ordered immutable artifact rows and precise evidence scope. Sign using an independently installed receipt Ed25519 key protected by the approved supervisor deployment; its public-key digest is pinned in the root-owned anchor. No child stdout, request key, user-generated record or caller receipt is an authentication source.

The root key and exact crypto implementation are deployment inputs not currently available. Select a reviewed root-installed Ed25519 implementation in the measured supervisor bundle; do not dynamically import an unpinned host crypto package. Test keys may exist only in repository-local inert fixtures. Public client verifies signature against the installed pinned public key plus exact request nonce/action/input transcript and artifact FD bytes. A `RESULT` is sent only after durable receipt/artifact commit and authenticated cleanup completion. No success receipt is signed for failed, timed-out, OOM, incomplete, cleanup-pending or unsupported actions. A generic stdout blob/record digest is not a receipt.

Packaging independently replays the full authenticated package-payload-to-normalized-tree comparison, both driver identities, probe-inclusive runtime discovery, probe and loader actions and locked comparator as authorized, using the active root-approved context. It compares freshly supervised authoritative report bytes and actual artifact identities, not caller-provided booleans. The final provenance archive includes exactly the immutable evidence snapshots consumed and its signed root-supervisor receipt. This remains a qualification artifact with explicit acceptance scope; it cannot register/promote a production toolchain profile by itself.

## 6. Durable ownership journal and recovery

Use a root-owned SQLite journal in the authenticated state directory with WAL and `synchronous=FULL`; SQLite/runtime/file-system dependencies belong to the measured supervisor deployment. Acquire a root-owned exclusive service lock and reserve quotas transactionally. Journal commit must complete before each daemon mutation or artifact publication. A corrupt/unsupported journal or failed durability operation blocks admission and success publication.

A job row records: random job ID; peer UID/GID/PID/start time/client nonce; kernel boot ID; supervisor generation/PID/start time; dedicated daemon service PID/start time/instance/data-root identity; approved deployment/index/lock/action/transcript/source/artifact identities; reserved quotas/deadlines; root stage/volume device+inode ownership; state/version; independent random container/volume attempt names and 256-bit ownership tokens allocated before their creates; actual immutable IDs when known; init PID/start time/pidfd-correlated namespace/mapping/capability measurements; cleanup state; immutable artifact/verity identities; receipt digest/signature and delivery state. Never use a PID alone, a caller label alone or a mutable object name as deletion authority.

State transitions: `INPUT_CAPTURED` → durable `CREATE_PENDING` → `CREATED` → `START_BARRIER` → `RUNNING` → `QUIESCED` → `OUTPUT_FROZEN` → `CLEANUP_PENDING` → `READY` → `DELIVERED`. Failures enter durable `ABORTING`; only authenticated cleanup plus quota/artifact accounting can reach `ABORTED`. Each transition requires its exact predecessor/version. Include volume creation/import and other daemon-created resources as separately journaled operations before sending their request, not only containers. Journal and immutable artifact publication ordering must survive injected crash at every boundary.

Before create, commit exact intended name/token/approval/image/source mounts and mark `CREATE_PENDING`. All create result losses (timeout, overflow, malformed reply, disconnect or supervisor crash) retain that intent. Reconcile through the trusted daemon by name/token, authenticate the complete journal correlation and immutable ID, then remove by immutable ID. A preexisting/colliding foreign object is never stopped or deleted; refuse/quarantine that job. Known-ID cleanup rechecks ownership as well. Token labels are correlation under the exclusive root-controlled daemon, not public secret-based authorization.

**Not-found is not proof of absence while an old create RPC may still finish.** Keep the durable row and quota reservation pending; do not delete intent, report clean completion or admit a conflicting job. A successful single inspect or a short timeout cannot discharge this ambiguity. For recovery, the approved supervisor has one fixed administrative operation on the dedicated runtime service: stop its dedicated daemon/containerd/shim cgroup, wait by pidfd/cgroup identity until all old service processes/in-flight request handlers are gone, and restart only that approved service/data root with live restore/restart policies disabled. This is the selected epoch barrier; it is not a client action and cannot target another daemon or arbitrary host service. If the barrier or daemon is unavailable, remain quarantined/unqualified. No worker payload receives daemon/service control.

After this verified epoch barrier, enumerate the dedicated daemon's full current object inventory through its root-only socket and correlate every journal-owned token/name/ID/image/deployment. Remove owned remnants by immutable ID; preserve foreign objects and block ambiguous state. Only after the old request-processing epoch is proven dead and the complete new inventory lacks a pending owned object may an unknown create be marked absent/aborted. This handles delayed daemon creation without assuming CLI cancellation cancelled server work. Recovered old-boot jobs are cleaned/aborted, never resumed as live qualification.

Root service startup must reconcile all nonterminal rows before accepting new work. Verify boot ID, actual daemon process/service/data-root identity and any surviving container PID/start time/namespace mapping before signaling. Use pidfds; never kill a reused numeric PID or a container found only by a client name. A supervisor restart within one boot does not erase its previous generation's durable ownership. An already completed immutable receipt can remain archival evidence, but a new packaging request requires its own nonce/current approval and fresh authorized replays; a stale signed result cannot satisfy a different action/input transcript.

Receipt commit is durable only after immutable output files and their directory entries are fsynced/verity-frozen and cleanup is complete. If the client disconnects before delivery, retain only bounded ready artifacts under journal TTL/quota policy; unfinished jobs cancel/clean. TTL cleanup acts only on root-journal-owned immutable artifacts and authenticated daemon objects. Generation, boot or daemon mismatch is an investigation/quarantine condition, never permission to widen cleanup scope.

### R1. Durable ownership starts before capture mutation

Replace the earliest state sequence with `ADMITTED` → `INPUT_CAPTURING` → `INPUT_CAPTURED` → `CREATE_PENDING`, followed by the remaining existing states. `ADMITTED` is a durable SQLite transaction containing job/generation/boot/peer/request identity, the exact approved input closure, the complete quota reservation, the authenticated stage/artifact parent device/inode/filesystem identities and independently random intended stage name/token. Commit this row before creating any per-job stage directory, spool file, volume or capture helper. Admission failure before that commit owns no resources and may not mutate storage. A failure after it enters journaled abort/recovery rather than deleting the row or sweeping a directory.

Every resource has a subordinate durable capture-operation row before mutation: operation/job ID, ordinal, logical approved input ID, exact parent identity, random exclusive name/token, expected byte/hash authority, cap/reserved bytes and state. Transitions are `INTENT` → `CREATED` → `COPYING` → `SYNCED` → `FROZEN` → `NAMED`; actual device/inode/verity identity is recorded as soon as available. Stage directory creation has the same intent/created identity records; it cannot be implicit in a later file operation. Persist the intent before `mkdir`, exclusive file creation, fsync/freeze or publication rename/link, and commit each resulting identity/state before moving to the next operation. Global job state becomes `INPUT_CAPTURED` only after every required resource has its durable immutable named identity and no live capture helper remains.

Use the already authenticated held root-owned parent directory FD. Create exclusively with no-follow semantics, root owner and mode 0700 for stages/0600 for spools. Creation happens inside a short fixed supervisor mutation section that cannot be interleaved with another generation's recovery. After creation, record the actual FD device/inode, set a fixed trusted filesystem ownership xattr `trusted.decomp_thing.capture` containing the job/operation/token tuple, fsync the file/directory and parent, and commit `CREATED` before handing a write FD to any helper. This trusted ownership marker is a selected deployment filesystem requirement; clients/workers cannot set it. It is not a digest supplied by a request.

A crash between exclusive creation and setting/committing that marker leaves a resource with an uncommitted identity. Recovery must not infer ownership from its random name alone or remove it speculatively. Preserve the intent and quota reservation, quarantine the stage, and require administrator reconciliation under the authenticated parent. A crash after the marker is durable can authenticate ownership by parent identity + exact trusted marker + actual device/inode as recorded or recovered, then resume cleanup/state reconciliation. Unknown, mismatching, missing or foreign replacement entries are preserved and quarantine the job. No root directory sweep, UID-only deletion, lexical-prefix cleanup or name-only inode adoption is permitted. The conservative unmarked crash window is an explicit refusal/recovery state, not an unowned leak claimed clean.

Helper spawn is similarly write-ahead: commit intended helper/job/generation identity before spawn; the approved helper waits at a start barrier without any caller-FD filesystem operation. The supervisor records boot/PID/start time and opens a pidfd, commits `CAPTURE_HELPER_READY`, then releases the barrier. Its helper operation row stays owned until pidfd-confirmed exit and all output FDs are closed/frozen or cleaned. A supervisor crash before release leaves a helper whose control-socket EOF makes it exit without input I/O. Disconnect/cancel and helper failure enter `CAPTURE_CANCEL_PENDING`/`ABORTING` durably; no cleanup completion or quota release is allowed while a helper may still write.

Recovery enumerates journal rows and their exact owned resources, including all admission/capture states, before any new admission. It reconciles file creation, partial write, file fsync, trusted marker, verity freeze and naming intent independently. Rename/link publication records both old/new exact names and expected inode/marker before the operation; on restart, inspect only those entries and adopt/clean only the same authenticated immutable inode. Contradictory/foreign entries remain untouched. Receipt readiness still requires every input/output resource and quota transition to be durable; these early capture operations are part of that invariant.

### R2. Potentially blocking caller I/O never runs in the root dispatcher

Adopt both an explicit filesystem acceptance policy and a supervised capture helper. All operations on client FDs that could invoke a filesystem callback—including `fstat`, filesystem identification, sparse/extent checks, seek and read—run inside the helper after its durable start barrier. The root Unix dispatcher does not invoke them and never waits synchronously for helper exit. It remains able to process STATUS/CANCEL/peer disconnect/deadline events using pidfds, timerfds and nonblocking control sockets.

The helper is a separately measured fixed native capture executable from the root-approved supervisor deployment, running as dedicated host UID/GID 65533 (distinct from clients and container/subuid ranges), with empty capabilities, no-new-privileges, a nondumpable process and its own cgroup. It inherits only the client source FD, the broker-created write-only spool FD and a fixed supervisor control FD. After its minimal startup it cannot open paths, create files/processes/namespaces, execute programs, mount, ptrace, create network sockets or access service keys/journal/runtime. Its syscall filter permits only the fixed bounded metadata/read/write/hash/control/exit operations. Client file bytes never become code or commands. Root ownership of the spool is maintained even though an already-open write capability is passed to this constrained helper.

Accepted source FD filesystems are only deployment-approved local ext4, XFS and tmpfs/memfd representations, verified inside the helper with descriptor-based filesystem identification. Reject FUSE, NFS, CIFS, other network/unknown filesystems and unsupported sparse/extent representations. No pathname or user-supplied filesystem label can authorize them, and no fallback silently broadens the list. The approved persistent spool/artifact filesystem separately requires quota, trusted ownership xattrs and verity. These checks do not replace the helper deadline: even a nominally supported local filesystem can stall, and metadata inspection of a rejected filesystem may itself block.

There is at most one live capture helper and one outstanding source read across the entire admitted qualification. Use 64 KiB buffers; each helper has 64 MiB memory, one CPU, one process, an output/fsize cap equal to its exact reserved approved input size and a 60-second wall-time deadline including metadata/extent checks. Total input capture is capped at 300 seconds and also the remaining 2,100-second qualification deadline. The supervisor clock owns those deadlines; no worker progress message extends them. Input-frame receipt has its separate existing 30-second deadline. Hard limits do not assert that maximum inputs fit this time; real deployment must demonstrate throughput or remain blocked.

On expiry/cancel/disconnect, journal `CAPTURE_CANCEL_PENDING`, send termination through the held pidfd and then SIGKILL/cgroup kill after a fixed short grace period. Poll pidfd/cgroup completion without blocking the dispatcher. A kill signal is not proof of exit: an uninterruptible I/O task can remain alive. In that case keep the job/helper/FD/spool ownership and full quota reservation quarantined, refuse success, stop new admission under the one-helper bound and continue responding to status/cancellation requests. Do not freeze/publish/unlink its writable spool or mark ABORTED/CLEAN until kernel-confirmed helper exit; do not spawn replacement helpers to bypass the bound. Recovery rechecks boot/start-time/pidfd/cgroup correlation. Reboot or administrator storage recovery can resolve a stuck task, but neither is automatically reported as completed capture.

After confirmed helper exit, the supervisor validates/finalizes only its own local protected spool FD on the approved state filesystem, compares exact independent approval length/content identity, fsyncs/verity-freezes and commits the resource state. No helper-written diagnostic or hash alone authorizes content. A helper that exits abnormally, exceeds a limit, leaves a partial spool or disagrees with approval yields refusal and journaled owned cleanup. The same helper isolation applies when checking a client-provided FD that claims to reference an earlier broker artifact; alternatively the broker may resolve an already authenticated immutable artifact ID using its own journal/held FD, without touching a hostile caller filesystem.
