### Package payload policy decision

Expected manifest format is versioned rows: {package:{name,version,architecture}, debSha256, path, kind, bytes, sha256, mode, uid, gid, target}. kind is regular-file, directory, symlink or hardlink; target is null for regular files/directories. SHA256 is file content for regular files and UTF-8 link text for links; directories have bytes 0 and SHA256 of empty bytes. Capture security.capability and other security xattrs only through an explicit supported extension; until implemented, reject packages/installed entries requiring such metadata rather than ignore it. Compare owner/group/mode, payload bytes and links; timestamps are intentionally normalized and excluded. Directories may share ownership only with identical expected metadata. Multi-package file collisions reject unless identical kind/content/metadata; differing replacements require an explicit authenticated replacement rule. Reject active diversions, nontrivial statoverrides and alternatives-generated package path changes until exact package/version-specific derivations are approved. Never infer replacement authorization from retained dpkg state.

Capture every installed .deb including bootstrap closure before install, with package identity, signed index row suite/component/filename/size/SHA256 and actual held payload digest. Determine bootstrap requested set from the reviewed debootstrap execution in the immutable environment and bind its downloaded package stream to signed indexes, then cross-check the complete installed tuple set; retained dpkg database cannot supply an omitted payload. Missing authenticated bootstrap payload blocks qualification. Payload evidence is retained outside caches and archived from the same bounded snapshots used to parse.

Parser bounds: ar total input at most maxArtifactBytes, member count at most 8, fixed 60-byte ar header validation, exactly one debian-binary member with 2.0 marker, exactly one control.tar and one data.tar with supported fixed compression choices (uncompressed/gzip/xz), no duplicate recognized members or ambiguous GNU/BSD long-name mechanisms. At most 1,000,000 decoded entries and 8 GiB cumulative decompressed bytes across all payloads, additionally constrained by configured rootfs/artifact/free-space budgets. Each decompressor read is bounded by remaining allowance and rejects trailing streams, truncated members, sparse files, devices/FIFOs/sockets, absolute/dot/escaping names, duplicate data paths, PAX/GNU path override ambiguity and unsupported security metadata. Hardlinks may reference only an already-seen regular file within the same package; verify target identity/content and installed same-inode relation, rejecting cycles/forward/escaping references. Symlink text must stay inside qualified root semantics without following host paths.

Comparison phase: parse/authenticate payloads, install, compare all payload-owned paths before normalization; run exact approved normalization; compare surviving paths afterward plus exact replacements/deletions. Initial exception registry is empty: unsupported maintainer-script modifications fail closed and must gain separately reviewed package/version/path derivations from authenticated script/input bytes before production can pass. Generated extra paths must have explicit derivation rules; exact volatile cleanup subtree policy may delete apt caches/lists and logs/tmp as currently enumerated, but does not exempt a package-owned path from pre-normalization verification. ## Revision 3 — final authority and numeric semantics clarifications

This section makes the approved-lock authority explicit and corrects numeric type wording throughout. It does not authorize source implementation or remove any evidence gate.

The fixed root-owned launcher resolves an action plus requested lock digest exclusively in `/etc/decomp-thing/approved-actions/v1/`, a root-owned directory outside all caller checkout/staging trees, with root-owned non-writable parent directories and no-follow regular-file reads. The root-owned launcher installation pins the approval authority public-key fingerprint and approved action-manifest digest index; that index and each lock/action manifest are authenticated by that authority. The index is not supplied by the caller or copied from its build record. Only a separate administrator-managed deployment of independently reviewed/authenticated lock artifacts may update this store and index; neither protocol requests, mutable checkout code, worker UID nor provenance records can add approval. Implementation must refuse if the approval key/index/store is absent, mutable, invalid or does not authorize the requested lock. No actual approved key/digest is invented for the inert implementation.

A lock's inputRecipeSha256 binds an approved action manifest containing the entire ordered source/resource/build/plugin closure and dependency/classpath identities, per-file byte digests and action parameters. The launcher first authenticates that approved root-owned manifest, then captures client no-follow descriptor snapshots and requires their complete canonical recipe identity and source closure to equal that approved manifest. It rejects missing, extra and changed inputs before compilation or execution. Captured recipes and rehashed records are comparison inputs only; they cannot authorize a source, plugin, image or action. The immutable environment identity must match the same approved lock, and actual execution uses that selected environment. Authenticating image bytes alone never authorizes arbitrary client sources. Packaging independently replays payload-to-normalized-retained-tree comparison and exact approved transformations; earlier provisioning checks alone cannot accept a subsequently rewritten retained tree.

Required inert controls: test_launcher_rejects_forged_self_consistent_lock_image_recipe_tuple; test_launcher_rejects_unapproved_source_with_self_consistent_recipe; test_launcher_rejects_action_source_closure_mismatch_before_compile; test_launcher_accepts_approved_root_owned_lock_and_exact_inputs. Simulated approval-store fixtures remain inside the repository and explicitly model trusted administrator installation; they do not count as production approvals. Missing/mutable approval store and record-only approval rewrite controls must fail before launching a compiler.

Independent schema corpus additionally requires const 1 accepts 1.0; uniqueItems rejects [1,1.0]; const 1 rejects true; integer accepts 1.0 and rejects 1.5. Evaluate numeric values according to JSON Schema mathematical value semantics, with booleans distinct, rather than Python subclass/type equality. Preserve all previously specified finite vocabulary/meta-validation, unselected-branch validation, local-only references and resource bounds.
