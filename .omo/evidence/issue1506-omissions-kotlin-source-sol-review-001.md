## R1 — enforce typed window cap before allocating v2 origin identities

`ReferencedDataByteEvidence.kt:47` executes `value.windows.map { Triple(...) }.distinct()` before the common 0/1..32 cardinality requirement at :49. Unlike the historical v1 branch, an over-cap v2 list is traversed and an additional list plus distinct set are allocated before admission rejects it. The cost scales with the entire supplied list, although only 32 windows may be admitted. This remains true for a public typed construction route: `RecoveredProgramModel` validates supplied evidence through `Budget.charge` (`ProgramModel.kt:52–58`, evidence :27–28), and prompt/render validation also calls this function. An already constructed input list does not authorize another unbounded allocation during admission.

The lexical and canonical wire readers have independent pre-append window caps, so this is not a demonstrated wire bypass. It is a concrete gap in the shared public typed validator and the approved bound-before-work contract. Move the common window cardinality check before v2 identity mapping/deduplication (and preserve v1 semantics). An authored inert control can supply an `AbstractList` whose `size` is 33 and whose element access throws: validation must issue the cardinality refusal without reading any element. Retain ordinary 32-window/v2-conflict controls. No large fixture, raised cap, or native execution is necessary.
