## Resolver byte contract already reviewed

`AcpProviderDnsResolverCandidate` at `AcpProviderDnsRuntimeProfile.kt:142-185` is a validation/serialization candidate. Its identity is SHA-256 over ASCII `provider-dns-resolver-policy-v1`, one NUL, followed by fixed-order `resolv.conf`, `nsswitch.conf`, `hosts`, each preceded by a four-byte big-endian length. Returned file bytes are defensive copies. This digest commits bytes, **not approval, deployment network permission, source provenance, owner uid/gid or filesystem capture**.

| Input | Accepted bytes / bounds |
|---|---|
| All three files | ASCII printable bytes plus LF only; final LF; no CR, NUL, tab, non-ASCII; at most 32 nonempty lines, 1..256 content bytes each; no leading/trailing spaces or doubled spaces |
| `resolv.conf` | 1..4096 bytes; one to three distinct canonical numeric nameserver lines; optional final `options timeout:[1-5] attempts:[1-2]` in that exact order |
| Numeric address | Canonical dotted IPv4 or lowercase canonical IPv6; no hostname, zone, port or brackets; mapped IPv6 uses `::ffff:<dotted IPv4>` |
| `nsswitch.conf` | 1..64 bytes and exactly `hosts: files dns\n` |
| `hosts` | 1..128 bytes and exactly `127.0.0.1 localhost\n::1 localhost\n` |
| Aggregate | At most 4288 bytes, checked before file copying |

Search/domain/sortlist/include, comments, blank lines, extra options, host-provider aliases, duplicate addresses and options ordering changes are refused. The line/byte ceilings cannot all be reached with this stricter grammar; existing exact-cap invalid controls are negative controls, not accepted full-size production files (`AcpProviderDnsRuntimeProfileTest.kt:137-147`, checkpoint review).

Canonical syntax is deliberately insufficient for destination admission. The frozen tests explicitly accept `0.0.0.0`, `255.255.255.255`, `::`, `::1` and documentation literals (test lines 116-120). No production approval follows. An approved policy must separately choose the exact real resolver addresses and justify their reachability/authority in the broker network placement. Do not promote test `192.0.2.0/24` / `2001:db8::/32`, ambient `/etc/resolv.conf`, loopback stubs, multicast/broadcast/unspecified addresses or whichever resolver happens to work into approved production policy.

The native fixture currently writes `nameserver 127.0.0.1\noptions timeout:30 attempts:1\n` (`AcpProviderNativeDnsContractTest.kt:145-147`). Timeout 30 is outside this production candidate grammar. Its full Java-home bind and relocation are expressly fixture-only (lines 465-478). These fixtures must retain a separate authenticated qualification identity; they cannot become the production policy or profile.

## Filesystem ownership and runtime limits

The approved Task6 plan, not the candidate parser alone, requires each capture tree to have one declared owner: root `0:0`, or the invoking service uid and configured primary gid. Source directories are 0755; data files 0644; only explicitly manifest-listed executables 0755. Refuse mixed/unexpected owners, writable group/world bits, setuid/setgid/sticky bits, ACLs, capabilities and unapproved xattrs. Root ownership never waives hashing. The candidate JSON merely validates declared `sourceOwner` numbers and per-record owner labels (`RuntimeProfile.kt:50-55,67-83`); service uid/gid matching requires future actual capture code.

Preparation uses service-owned 0700 directories/0600 files. Publication requires fresh single-link service-owned copies, 0400 data/resolver files, 0500 executable files and hardened directories, with 0700 private control parent. Descriptors, device/inode/mount identities and before/open/after content/mode/owner checks must bind source and copies. No symlink dereference, hardlink alias, special file, unexpected mount crossing or change after hardening. Cleanup may restore directory write permission only under the private cleanup lock after terminal owner proof and exact tree authentication; uncertainty retains the tree. Same-uid hostile processes outside supported isolation are not defeated merely by these modes.

Runtime schema ceilings: 1 MiB manifest, 2048 entries, depth 16, 256 MiB total regular bytes, 16 MiB non-module file, 192 MiB `jdk/lib/modules`, 256 ELF edges, 32 native library records. Lower configured limits and existing stricter sandbox limits remain binding. Checked sums and cancellation/deadline checkpoints must cover extraction, traversal, hashing, copying and dispatch revalidation. These constants exist at `RuntimeProfile.kt:14-21`; actual bounded assembly/capture does not exist in this checkpoint.

## What Linux/JDK/NSS source actually establishes

There is currently **no supported runnable profile** from which to infer resolver behavior. The following exact upstream references are mechanism evidence for selecting/reviewing a future profile, not an approval of these distributions. Tag-to-commit identities were resolved read-only through GitHub API: OpenJDK `jdk-21.0.10+7` -> `97a3d2372d457c5a72413df14bf08cf99545c695`; glibc `glibc-2.39` -> `ef321e23c20eebc6d6fb4044425c00e6df27b05f`. A future chosen vendor build must authenticate its own matching source/patch/toolchain relationship.

The parallel inventory researcher identified a concrete candidate family already pinned by master Dockerfile: `eclipse-temurin:21-jdk-jammy@sha256:55fb9bf738f5d9b4a6c01b39337e3070d3e27370dd3c478fd1d5d3cd2233c6d8`. This researcher did not acquire or independently inventory it. Its amd64 child manifest/config/layers and exact JDK/glibc release/source receipts have not been captured. **The OpenJDK/glibc sources below are not bound to that candidate**; in particular glibc 2.39 must not be assumed for a Jammy base. Reperform each source obligation against the exact selected authenticated binaries.

- OpenJDK's Unix native IPv6 implementation calls `getaddrinfo` with `AI_CANONNAME` and family derived from lookup characteristics. Java's API call is not a self-contained DNS packet client. [Pinned OpenJDK `Inet6AddressImpl.c`, lines 210-214](https://github.com/openjdk/jdk21u/blob/97a3d2372d457c5a72413df14bf08cf99545c695/src/java.base/unix/native/libnet/Inet6AddressImpl.c#L210).
- In this glibc source, resolver initialization reads `LOCALDOMAIN` / `RES_OPTIONS`, initializes host.conf, and, even with an existing resolv.conf lacking search/domain, derives a search domain from hostname. Missing nameservers can imply loopback fallback. Empty environment and exact files are necessary; a fixed dotless private UTS hostname and actual absence/default-file proof are also review requirements. [Pinned `res_init.c`, lines 243,482-507,523-525](https://github.com/bminor/glibc/blob/ef321e23c20eebc6d6fb4044425c00e6df27b05f/resolv/res_init.c#L482).
- A dotted name without a final dot can undergo suffix searches following eligible failures. Thus fixed literal `chatgpt.com` plus no explicit search directive does not by itself prove only that DNS QNAME. Bind private hostname/UTS state, then qualify negative-answer paths. Changing worker literal or resolver grammar would need a reviewed recipe/worker commitment change. [Pinned `res_query.c`, lines 343-415](https://github.com/bminor/glibc/blob/ef321e23c20eebc6d6fb4044425c00e6df27b05f/resolv/res_query.c#L343).
- This glibc has built-in `files` and `dns`; other NSS module names use library loading. Therefore `libnss_files.so.2` / `libnss_dns.so.2` are not universally required external dependencies. Pin actual libc build and inspect its behavior instead of inventing DLOPEN edges just to fill a fixed filename list. [Pinned `nss_module.c`, lines 132-171](https://github.com/bminor/glibc/blob/ef321e23c20eebc6d6fb4044425c00e6df27b05f/nss/nss_module.c#L132).
- Depending on build, getaddrinfo can try nscd and reads `/etc/gai.conf` for address ordering. Private closure must ensure ambient daemon sockets and extra config are absent/inaccessible, or authenticate explicit reviewed inputs. A three-file manifest alone is not a proof of all file/socket access. [Pinned `getaddrinfo.c`, lines 445-464 and 1623](https://github.com/bminor/glibc/blob/ef321e23c20eebc6d6fb4044425c00e6df27b05f/nss/getaddrinfo.c#L445).
- Resolver retries can traverse nameservers; dual queries and TCP fallback on truncation exist. `timeout` and `attempts` are not one-packet or whole-invocation time guarantees. Decide explicitly whether approved DNS egress includes UDP/TCP 53 and retain the outer absolute deadline/process termination boundary. [Pinned `res_send.c`, lines 323-360,817-819,1174-1180](https://github.com/bminor/glibc/blob/ef321e23c20eebc6d6fb4044425c00e6df27b05f/resolv/res_send.c#L323).

These are concrete reasons that `java -version`, a successful DNS lookup, synthetic edge reachability or a host library listing cannot approve the runtime. A source-bound file/open/library/socket observation on the actual packaged profile must confirm the intended absent inputs, fixed hostname, NSS implementation and DNS egress behavior. Do not broaden mounts to make an unexpected read succeed.

## Call, authority, privacy and cleanup boundaries

The stable worker calls `InetAddress.getAllByName("chatgpt.com")` once, selects the first address, emits only magic/family/4-or-16 bytes, and suppresses errors (`src/providerDns/java/decompengine/acp/ProviderDnsWorker.java:10-24`). It accepts no hostname argument and receives no credentials. Parent DNS process conversion uses `InetAddress.getByAddress` and requires reaped process and closed streams before returning (`AcpProviderDnsProcess.kt:89-104`). Current launch material clears the environment and fixes worker flags (lines 320-325); the future loader launch must preserve these constraints.

Stable HTTP still resolves in the parent at `AcpProviderBroker.kt:978`. The isolated worker is **not wired into HTTP yet**. Existing HTTP constrains one connect, no proxy, original hostname TLS endpoint identification and TLS1.2/1.3 (lines 968-995), with fixed canonical approved endpoint in `AcpProviderTransportPolicy.kt:13` and production network authority at broker lines 1135-1142. DNS bytes supply routing evidence only; they do not widen host, path, operation, model, redirects, proxy or private-network permission. No DNS result should cause credential use before context admission.

Factory has no production DNS permit issuer (`AcpHarnessFactory.kt:159-171`). Boundary context registry is identity based; consume removes first and checks consumer identity, request digest and exact invocation deadline (`LinuxBubblewrapBoundary.kt:1677-1694`). Task6 must add production composition with immutable request/profile/resolver/transport/endpoint/model/invocation/deadline binding and factory-owned exact-harness permit. Names, reflected constructors, arbitrary candidate hashes or copied configuration cannot substitute for that issuer.

Production DNS belongs in the already approved broker network boundary, never the agent/candidate network namespace. Qualification's no-external-route loopback blackhole is separate. Preserve one-address/one-connect/exchange, at most one context per boundary, eight lifetime dispatch slots and one simultaneous unverified ticket; reserve slots before scheduling. Exact invocation deadline clamps all DNS dispatches; retry/callback/remediation cannot renew it. Close revokes first and shares one absolute cleanup end through resolver/backend/boundary/tree deletion. Retain trees/descriptors, lease, timers, unresolved/late starts, processes and pipes until exit/reap/join/closure proof; uncertainty means quarantine and UNVERIFIED. Later remediation proves cleanup only.

DNS configuration is non-secret but deployment sensitive: ordinary evidence should retain immutable digests and bounded typed outcomes, not raw addresses, host paths, query answers, namespace/PID inventories or resolver error text. Restricted qualification receipts may retain necessary bounded observations under the coordinator's existing evidence policy. Never add credentials, prompts, auth cache contents or ambient environment to manifests, args or logs.

3. **Construct real runtime candidate offline from approved inputs.** The parallel runtime inventory owner supplies exact link-free archive/source/toolchain/recipe closure. Required file-name lists are constraints, not claims that a vendor image has these bytes or needs every optional library.
4. **Close loader/environment/file/socket semantics.** Bind the packaged loader, fixed `--inhibit-cache --library-path` argv, empty environment, private mounts, dotless private hostname/UTS state and absence of ambient host config/cache/daemon endpoints. Exercise changed file/owner/mode, wrong profile/resolver/deadline/request/consumer, replay, forged/reflected objects, close/preparation/start races and retained late owners through actual supported-profile issuance. Keep reflection-only tests scoped as components.
7. **Qualify exact profile on observable isolated hosted lane.** Authenticate helper/compiler/linker/worker/runtime/source/command receipts; preserve approved outer 0x1400 capability bootstrap and zero inner capabilities/NNP. Observe real fixed-host A/AAAA query against isolated blackhole before cancel/deadline, prove no address/connect admission, actual reap/no zombie, streams closed, owner joined, private tree deleted and complete namespace destruction. ## Proposed approval record for source-owner review

This is a concrete schema proposal, not an accepted schema or a populated approval. Keep candidate parsing and this approval separate. Unknown or missing fields must fail; digest fields are identities only until authenticated by the application commitment and exact approved review/provisioning closure.

| Required field | Meaning / source of authority |
|---|---|
| `schema` | Fixed version, proposed `provider-dns-resolver-approval-v1` |
| `policyId`, `revision` | Stable bounded policy identifier and explicit immutable revision selected by #958 owner |
| `transportDescriptorSha256`, `endpoint`, `operation` | Exact immutable already-approved transport; endpoint fixed to existing canonical service, operation fixed to RESPONSES_CREATE |
| `runtimeProfileId`, `runtimeManifestSha256`, `workerSha256`, `applicationBuildSha256` | Exact selected authenticated closed profile/application/worker; no version-only match |
| `resolverFiles` | Exactly three fixed-name records with size/SHA-256; exact canonical bytes captured with approval input |
| `resolverPolicySha256` | Existing domain/length-framed three-file candidate identity, recomputed from actual authenticated bytes |
| `sourceOwnerPolicy`, `sourceUid`, `sourceGid`, `sourceTreeIdentitySha256` | Declared root or configured service identity and provisioning receipt; actual capture must independently observe files/metadata |
| `networkAuthorityId`, `networkAuthoritySha256`, `deploymentPlacementId` | Independently approved broker network policy and immutable deployment placement; **cannot be derived from nameserver text** |
| `dnsDestinations` | Exact ordered numeric addresses, fixed port 53, approved transports, resolver operator identity and explicit classification/permission for any private/local address; must match canonical bytes |
| `queryPolicy` | Fixed worker hostname, permitted A/AAAA behavior, explicit search/alias expectations, selected source semantics, fixed private dotless hostname and UTS/mount identity recipe |
| `launchClosureSha256`, `sourceClosureSha256` | Authenticated fixed loader/argv/empty-environment/mount/absent-file/socket closure and exact JDK/libc source/patch/toolchain identities |
| `provisioningReceiptSha256`, `policyDecisionReceiptSha256`, `independentReviewReceiptSha256` | Exact bounded receipts proving origin, policy-owner decision and independent scoped review; caller-provided hashes alone cannot satisfy |

Application distribution must commit the approved record digest and its receipt/source/network trust roots (or an existing authenticated equivalent explicitly adopted under review). Configuration selects that entry by identity. The app/issuer compares every binding; it cannot accept a new user record just because its hashes validate, a host uid is root, or a signed statement comes from an unrelated/unrecognized key. Provisioning records establish where approved bytes came from; policy-owner review grants the intended resolver/network authority; native qualification proves the implementation honors it. Each is separately necessary. If the repository has no existing approved deployment network-policy record or trusted issuer, the source owner must define/review that contract under #958 before enabling #1510 consumption.
