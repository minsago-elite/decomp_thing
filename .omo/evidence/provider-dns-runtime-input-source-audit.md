## Result

No authenticated, approved, link-free DNS runtime image or approved JDK archive/build closure was found in the inspected repository caches. The frozen contract correctly describes a structural candidate and unconditionally refuses usable profile admission. It must eventually acquire one concrete reviewed profile; adding more synthetic candidates or an indefinitely empty production registry does not complete #1510.

This is a candidate for a bounded, separately approved packaging lane using the JDK and matching native runtime from that exact base image. Its use as a DNS source, platform child/config/layers, actual JDK version, file identities, output and jlink semantics have **not** been approved or established. The application Dockerfile's mutable `apt-get update/install` stages are not a closed builder recipe.

The smallest credible construction is a `java.base` jlink output plus the same approved distribution's exact ELF loader/native/NSS subset, then a regular-only runtime archive and application-committed output manifest. The pinned base makes this a concrete acquisition target, not a ready runtime. The approved plan currently requires regular-only JDK archive extraction and rejects symlink-bearing distributions; an OCI-backed packaging lane therefore requires an explicit reviewed source-policy/recipe amendment before use. It cannot be quietly substituted for the approved archive route. Production traversal remains strict in either route.

## Closed construction proposal

This is a proposed packaging policy, not current approval. The existing full-JDK walker remains unchanged.

1. **Source/tool authority.** Begin with the committed Temurin digest as the named candidate. Acquire only through an authorized lane into repository-local cache; retain exact index/manifest MIME types, sizes/digests, unique `linux/amd64` child manifest, config, compressed layers and decompressed diffIDs. Reject ambiguous platform selection, unexpected foreign layers, whiteout/path ambiguity and decompression bounds violations. Review vendor provenance, exact release, licensing and supported CPU/kernel ABI. Do not equate a registry tag or observed image ID with that receipt. For strict adherence to the current archive plan, instead approve a particular regular-only JDK archive with size/digest and provenance; none exists here. An OCI selection route needs the explicit amendment already noted.

2. **Hermetic jlink recipe.** Freeze the packaging script, builder platform/OCI graph or full tool dependency manifest, fixed working directory, empty environment, all executable/JVM/plugin/module and optional external strip-tool inputs, and exact existing planned argv `--add-modules java.base --no-header-files --no-man-pages --strip-debug --output <fresh-build-local-image>`. The builder's jlink implementation and defaults are part of the pinned toolchain. Authenticate whether this `--strip-debug` actually calls native tools and pin them if so. No apt/pip update, network, host JDK, host mounts or PATH-based executable selection during assembly. Produce in a fresh repository build subtree. Treat source archive, builder, recipe, jmods, jlink output and final manifest as separate identities; `sourceArchiveSha256` cannot hide an unbound builder.

3. **Regular output only.** Inspect the whole generated image without following links. Require only `java.base`, exact release/module identity, planned required JDK files, and every emitted configuration/legal file. Reject every symlink/hardlink/special file, extra module, JAR/service SPI/launcher hook, duplicate path, unsupported mode/owner or overflow. All license files must remain. If jlink emits legal links or any forbidden entry, reject this output and revise the reviewed construction recipe; do not dereference or silently omit it. Resolve the libjvm size gate from actual output. Two builds from identical approved inputs must produce identical manifest/file bytes.

4. **Native closure from the same approved distribution.** Select direct regular object member paths by explicit path+size+digest in the approved source receipt. Do not look up a mutable SONAME link and copy whatever it points at. A versioned regular source object may be deliberately mapped to one fixed destination name only when both source and destination are reviewed in the recipe; this is new-file construction, never runtime link traversal. Target ELF64, little endian, `EM_X86_64=62`, Linux GNU libc ABI and exactly the frozen Java PT_INTERP `/lib64/ld-linux-x86-64.so.2`. Record libc/loader build identity, symbol-version requirements and CPU/kernel constraints from actual bytes. The exact subset of the frozen allowlist must follow the inspected dependencies, not this report: loader, libc, libm, libdl, libpthread, librt, zlib, libstdc++, libgcc_s, libnss_files, libnss_dns, libresolv only if required/provided. No host fallback and no blanket copying all names to make tests pass.

5. **Non-executing inspection plus semantic evidence.** Read PT_INTERP, DT_NEEDED, SONAME, RPATH/RUNPATH, symbol versions and load directives from retained bytes; recurse over the selected exact closed map. Reject unresolvable/duplicate SONAMEs and external search/audit/filter/config directives. Record every JVM/libjli/libnet and libc NSS `dlopen` edge from authenticated implementation/build evidence. DT_NEEDED alone does not reveal the complete DNS closure. NSS backend organization is libc-version-specific; missing external `libnss_dns.so.2` is not automatically a defect or permission to search host libraries. Explicitly exclude nscd/system sockets and ambient resolver/search/plugin files from the runtime namespace. Source/code review plus isolated observed behavior must support that assertion.

6. **Publish and approve one real profile.** Package the accepted regular tree into a bounded regular-only archive, freeze archive size/digest, output manifest, ELF edges, loader argv, recipe/tool/input receipts and separate fixed worker JAR commitment into an application distribution resource. Independent review approves that exact tuple. Only then add the concrete profile identity/digest to the private production selector; user paths/adjacent hashes do not authorize it. Reject missing/changed/extra bytes before context or secret access. #958 must independently approve exact resolver files/nameservers and the broker network placement before any usable context. That policy is not guessed from the packaging image or local `/etc`.

The pinned fixed loader argv uses `--inhibit-cache --library-path /provider-dns-runtime/native:/provider-dns-runtime/jdk/lib:/provider-dns-runtime/jdk/lib/server`. Those flags alone do not disable glibc's default directory search. The supported namespace must contain no usable host default `/lib`/`/usr/lib` trees or ld.so.cache and must admit only the fixed private resolver/proc/dev mounts. Verify actual launcher/libjli/JVM behavior with this exact command, empty environment and read-only mounts; do not infer it from an ordinary `java -version` success.

## Reuse limits and first startable deliverable

Existing `BehaviorElfRuntimeMetadata.kt` SHA256 `e19bcb0a8ba4b20fb62f1d428a508eb0501711c52cef74324b41f7551b582dc6` provides bounded non-executing ELF table parsing and rejects RPATH/RUNPATH and several external-loading tags. It can seed a DNS inspector, but currently returns no SONAME/symbol-version/dlopen proof. Its companion `BehaviorRuntimeClosure.kt` SHA256 `a1a9775099c637f1c9cadfe2a92d344fc8578891ff0af102d37cc7330e40af6b` resolves host paths and a loader cache; do not reuse that resolver as DNS authority. A JVM often carries intentional origin-relative search metadata, so the actual candidate must be inspected and either rejected or supported through an explicitly reviewed confined-path rule; no blanket relaxation.

`BoundedTarXzArchive.kt` SHA256 `5dd9671df46d898d315d2c04e22b85d1814f1de079f0b950f3c9b9c24dc4c69e` supplies bounded positional archive-reading patterns. Its LLVM source `scan` deliberately admits symbolic links; `scanGeneratedSnapshot` forbids them but has LLVM-specific generated-header/mtime semantics. Neither is a drop-in vendor archive or OCI parser. Adapt bounds/descriptor patterns only under a separately specified archive profile. `LlvmSourceArchiveMaterializer.kt` SHA256 `1fe8be8b85cfff45d0abe8e92cb9c8b261e9efcdf22b28cf37d18725016a8708` demonstrates signature/hash/current-input reauthentication, with LLVM-specific authorities that must not approve JDK bytes.

The first startable implementation deliverable is the runtime input-lock/inspection checkpoint, followed immediately by authorized acquisition of the concrete candidate, rather than further synthetic profile work: define a domain-separated JDK/builder/source/recipe approval receipt; implement bounded offline inspection of already-approved archive/OCI descriptors and exact selected regular member mapping; emit a deterministic rejected-or-complete closure report including the per-file limit decision. It must consume expected identities from application/review authority and never offer a usable profile for an incomplete lock. For the concrete pinned base, the next external prerequisite is the authenticated platform graph/payload receipt and reviewed OCI policy amendment (or an approved regular-only JDK archive under the current policy). That acquisition belongs to the coordinator's authorized owner, not this read-only audit.

Required gates before admitting the first profile: independent input/recipe review; exact complete archive/tool hashes and ABI; two identical packaging outputs; whole-tree no-link/owner/mode/bounds validation; static dependency and explicit dlopen closure; actual fixed-loader java.base worker launch in the isolated supported namespace; actual factory issuance/composition with all forgery/race/cleanup retention controls; #958 resolver identity; and the dedicated observable hosted cancellation/deadline DNS lane with full teardown proof. Required CI must fail when the real package/receipt is absent. A reflected context, host JDK bind, local hash manifest or partial native record cannot substitute for any gate.
